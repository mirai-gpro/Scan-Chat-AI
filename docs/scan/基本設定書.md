## 1. 設計思想

### 1.1 最終ゴール（絶対）と、設計思想（手段・従属）

- **最終ゴール（絶対）**: 検査票 → **正確な JSON（①漏れなく ②捏造なく ③余剰を渡さない）** → Elith → 高精度 AI 診断。
- **設計思想（手段・従属）**: 多様な検査票フォーマットに **ネイティブマルチモーダル LLM** を活かし柔軟に対応。出力は、**業界標準の電子データ構造**[^std]に、臨床的意味を解釈して対応。
  - 出典: `docs/scan/scan_canonicalization_standard_format_design.md` §0。

[^std]: **業界標準の電子データ構造（サマリー・詳細は §2.4）**: 健診・人間ドックの電子データには紙面（見た目）と違い業界標準が存在する。①**健診標準フォーマット（KMAT）** = 日本医学健康管理評価協議会が策定した業界標準（標準名称ベース・CSV、ver5.0 ≒ 約 2000 項目）。②**特定健診・特定保健指導 標準仕様書** = 国（厚生労働省）の法定電子データ様式（XML／HL7 CDA R2、第 4 期 2024〜2029）。本システムは①を②正準化の主標的、②を法定コア・サブセットとして扱い、読取値の**臨床的意味（項目名・単位・判定）を解釈して標準の統制語彙へ写像**する（診断＝Reasoning は Elith が担当。§1.2）。

### 1.2 Perception と Reasoning を分ける（役割分業）

医療データ処理は **「紙面から正しい値を読む（Perception）」** と **「臨床的意味を解釈する（Reasoning）」** の二つの別タスクから成り、それぞれ別モデル・別サービスに割り当てる。

| レイヤ | 性質 | 担当 |
|---|---|---|
| Perception（読取） | 視覚＋構造化 | Scan-Chat-AI（Gemini・忠実な転記に徹する） |
| Reasoning（診断） | 推論＋臨床知識 | 診断 AI（Elith・別 LLM） |

Scan-Chat-AI は「診断・治療判断を一切しない／忠実な転記に徹する」。出典: `docs/architecture/system_architecture_overview.md` §1.1、`scan-prompt.ts:7-10`。

### 1.3 2 層アーキテクチャ（読取 / 正準化）— 矛盾は「分ける」と消える

「native multimodal で自由に読む」思想と「標準フォーマットへ揃える」ゴールは、**層を分けると衝突しない**。

| 層 | 方式 | 思想との関係 | 得点する対象 |
|---|---|---|---|
| **① 読取 (Perception)** | ネイティブマルチモーダル LLM（**現行維持**） | レイアウトが多様 → テンプレ化しないのが正しい | 紙面 → 忠実な転記（値・単位・基準・判定） |
| **② 正準化 (Normalize)** | **業界標準フォーマットへの決定論マッピング（新規）** | 標的は「1 つの標準マスタ」＝様式別テンプレではない＝汎化しない負債でない | 名寄せ・単位・判定の統一、余剰/不足の判定 |

②は「ピクセル/レイアウトの照合」ではなく、LLM が自由に読んだ **意味（項目名・単位・判定）を統制語彙（標準マスタ）へ写像**する。現代の医療データ連携の標準手法であり、「テンプレ OCR を使わない」思想と矛盾しない。出典: `docs/scan/scan_canonicalization_standard_format_design.md` §2。

### 1.4 決定論・捏造ゼロ・保守的マッピング

- **判定・整形は決定論プログラムに集約**。LLM に判定・整形・補完をさせない（捏造の温床にしない）。
- **保守的マッピング**: 高信頼で写像できた時だけ正準化する。写像不能は**元のままフラグ**（強制変換で誤マップ＝捏造を作らない）。
- **余剰は自動削除せずフラグ提示**、不足は `deficient` でブロック。
- 出典: `docs/scan/scan_canonicalization_standard_format_design.md` §5、CLAUDE.md「納品整形は決定論プログラムに集約」。

### 1.5 個人情報（PII）と医療データの物理分離

- `customer` スキーマ（PII）と `diagnosis` スキーマ（非 PII）を **`diagnostic_user_id` のみで橋渡し**。氏名・住所・生年月日を診断系／外部／S3 に載せない。
- 氏名 OCR のみでの顧客割当確定は禁止。
- 出典: `docs/architecture/system_architecture_overview.md` §1.2、`docs/architecture/data_integration_requirements.md` §1.3、`docs/lab/lab_integration_workflow.md` §1.1。

### 1.6 LLM ネイティブ / 公式推奨パターン

- **Markdown ファースト**（AI 間通信の一次形式。JSON はサーバ側でバッチ変換）。
- 画像は **Files API + バイナリ direct**（Base64 inline 化しない）、レスポンスは**ストリーミング**、下流リソース近接配置（Vercel iad1 ≒ Gemini US）。
- 出典: `docs/architecture/system_architecture_overview.md` §1.3/§1.6/§3.2。

### 1.7 業界標準の位置づけ（②正準化の標的）

紙/PDF の**見た目**には支配的な統一標準は無い（機関裁量で様式が変わる → 読取はテンプレ OCR 不可）。一方で**電子データ構造**の業界標準は存在し、②正準化の標的になる。本システムは次の 2 標準を参照する（詳細は §2.4）。

1. **健診標準フォーマット（KMAT）** — 人間ドック・一般健診向けの**業界標準**。日本医学健康管理評価協議会が策定。
2. **特定健診・特定保健指導の標準仕様書** — **国（厚生労働省）基準**の法定電子データ様式。

## 2. 基本設計

### 2.1 システム全体（4 構成 + 診断 AI）

```
ユーザー（受診者）
  │ 購入            │ スキャン/問診          │ 結果閲覧
  ▼                 ▼                        ▼
(a) HP/EC       (b) Scan-Chat-AI        (d) ユーザー Web アプリ
 顧客マスタ      検査票の読取→Markdown     マイページ（結果/進捗/通知）
 (PII)          音声問診(Live)・ステートレス
  │ diagnostic_id   │ scan_md / 問診_md        ▲ diagnostic_result
  ▼                 ▼                          │
     ┌──────────── 診断系 DB（匿名・PII なし）────────────┐
     │  diagnostics / scan_artifacts / diagnostic_results │
     └────────────────────────────────────────────────────┘
        │ scan_md + 問診_md          ▲ diagnostic_result
        ▼                            │
     (c) 診断 AI（株式会社 Elith）：臨床推論、Markdown+JSON を返す
```

出典: `docs/architecture/system_architecture_overview.md` §2〜§3。Scan-Chat-AI は **wellfort-site（www.wellfort.co.jp）配下の診断アプリ**であり、管理 UI は wellfort-site 側、Scan-Chat-AI は API 提供側（CLAUDE.md「アプリ構成／管理画面の所在」）。

### 2.3 データフロー（スキャン系）

```
撮影(JPEG) → /api/scan (Gemini Flash, streaming, thinkingBudget:0)
  → 10列 Markdown（読み取った値/推論値/判定/備考…）
  → toMeasurements → sanitizeMeasurementsForDelivery（決定論整形）
  → （②正準化：標準マスタへの写像・余剰/不足判定：段階導入）
  → Elith 納品 JSON（lean measurement）→ S3（elith_s3_data_handoff_spec 準拠）
  → Elith が Markdown/JSON を読み診断
```

- **1 画像 = 1 リクエスト**（Vercel 関数タイムアウト ~60s のため分割。クライアントが順に呼ぶ）。出典: `docs/architecture/system_architecture_overview.md` §10、CLAUDE.md「インフラ／実行モデル」。
- S3 パス/命名: `/{prefix}user/{client_id}/date/{YYYY_MM_DD}/{format_id}_date_{YYYY_MM_DD}_user_{client_id}.json`、`client_id = diagnostic_user_id`（PII 非含有）。出典: `docs/elith/elith_s3_data_handoff_spec.md`。

### 2.4 標準フォーマット（②正準化の標的）

#### 2.4.1 健診標準フォーマット（KMAT）— 人間ドック・一般健診向け（業界標準）

- **策定**: 日本医学健康管理評価協議会（日本人間ドック・予防医療学会など健診関係団体で構成）。管理事務局は日本医師会総合政策研究機構（JMARI）系。
- **特徴**: CSV・**標準用語（名称）ベース**（原則コードでなく標準名称）、判定名称・記号（未満/以上）・標準用語の統一、画像所見も用語リストで標準化。**特定健診にも対応**。
- **規模**: **KMAT ver5.0 ≒ 約 2000 項目**（2025-02 公開）。従来の 1500 項目から 2000 項目へ 2025 年度中に移行。
- **運用ソフト/維持**: POST.ex®（変換ソフト）、**HASTOS®**。維持運用は一般社団法人 日本医学健康管理推進機構（HASTOS / hastos.jp、商用 2025/4〜）。
- **業界の主流アプローチ**: バラバラの様式を**システム側でこの標準データへ強制変換（マッピング）**する（＝本システム②と同じ発想）。
- **一次資料**: [健診標準（kenshin-hyojun.jp）](https://www.kenshin-hyojun.jp/) / [HASTOS 最新健診標準フォーマット説明資料 2024.8（PDF）](https://hastos.jp/wp-content/uploads/2024/08/20240802_1.%E6%9C%80%E6%96%B0%E5%81%A5%E8%A8%BA%E6%A8%99%E6%BA%96%E3%83%95%E3%82%A9%E3%83%BC%E3%83%9E%E3%83%83%E3%83%88%E8%AA%AC%E6%98%8E20240802.pdf) / [HASTOS 説明会資料 2025.2（PDF）](https://hastos.jp/wp-content/uploads/2025/02/2.HASTOS%E8%AA%AC%E6%98%8E%E4%BC%9A202502%EF%BC%88%E5%81%A5%E8%A8%BA%E5%AE%9F%E6%96%BD%E4%B8%BB%E4%BD%93%EF%BC%89v2.7fix.pdf) / [これまでの活動（kmat.jp）](https://kmat.jp/%E6%B4%BB%E5%8B%95%E7%8A%B6%E6%B3%81/)。
- **注意（R3・捏造ゼロ）**: 完全な用語リスト（約 2000 項目・単位・判定）は**推進機構/HASTOS への照会 or クライアント/Elith 経由で入手**する。当社で項目名を捏造しない。

#### 2.4.2 特定健診・特定保健指導の標準仕様書 — 国・厚労省基準

- **位置づけ**: 高齢者医療確保法に基づく**特定健診（メタボ健診）**の法定電子データ様式。実施機関 → 保険者 → 国 の**電子的データ授受**を規定。
- **技術**: XML（**HL7 CDA R2 準拠**）。データ整合性を保ちつつ簡潔な XML 構造を目指す設計。**社会保険診療報酬支払基金**が XML サンプルデータ・解説を提供。
- **期**: 現行は**第 4 期（令和 6 年度〜令和 11 年度／2024〜2029）**。仕様の訂正・追補は随時（令和 6 年 2 月の事務連絡等）。
- **主なファイル**: 交換用基本情報ファイル仕様説明書、結果情報ファイル、決済情報ファイル 等（Version はファイルごとに更新）。
- **一次資料**: [特定健診・特定保健指導 交換用基本情報ファイル仕様説明書 Ver1.41（厚労省 PDF）](https://www.mhlw.go.jp/bunya/shakaihosho/iryouseido01/dl/info02j_1-1a.pdf) / [交換用基本情報ファイル仕様説明書 1-1A/1-1B（厚労省 PDF）](https://www.mhlw.go.jp/content/12401000/001079086.pdf) / [XML サンプルデータ及び解説（社会保険診療報酬支払基金）](https://www.ssk.or.jp/smph/datahealth/tokuteikenshin/tokuteijoho/tokuteijoho_01_h30.html) / [事務連絡 令和6年2月20日（関係団体宛）](https://www.hospital.or.jp/site/news/file/1708503307.pdf)。
- **注意（R3）**: 実際の項目定義・コード・単位は上記一次資料で確認する。

#### 2.4.3 本システムでの 2 標準の使い分け

| 観点 | KMAT（健診標準フォーマット） | 特定健診・特定保健指導 標準仕様書 |
|---|---|---|
| 主体 | 業界団体（日本医学健康管理評価協議会） | 国（厚生労働省） |
| 対象 | 人間ドック・一般健診（広範・約 2000 項目） | 特定健診（メタボ健診・法定項目のコア） |
| 形式 | CSV・標準名称ベース | XML（HL7 CDA R2） |
| 本システムでの役割 | **②正準化の主標的（上位集合）**。名寄せ・単位・判定の統制語彙 | KMAT に内包される**法定コア・サブセット**。Elith が確実に要する最小項目の基準に使える |

→ **②正準化の標準マスタは KMAT を主標的**とし、**特定健診の法定項目を確実に含むコア・サブセット**として扱う。**完全マスタは一次資料受領後に差し替える**（それまでは代表検体に実在する標準項目で starter マスタを小さく作る。§3.6）。

**②正準化の処理モデル = テンプレート穴埋め方式**（設計意図）: 出力側を「標準の検査項目名・単位」で**先に固定した空テンプレート**として持ち、読取値をその該当スロットへ**穴埋め**する。全体像は §3.6。要旨は【元画像の検査結果を、正確に（漏れなく・捏造なく・不要は落として）業界標準の項目名・単位で、Elith と決めた JSON として作る】。

## 3. 詳細設計

### 3.1 読取層 — システムプロンプト（`src/lib/scan-prompt.ts`）

- **役割**: 「臨床検査データの監査スペシャリスト」。忠実転記＋不整合の露呈のみ。診断はしない。`scan-prompt.ts:7`。

### 3.4.1 画像証拠ベースの後段補修（P-perc）— 人間ドックの numeric 完全性（課題A/B/C）

**背景（人間ドックの実測課題・2026-08）**: 検診票（§4.2 の 3 期間横並び）と別系統で、人間ドックの高密度・多テーブル様式に 3 課題が残る。

- **課題A（行ごと欠落）**: 主パスが行を丸ごと落とす（実測: 甲状腺セットで FT3=3.1 が raw に一切存在しない）。既存 VQA（§3.4）は allow-list 依存で範囲外。
- **課題B（推移グラフ混入）**: 「検査結果の推移」トレンドグラフを measurement 抽出し前回値を拾う（内臓脂肪 108.0/正 140.3・LDL 102/正 129 等）。詳細表の今回値と重複＋食い違い。
- **課題C（別名重複）**: 同一項目が複数テーブル（総合判定＋詳細表＋推移グラフ）に現れ別名重複を量産（最高血圧×2・尿蛋白定性 vs 蛋白 等。rows 88〜109）。

**中核原則（Gemini/ChatGPT 再レビュー収束・2026-08）**: 3 課題は別バグでなく「主パス出力に**画像内のどの領域/テーブル/セル由来かの来歴が無い**」共通根に帰着する。→ **モデル出力を起点にせず、「画像証拠候補」と「主パス出力」の双方向照合で確定する**。§3.6.1 S3（移植カバレッジ照合＝漏れ検知）の思想を、②正準化層から**①読取層へ拡張**したもの（新原理でない）。**主パス（プロンプト・入力画像）は不変**（§4.4）。

**設計（確定・env gate＋🎯後に有効化）**:

1. **occupied-cell-first インベントリ（課題A）**: 前処理（`sharp`・**分析用コピーにのみ**適用し主パス入力は元画像のまま）で今回列の occupied セルを検出し、そのセルの行だけラベル/値を読む。「ラベルあり AND 今回セル占有 AND 主パス出力に対応なし」→ 局所 VQA で再読。全 100 行のラベルは読まない（60s 対策）。
   - occupied 判定は**複数検出器の和集合**（前景画素/色成分/エッジ・連結成分/隣接差）＋**相対閾値**（同一テーブル・列内の空/印字分布基準）。`T_high`/`T_low` の 2 閾値で中間は `OCCUPANCY_AMBIGUOUS`（**空扱い禁止・再処理**）。**迷ったら occupied**（見落とし＝全損より、空セルを VQA に渡し null 返しの方が安い）。
   - **相関失敗の防止**: 最大リスクは主パス・補助VLM・CV が**同じ今回列誤認**を共有すること。テーブル別に `current_column_confidence` を持ち、低信頼なら列再解析／低信頼・疎ページ・残留インク時はラベル列全体パスへフォールバック。VLM 2 回は独立検証にならない前提で、CV＋残留証拠監査で独立性を補う。
2. **正の証拠＝リスク別ゲート（課題B）**: グラフ由来値は詳細表の今回セルに裏付けが無い→落とす。**「タイブレーク限定」でも「全値必須」でもなく**、①高リスク出力（推移/サマリ近傍・同名複数・今回セル対応なし・備考のみ・疎今回列・領域不明）＝**証拠必須**／②通常の詳細表出力＝CV 証拠が取れなくても直ちに削除せず `EVIDENCE_WEAK` で保持（競合で勝たせない）／③過去セル・グラフに一致し今回セルに不一致＝`EVIDENCE_CONTRADICTED` で除外。**位置推定失敗はドロップせず** `AMBIGUOUS_EVIDENCE_LINK` として再読/監査（誤ドロップ＝漏れを作らない）。グラフ分類は補助信号・却下理由に留め、安全性を分類精度に賭けない。
3. **概念/実体/来歴の 3 分割 ID（課題C）**: ①概念ID `canonical_observation_code`／②意味実体キー `semantic_instance_key`（code＋検体＋部位＋測定法＋左右＋時系列役割＋`collection_ordinal`＋日時＋空腹時文脈。**dedup キー**）／③物理来歴 `evidence_occurrence_id`（page/table/row/bbox・1 Observation に複数可）。**`table_id`/`row_occurrence` を意味キーに含めない**（詳細表とサマリ表の同一検査を別実体にしない）。同一キー・同一値のみ統合、同一キー・別値は `CONFLICT_UNRESOLVED` で保持（自動採用しない）。**値一致は重複の十分条件でない**（左右/別日同値は canonical_name と単回納品で区別）。免疫便潜血 1日目/2日目 は `collection_ordinal`（文字が無ければ y_order から導出）で別実体。
4. **残留証拠監査（reject 専用）**: 認識済みセル・罫線・見出し・基準値領域を除いた measurement_table＋今回列内に未対応インクが残れば `INVENTORY_UNRESOLVED`（**充填せず**再読/監査）。印鑑・ロゴ・手書き誤検知を範囲限定で防ぐ。

### 3.6 正準化層（②）の処理モデルと実装方針

#### 3.6.1 処理モデル = テンプレート穴埋め方式（設計意図）

**要旨: 【元画像の検査結果を、正確に（①漏れなく ②捏造なく ③不要は落として）業界標準の項目名・単位で、Elith と決めた JSON として作る】。**

出力側を後追いで整形するのではなく、**出力の形（標準の項目名・単位）を先に固定**し、そこへ読取値を流し込む。処理は 5 ステップ：

```
[S1] 空テンプレート生成
     標準マスタ(§2.4 KMAT/特定健診サブセット)から
     {標準項目名, 標準単位, ref, value=null} の空スロット集合を用意
        ▼
[S2] 穴埋め（写像）
     ①読取＋sanitize 済みの measurement を、名寄せ/単位換算して
     該当スロットの value に**高信頼時のみ**代入（保守的マッピング）
        ▼
[S3] 移植カバレッジ照合（漏れの検知）
     「読取に値があった項目」が全てスロットへ移植できたか確認。
     どのスロットにも入らなかった読取値 = 未写像 → **surplus として記録**
     （silent drop しない＝漏れの可視化）。逆に必須スロットが空 = deficient
        ▼
[S4] 空スロット削除
     value が空のスロット（＝当該検体で未実施/未取得）は**納品から除外**
     （空欄を Elith へ送らない）
        ▼
[S5] Elith JSON 化
     lean measurement（name/value/value_num/unit/ref_low/ref_high/flag）＋
     エンベロープ（format_id/client_id/test_date…）で出力（§3.5 allowlist 準拠）
```

**確定事項との整合（重要）**:

| 手順 | 対応する既存実装/決定 | 捏造ゼロ・漏れゼロの担保 |
|---|---|---|
| S1 出力項目の事前固定 | `elith-necessity-check` の `requiredItemsMaster`（受け皿実装済・`elith-necessity-check.ts:42`） | マスタは一次資料受領後に確定（当社で項目を捏造しない・R3） |
| S2 穴埋め（写像） | `pickDeliveryName` をマスタ照合へ置換（`elith-export.ts:364`）。**保守的マッピング**（高信頼時のみ・§1.4） | 誤マップ＝捏造を作らない。写像不能は元のままフラグ |
| S3 移植カバレッジ照合 | `checkNecessity` の surplus/deficient 判定（`elith-necessity-check.ts:95/101`） | 未写像を**自動削除せず surplus 記録**（漏れ検知）。「不要削除」はテンプレに枠が無い＝出力に載らないことで実現するが、**何を落としたかは監査に残す** |
| S4 空スロット削除 | `sanitizeMeasurementsForDelivery` の空白（未実施）行除外（`elith-export.ts:320`） | 空欄は納品除外（既存挙動と一致） |
| S5 Elith JSON 化 | `MEASUREMENT_ALLOWLIST`/`ENVELOPE_ALLOWLIST`（`elith-necessity-check.ts:11/14`）、`docs/elith/elith_s3_data_handoff_spec.md` | 余剰フィールドを載せない |

**①読取層との直交（前提）**: S2 で穴埋めする値は「今回列の値」でなければならない。**3 期間リーク（§4.2）で過去値が今回に混入したまま S2 に入ると、マスタの正しい項目に誤値が穴埋めされる**（＝正しい枠に入った False-Value で発見が難しい）。したがって **VQA 第 2 パス（①・§3.4）で読取を正した後に②を通す**。②は名寄せ/単位/余剰を担い、**読取揺れの是正は担わない**（層を混ぜない）。

#### 3.6.2 段階導入

1. **①読取は変えない**（VQA も維持）。
2. **②を Elith 必要サブセットに絞って構築**（約 2000 項目を全部作らない）。
3. **starter マスタ**: 代表検体に実在する**実名の標準項目**（尿酸・中性脂肪・白血球数 等＝捏造でない）で同義語/単位/判定マップを小さく作り、🎯で効果（名寄せ Missing 減・余剰減・回帰ゼロ）を検証してから拡張。
4. `pickDeliveryName(section, detail)`（`elith-export.ts:364`）の当て推量を**マスタ照合へ置換**（section/detail のどちらが分析名かを推測せず、両方を標準マスタに照合しヒットした方を正準名に）。
5. **完全マスタ**は推進機構/HASTOS or クライアント/Elith 受領で差し替え（starter を権威データで置換）。
- 出典: `docs/scan/scan_canonicalization_standard_format_design.md` §3〜§7。

### 4.2 ゴールデン検体の版面構造 = 3 期間横並び（揺れの根因）

実画像で確定した決定的事実: **データ列が［基準値｜今回｜前回 2023/4/22｜前々回 2020/8/3｜単位］の 3 時点並列**である。揺れる項目は例外なく「**今回セルが空 or 淡い反復トークンなのに、隣接過去列に目立つ値がある**」行。以下は実画像を PII 除去して模式化したもの（値は `docs/scan/golden/scan_golden_healthcheckup_20250123.md` の転記）。

**(a) 眼圧 — 今回=空／過去列に 16（時系列リークの典型）**
```
検査項目 | 基準値 |  今回  | 前回 2023/4/22 | 前々回 2020/8/3 | 単位
眼圧 右  |   —    | (空)   |      —         |      16         | mmHg
眼圧 左  |   —    | (空)   |      —         |      16         | mmHg
             ↑今回は空が正       ↑ここの16を今回へ吸うと False-Value
```

**(b) 免疫便潜血 — 同一の淡い (-) が 3 列反復（列帰属の曖昧＋空誤認）**
```
検査項目           | 今回 | 前回 2023/4/22 | 前々回 2020/8/3
免疫便潜血反応 1日目 | (-) |      (-)       |      (-)
免疫便潜血反応 2日目 | (-) |      (-)       |      (-)
   ↑正解は今回=(-)。同一トークン反復でどれが今回か run毎に揺れる
```

**(c) 血球分画 — 今回=空／前々回のみ値（過去列リーク）**
```
検査項目 | 基準値      |  今回  | 前回 | 前々回 2020/8/3 | 単位
MCV      | 82.0〜98.0 | (空)   | (空) |     92.6        | fL
MCH      | 26.0〜34.0 | (空)   | (空) |     32.1        | pg
好中球    | 30.0〜75.0 | (空)   | (空) |     58.7        | %
   ↑今回は測定なし=空が正。過去列の値を今回へ読むと False-Value
```

> **訂正の記録（R5）**: 調査途中で「lite が分画を読めて high-recall＝良い」と述べたのは**誤り**。実画像では分画の**今回列は空**（値は前々回のみ）であり、lite の分画値は**過去列リーク（False-Value）**、3.5 が空にしたのが正だった。事実を示され撤回済み。

### 4.3 統一根因

> **多期間（今回/前回/前々回）横並び表で、今回セルが「空」または「淡い反復記号（(-)/0）」なのに隣接過去列に目立つ値がある行**でのみ、LLM の列境界解決が run 毎に揺れる（非決定）。

- 今回列が**明瞭に埋まる**行（身長 163.3・白血球 45.2・GOT 19…）は**安定**。numeric 本体が安定で、空/淡いセルだけ揺れる**非対称性**が説明される。
- ゆえに **モデル格上げ（3.5）でもプロンプト強化でも直らない**（列解決の揺れは能力でなくサンプリング）。構造的補修（VQA・行で辿る/今回セルのみ）が正しい。

### 4.4 却下・保留された手段（履歴）

| 手段 | 判定 | 理由 |
|---|---|---|
| 様式別プロンプト/テンプレ OCR | **却下** | 見た目に標準が無く様式は機関裁量で変わる → 保守地獄・汎化しない負債 |
| 主パス（プロンプト）への時系列/定性規則強化 = 対策 A | **不採用（実証済）** | False-Value=0 になるが Missing 9 の numeric 回帰（身長/体重等）|
| 列追加（O/X・構造保持）= 対策 B | **不採用** | O/X 却下と同じ numeric 回帰リスク |
| `SCAN_OUTPUT_FORMAT=json` | **不採用（コード温存）** | 補助欄暴走の False-Value |
| モデル階層 3.1-lite→3.5 格上げ | **不採用** | md 段階で lite を超えず（K-W・免疫便潜血を空に）＋503 リスク |
| 採用 = 対策 C（後段 VQA でドロップ/充填） | **採用** | 主パス不変・高信頼時のみ・誤削除を構造防止 |

出典: `docs/scan/scan_canonicalization_standard_format_design.md` §8、CLAUDE.md「却下再掲」。
