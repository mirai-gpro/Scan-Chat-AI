## 1. なぜ作るか

**いまは利用者が画面を開いたまま待つ。** `sendAll()` が 1 枚ずつ `await fetch('/api/scan')` し、
サーバは `await callGemini()` の結果を同じ応答で返す（キューもジョブも無い）。

- 1 枚あたり **30〜50 秒**かかった記録がある（`astro.config.mjs:9-11` のコメント。
  gemini-2.5-flash 当時の値で、現行既定 `gemini-3.1-flash-lite` での実測ではない）。
  6 枚なら **3〜5 分**。
- **ページ列はメモリだけ**なので、送信中にタブを閉じる / リロードすると**全ページ失われて最初から**。
  （`scan.astro` / `scan-pages.ts` に `localStorage` / `sessionStorage` / `indexedDB` は 0 件）

**ゴール = 送信を押したら画面を離れてよい。**
**ユーザーにとっては「送信完了＝完了」**（発注者判断 2026-09-10）。
戻ってきたら結果ができている、を**約束としては掲げない**（通知も進捗も作らない）。

## 2. 前提の訂正（設計に直結するので先に）

### 2.1 Vercel の関数上限は 60 秒ではない

出典: `vercel.com/docs/functions/limitations`（2026-08-24 版・fluid compute 有効時）

| | 既定 | 最大 |
|---|---|---|
| Hobby | 300s | **300s** |
| Pro / Enterprise | 300s | **800s**（1800s は Beta） |

**`astro.config.mjs` の `maxDuration: 60` は自分で絞っている値**であって上限ではない。
→ CLAUDE.md の「60s だから 1 画像 = 1 リクエスト」という**根拠は現在成り立たない**。
1 起動で複数枚を回せる。

**リクエスト本文 4.5MB の制限は別で、こちらは今も有効**（同ページ「Request body size」）。
だから**画像本体は関数を通さず S3 経由**、という既存の設計は変わらない。

### 2.2 Vercel Cron の最小間隔はプランで決まる → **本番は Pro (2026-09-10 確定)**

**Pro なので毎分 cron が置ける / 関数は最大 800s まで伸ばせる。** 以下は根拠。

出典: `vercel.com/docs/cron-jobs/usage-and-pricing`

| | 最小間隔 | 精度 |
|---|---|---|
| Hobby | **1 日 1 回** | ±59 分 |
| Pro / Enterprise | 1 分に 1 回 | 分単位 |

> Hobby accounts are limited to daily cron jobs. Cron expressions that would run more
> frequently will **fail during deployment**.

**→ 解決済み (2026-09-10・発注者回答)= Pro。** よって **Vercel Cron 毎分**を採る
（GitHub Actions への迂回は不要になった。§5）。

## 3. 画像の置き方と消し方（今回の判断の中心）

### 3.1 全ページを S3 へ置く

いまは**予算超え（≒3.2MB 超）のときだけ** S3 に置き、それ以外は data URL を関数に通している。
バックグラウンド化では**後から読む必要があるので、全ページを S3 に置く**。

- 置き場所は既存のまま `{prefix}scan-uploads/YYYY/MM/DD/<UUID>.<ext>`
  （`src/lib/scan-upload-ticket.ts`）。**新しい置き場を作らない。**
- **カメラ撮影も S3 へ**。いまカメラは `prepareScanUpload` を通らず data URL のままなので、
  Blob 化して同じ presigned PUT に載せる経路が要る。
- キーの安全性は既存の作りをそのまま使う: **サーバが採番** / `isScanUploadKey` の**完全一致**検査 /
  UUID / Content-Type と ContentLength を署名に固定 / 期限 15 分 / **`.json` を許可拡張子に入れない**
  （同じバケットの Elith 納品 JSON を読ませないため）。

### 3.2 消し方 = 既存のライフサイクルで足りる

**AWS 側の追加作業は要らない見込み。** 2026-09-04 に適用済みのライフサイクルが
そのまま「定期的に削除」になっている:

```
Expiration{Days:1}
NoncurrentVersionExpiration{NoncurrentDays:1}   ← バージョニング有効なので必須
AbortIncompleteMultipartUpload{DaysAfterInitiation:1}
```

- **保持は最長 1 日**。ジョブは通常数分で終わるので十分。
- **「読み終わったら消す」も入れる**（下記 §4.4）。ライフサイクルは**取りこぼしの保険**として残す。
  この二段にする理由: ジョブが落ちたまま放置された画像も 1 日で必ず消えるため。

> **→ 確定 (2026-09-10・発注者)= 1 日でよい。AWS 側の作業は無し**（既存ライフサイクルのまま）。
> ジョブが 1 日以上滞留すると画像が先に消えて復旧不能になるが、その場合は**そのジョブを
> 失敗として残す**（黙って消さない）。Pro の毎分 cron なら通常は数分で終わるので、
> 1 日滞留＝ワーカーが止まっている異常であり、**滞留の検知自体が監視項目**（§4.5）。

### 3.3 PII の扱い

検査票の画像は PII を含む。今回**「一定期間サーバに置く」ことを許容する**という判断だが、
以下は変えない:

- **診断系 DB / Elith / 外部には画像を載せない**（`diagnostic_user_id` だけで橋渡し）。
- ジョブ行に**氏名・生年月日等を持たない**。持つのは `diagnostic_user_id` と S3 キーだけ。
- **ログにキーを出さない**（キーが漏れても署名が無ければ読めないが、出さないに越したことはない）。
- 10 年保管の `putOriginal()` は**引き続きスキャン経路から呼ばない**（あちらは検査機関の原本用）。

## 4. 設計

### 4.1 流れ

```
ブラウザ  ①全ページを S3 へ PUT（presigned・本体は関数を通さない）
          ②POST /api/scan/jobs  { keys[], hint }        ← 数百バイト
          ③「送信しました」を出して**終わり**。ここでユーザーの用事は完了
ワーカー  ④未処理ジョブを拾い、1 枚ずつ Gemini へ（1 起動で回せるだけ回す）
          ⑤全枚数終わったら結果を束ねて DB へ、S3 の画像を削除
admin     ⑥失敗・滞留を監視して対応する（ユーザーには出さない）
```

**③で終わる**のが今回の確定事項 (発注者 2026-09-10「ユーザーにとっては送信完了＝完了でよい」)。
**進捗も完了通知も出さない。** 「読み取り中 (3/6)」も作らない。
問題が起きたときの対応は**ユーザーでなくこちら側** (同「それはこちら側のトラブル対応」)
→ **⑥の admin 監視が無いと誰も気づかない。§4.5 は"あれば良い"ではなく必須。**

### 4.2 ジョブの置き場 = `diagnosis.scan_jobs`（新規テーブル）

**`test_artifacts` に相乗りさせない** — あちらは「確定した検査 1 件」であって、
失敗・再試行・途中経過を持たせると意味が濁る。

**実物 = `supabase/migrations/20260910000010_scan_jobs.sql`（作成済・検証済・未適用）。**
以下は要点だけ。列ごとの意図はファイル内のコメントが正。

| 列 | 何のためか |
|---|---|
| `diagnostic_user_id uuid` | `test_artifacts` と**同じ型・同じ参照先** (`app_users`)。下書きの `text` は誤り |
| `image_keys text[]` | **順番が紙の順番**なので配列。`isScanUploadKey` を通る形のキーだけ |
| `page_count` / `done_count` | 時間切れで中断しても**続きから**再開するための位置 |
| `failed_pages` | 読めなかった枚数。`done` でも 0 でないことがある（成功分で先へ進む現行の思想） |
| `artifact_id` | 保存先の検査 1 件。**後追い確認はここから辿る**（下記 §8・案B）。`on delete set null` |
| `verified_at` | 人が確認した時刻。**null = 未確認**。確認は任意なので**null を理由に納品を止めない** |
| `attempts` / `locked_until` | 再試行の上限と二重起動よけ |

- **RLS は有効化し、ポリシーは 1 つも置かない**（service_role だけが読み書き）。
  さらに `force row level security` と `revoke all on ... from anon, authenticated` を明示する。
  **既存 diagnosis 系の `dev_read_all`（`using (true)`）を真似しない** — この表は
  **PII を含む検査票画像への参照（S3 キー）**を持つため。
- **適用は発注者**（「Claude 側では Production DB を変更しない」）。
  適用済みのマイグレーションは**編集せず前進マイグレーションを足す**。

#### 検証（スクラッチの PostgreSQL 16 で実測・2026-09-10）

`supabase db push` は使わない取り決めなので、**使い捨ての PG に全 16 本を順に当てて確かめた**。
「SQL が構文として通る」ではなく**意図した性質が実際に成り立つか**を見ている。

| 見たこと | 結果 |
|---|---|
| 全 16 本がクリーンな DB へ順に適用できる | OK（`fail=0`） |
| `anon` / `authenticated` から読めない | **両方とも `permission denied`**（既存 `test_artifacts` は読めてしまうのと対照的） |
| `service_role` で登録・取得できる | OK |
| `image_keys` の**順序**が保たれる | OK（1=aaaa / 2=bbbb） |
| `status` の check が効く | `'processing'` を弾く |
| `updated_at` トリガが発火する | 更新後に `updated_at > created_at` |
| 検査を消してもジョブが残る | `artifact_id` だけ null になり行は残る |
| **再適用しても壊れない（冪等）** | 2 回追加で当てて rc=0・error 0 行 |

- **`service_role` の BYPASSRLS に依存している**（`force row level security` はテーブル所有者も縛るため）。
  依存先は既存の `20260601000020_rls_policies.sql:24-25` が
  `create role service_role nologin bypassrls` で作っており、本番 Supabase も同じ。
  **ここが崩れるとワーカーは 0 行しか見えないのにエラーも出ない**ので、依存として明記しておく。
- **見つけて直した欠陥が 1 件**: `create trigger` には `if not exists` が無く、
  **このファイルで唯一 再適用がエラーになった**。既存 `20260621000010` と同じく
  `drop trigger if exists` を前に置いて解消（トリガは 1 つだけ・発火も確認）。

### 4.3 ワーカー

`GET /api/cron/scan-worker`（Bearer で保護）。**1 起動で「時間が許すだけ」回す**:

```
deadline = 起動時刻 + (maxDuration - 安全余白)
while (未処理の枚がある && now < deadline - 1枚ぶんの見積り) { 1 枚処理 }
```

- `maxDuration` はこの関数だけ**300s（Hobby でも通る値）**に上げる。
  Pro が確定すれば 800s も可。**`/api/scan` 側の 60s は触らない**（前景経路を巻き込まない）。
- **`locked_until` で二重起動を防ぐ**。cron が重なっても同じジョブを 2 度処理しない。
- 途中で時間切れになっても `done_count` まで進んでいるので、**次の起動が続きから**。
  → 1 起動で終わらなくても正しく終わる（デメカルの `last_to` 単調前進と同じ考え方）。

### 4.4 完了時

1. `mergeResults` で束ねる（既存関数をそのまま使う）
2. `sanitizeMeasurementsForDelivery` を通す（**納品整形は 1 箇所に集約**の規律どおり）
3. DB へ保存（既存 `/api/scan/save` と同じ書き込み口）
4. **できた `test_artifacts` の id を `scan_jobs.artifact_id` に書く**
   ← これが**後追い確認の入口**（§8・案B）。ここを書き忘れると確認画面へ辿れない
5. **S3 の画像を削除**（`DeleteObject`）。失敗してもライフサイクルが 1 日で消す

**保存は人の確認を待たない**（案B の前半）。`verified_at` は null のまま = 未確認だが、
**それを理由に納品を止めない**。止めると「送信完了＝完了」が成り立たなくなる。

### 4.5 失敗の扱い ← **発注者回答により第一級要件へ格上げ**

前景処理では `alert()` で「6 枚中 2 枚読めませんでした」と伝えていたが、
**バックグラウンドでは誰も見ていない**。しかも発注者判断で**ユーザーには一切出さない**
(「問題があれば、それはこちら側のトラブル対応」) ので、
**admin が見なければ本当に誰も気づかない**。ここは「あれば良い」ではなく**必須**。

- **枚単位で失敗を記録し、成功分だけで先へ進む**（今の挙動と同じ思想）。
- ジョブ単位の失敗は `status='failed'` + `error` に残し、**黙って消さない**。
- `attempts` を上限（3 回）まで自動再試行。超えたら `failed` で止める。
- **admin から一覧できる口**（wellfort-site 側 UI / Scan-Chat-AI 側 API の分担どおり）。
  出すのは **①失敗したジョブ ②滞留しているジョブ**（`queued`/`running` のまま一定時間超え
  = ワーカーが止まっている／画像がライフサイクルで消える前の警告）。
- **見張りは既存の型を流用する** — 通知基盤は作らず、**GitHub Actions の日次ワークフローで
  「失敗 or 滞留が 0 件か」を叩き、非 0 なら赤くする**。デメカル無人運用で採ったのと同じ形
  (CLAUDE.md「通知基盤を作らず GitHub Actions の日次ワークフローを見張りにする」)。
  **赤くなればメールが飛ぶ**ので、そこが実質の通知になる。
- **admin の口はユーザーの画面に出さない**（ユーザーは送信で完了、が確定事項）。

### 4.6 完了をどう伝えるか → **伝えない (2026-09-10 確定)**

発注者回答:「**ユーザーにとっては送信完了＝完了でよい**」。

- **通知も進捗表示も作らない。** 「読み取り中（3/6）」「できています」も**作らない**。
  ポーリング API も要らない (当初案から削除)。
- 送信後の画面は「**送信しました**」で終わり。ダッシュボードへ戻す。
- メール / Push はやらない（元より作らない方針）。
- **結果はいつも通り `/result/{id}` に出る**ので、見たい人は普通に見に行ける
  (=「開いたら見える」は結果として成立するが、**それを機能として作り込まない**)。

## 5. 実行方式 = **Vercel Cron 毎分**（プラン Pro 確定・2026-09-10）

- `vercel.json` に `crons` を足し、**毎分** `/api/cron/scan-worker` を叩く。
  現状の `vercel.json` は `{"regions":["iad1"]}` だけで **cron 定義は無い**（新規追加）。
- **送信から開始まで 〜1 分**。1 起動の持ち時間は **最大 800s**（この関数だけ引き上げる）。
- 1 枚 30〜50 秒の記録から見て、**6 枚なら 1 起動 (300s 前後) で収まる公算**。
  収まらなくても `done_count` から次の起動が続きを拾う（§4.3）。
- **GitHub Actions への迂回は不要になった**（Hobby だった場合の代替案は撤回）。
  ただし**失敗・滞留の見張り**としての GitHub Actions は別途使う（§4.5）。

> Hobby だった場合は cron が日次しか置けず GitHub Actions (最短 5 分) 経由になる、
> という代替案を検討していた。**Pro 確定で不要**。記録としてのみ残す。

## 7. 積み残し・注意

- **「少し時間がかかります」の文言**は P4 で消える（送信＝完了になるので待ち時間の説明が要らない）。

- **`/api/scan` の同期経路は残す**。ワーカーと同じ読み取りを使うので、
  デバッグ・admin バッチ・回帰チェックの入口として要る。
- **ライフサイクルの prefix を触らない**。`scan-uploads/` を外すと **Elith 納品 JSON が消える**。

|---|---|---|
| ① | 一覧の**「全てを送信」** (`review-send`) | ここから読み取りが始まる ← **今回バックグラウンド化する対象** |
| ② | 結果画面の**「✓ 確認して送信」** (`scan-submit`) | **ここで初めて DB と S3 (Elith 納品) へ書く** |

そして**②は人が確認するまで押せない**。`src/scripts/scan-verification.ts:859-868` が、
**疑念ありと判定されたセルを全部「修正」か「このまま OK」で解消するまでボタンを `disabled`**
にしている（未解消なら「N 件の疑念がまだ未解消です」／解消で「✓ 全行を確認しました。問診へ進めます。」）。

つまり **現状は「AI の読み取りを人が一度確認してから Elith へ行く」作り**で、
**「送信完了＝完了」にすると、この確認が構造的に無くなる**。

### 選択肢

| | 案 | 内容 | 帰結 |
|---|---|---|---|
| **A** | **確認をやめる** | ワーカーが読み取り→そのまま保存。②の画面は廃止 | 発注者の言葉に最も忠実・最小。**疑念セルを人が直す機会が消える** |
| **B** | **確認を任意にする（推奨）** | ワーカーが読み取り→**そのまま保存**（ここまで A と同じ）。②の画面は**後から見て直せる場所**として残し、直したら上書き | ユーザーは送信で完了（要件を満たす）。直したい人・こちらの運用側が**直せる道が残る** |
| C | 確認を admin へ移す | ユーザーには出さず admin が全件確認 | 件数が増えると回らない。admin バッチ側には既に照合器があるので二重になる |

### 確定した内容（案B）

**発注者判断 2026-09-10 =「B. 確認を任意にする（推奨）」。** 決まったのは次の 3 点。

1. **ワーカーは人の確認を待たずに保存する。** 疑念セルが残っていても保存し、Elith まで進む。
   → ユーザーは**送信で完了**（要件どおり・§4.1 ③）。
2. **結果画面（`scan-verification.ts`）は捨てない。「後から見て直せる場所」として残す。**
   入口は `scan_jobs.artifact_id`（§4.2・§4.4-4）。
3. **`disabled` の意味が変わる。** いまは
   `scan-verification.ts:859-868` が**疑念を全部解消するまで送信ボタンを押させない**
   ＝**先へ進むための関門**。案B ではもう関門ではないので、
   **未解消でも画面を開けて、直したぶんだけ上書きできる**ようにする。
   **「N 件の疑念がまだ未解消です」で行き止まりにしない。**

### なぜ B か（記録）

①発注者の要件（送信＝完了・通知不要）を満たす ②**既にある検証 UI を捨てない**
③「LLM⇒Json⇒Elith で問題があれば、それはこちら側のトラブル対応」と言われた**その対応の道具になる**
（疑念行を後から直せる） ④A から B への差分は「保存済みの結果を上書きする経路」だけ。

### 案B で新しく要るもの（実装時の申し送り）

- **上書き経路**: 既存の `/api/scan/save` は**新規保存**の口。後追いの修正は
  **同じ `test_artifacts` を更新する**ので、新しい行を作らないこと
  （作ると「検査が 2 件ある」ことになり、Elith 納品も二重になる）。
- **`verified_at` を書くのは人が確認したときだけ。** null=未確認は**正常な状態**であって
  異常ではない。**null を理由に納品・表示を止めない。**
- **上書き後の再納品をどうするかは未決**（S3 の納品 JSON は書き出し済みのことがある）。
  P4 に入る前に決める。**ここだけは案B でも残る宿題。**
- **admin からも辿れるようにする**（P5）。ユーザーが直さない前提で運用が回る必要がある。
