## 3. スペシャルアカウント枠（要件①）

### 3.1 デモ枠に相乗りしない

デモ用アカウントは **ダミーデータを見せるための枠**（`docs/operations/デモ用アカウント_仕様書.md`）。
同じ枠に入れると **実データの利用者にダミーの検査結果が出る**。**必ず別枠**にする。

### 3.2 設計

- `src/lib/special-accounts.ts` … `demo-accounts.ts` と同じ作り
  - 登録は **Google アカウント（メール）**、判定は **uid**
  - 保存するのは **sha256 / マスク / uid / メモ** の 4 つだけ。**メール現物を保存しない**
  - 供給元は `BUILTIN` ∪ env ∪ `app_config`、そこから除外リストを引く（デモ枠と同じ形）
- 橋渡しは `api/auth/resolve.ts` の **未連携 early return より前**に置く
  （後ろだと到達しない。デモ枠で実証済み）
- **`demoFallbackEnabled` とは完全に独立**。スペシャル枠でダミーは一切出さない
- 管理画面 `/admin/special-accounts`（wellfort-site）。処理は Scan-Chat-AI 側 API

### 3.3 検査（静かに壊れるため必須）

- スペシャル枠の uid で **ダミーが 1 件も出ないこと**
- 判定に admin 権限が混ざっていないこと（デモ枠で踏んだ誤り）
- 除外リストが「和のあと」に効くこと

## 4. 複数年アップロード（要件③）

### 4.1 いまの挙動（変えない部分）

- `POST /api/scan/save` は **1 回の呼び出しで 1 件の `test_artifacts`** を作る
  （`lib/scan-persist.ts:74-92`。`source: 'user_upload'`=`:78` / `test_type: 'health_checkup'`=`:80`）
- 検査日は **明示 → 検査票から抽出 → 今日** の順（同 `:64-68`。`extractExamDate` は Elith 書き出しと同じ関数）。
  出どころは `date_source` に残る（`provided` / 抽出 / `today`）
- 測定値は `persistMeasurements()` が jsonb と正規化テーブルの**両方**を書く（同 `:106`）
- 推移グラフは正規化テーブル由来で、**日付違いの点が 2 つ以上あれば自動的に線が出る**
  （`lib/measurement-queries.ts:215` `getTrendCandidates`）

→ **複数年は「回ごとに送る」だけで成立する。DB もグラフも改修不要。**

### 4.2 画面に足すもの＝「回（1 年分）」の概念

```
① ファイルを選ぶ（1 回分 = 複数ファイル可）
      ↓
② 一覧を見せて「この回（1 年分）はこれで完了ですか？」
      ↓ はい
③ 送信 → スキャン → 保存 → 「この回の検査日: YYYY-MM-DD（検査票から読み取り）」を表示
      ↓
④ 「他の年度分も続けてアップロードしますか？」
      ↓ はい（**最大 5 回**）→ ① へ
      ↓ いいえ → 完了
```

- **カメラも同じ**。撮り終えたら②の確認を挟み、④で次の年度へ進む（発注者指示）
- 実装は `src/scripts/scan-pages.ts` の `ScanPageList` を **回ごとにリセット**して繰り返す。
  ページの積み方・送信そのものは現行のまま
- `origin`（`camera` / `file`）は現行どおり保持し、「次の年度」も**入れたときと同じ手段**で続ける

### 4.3 必ず守ること

1. **回ごとに検査日を画面へ出す。** 読めなかった回（`date_source: 'today'`）は
   **警告し、次へ進ませない**。今日の日付で保存すると別の回として積まれる
   （臨時案件で実測した事故）
2. **最大 5 回でガード**する
3. **完了した回はその時点で保存済み**である旨を出す。送信中にタブを閉じるとその回は失われる
   （現状の既知事項。`docs/scan/スキャン非同期処理_仕様書.md`）
4. 回の一覧（何年分入ったか）を画面に残す

## 5. ウェルネス年齢（要件③の一部）

### 5.1 人間ドックなら算出できる

golden（元画像から人手で起こした正解データ）で実測した。

| 検体 | アルブミン | クレアチニン | 血糖 / HbA1c | リンパ球% | MCV | ALP | 白血球 | 判定 |
|---|---|---|---|---|---|---|---|---|
| 人間ドック 2024-09-24 | 3.9 | 0.68 | 空腹時 101 / 5.7 | 30.9 | 88.9 | 78 | 6700 | **正規版 v5.4** |
| 人間ドック 2025-02-17 | 4.4 | 0.96 | 随時 79 / 5.0 | 空（分画未実施） | 95.0 | 76 | 6900 | **簡易版 v7.0** |
| 定期健診（法定） | **欄なし** | **欄なし** | 空腹時あり | — | — | — | 空欄 | **算出不能** |

出典: `docs/scan/golden/scan_golden_humandock_20240924.md` / `…_20250217.md`。

### 5.2 「随時血糖」は血糖として拾わない（正しい挙動）

血糖のエイリアスは `空腹時血糖 / 血糖 / グルコース / glucose / glu / fpg`（`lib/health-age.ts:247`）。
**随時血糖は含まない。** PhenoAge は空腹時血糖前提のモデルなので、混ぜると別物になる。
その回は **HbA1c から eAG を推定**する簡易版に落ちる（`lib/health-age-simple.ts`）。
版と推定の別は `method` / `glucose_source` に残る（`lib/wellness-age.ts`）。

### 5.3 【重要】自動では算出されない

`diagnosis.health_age_scores` に**書き込むのは `api/admin/health-age.ts` だけ**（grep で確認）。
**ユーザーのスキャン保存では算出も保存もされない。**

→ 運用手順に **「年ごとに admin から算出を実行する」** を入れる。
スキャン保存時の自動算出は本案件の範囲外（別途）。

### 5.4 版が混在し得る

分画の有無で正規版↔簡易版が年ごとに変わる。**版を伏せて数値だけ並べない**（確定事項）。
複数年を並べて見せるかは §11 の確認事項。

## 6. Elith 納品（要件⑤）

### 6.1 問診は既存で完成

`api/interview/export.ts` が **納品仕様**（`elith_s3_data_handoff_spec` §7.3）で書き出す。
パス・ファイル名・PII 除去（`subject:{sex, age}` のみ）とも規則どおり。**変更不要。**

### 6.2 健診が穴

ユーザースキャンの `api/scan/export.ts` は **`scan-export-v0` の暫定形式**で、
`{prefix}{diagnosticId}/` に書く（`lib/scan-export.ts:19,272`）。**納品仕様ではない。**

→ **新規**: `diagnosis.test_artifacts` から `HealthCheckupData` を納品仕様で書き出す admin 口。
- 整形は `sanitizeMeasurementsForDelivery()` を通す（**唯一の正規化本体。二重管理しない**）
- **年ごとに** `user/{client_id}/date/{YYYY_MM_DD}/HealthCheckupData_…json`
- **納品ゲート**（臨時案件の実測で必要性が確定）
  - 読み取り 0 項目なら納品しない
  - `date_source` が `today` なら納品しない
- 起動は admin のみ（利用者の操作で納品が走らない）

### 6.3 納品先のプレフィックス

`AWS_S3_PREFIX` は既定 `scan-accuracy-test/`。**env で空にはできない**
（`lib/s3.ts` の `env()` が空文字を未設定とみなす。実測）。
納品先は**バケット直下 `user/`** なので、既存の複製の口を使う
（`api/admin/elith-delivery-promote.ts`。`.json` だけを移す）。確認・掃除は
`api/admin/elith-delivery-cleanup.ts`。

> **注意**: この 2 つは **まだ本番ブランチに入っていない**。臨時案件で作ったもので、
> `feat/transcos-delivery-cleanup` にある（2026-09-15 時点で未マージ）。
> 本案件で使うなら、**先にマージが必要**。

## 9. 失敗モードとゲート

| 失敗モード | 何が起きるか | ゲート |
|---|---|---|
| デモ枠に入れる | 実データの利用者にダミーが出る | 別枠 + 検査で固定（§3.3） |
| 検査日が読めない | 今日の日付で別の回として積まれる | 回ごとに検査日を表示・`today` は先へ進ませない |
| 複数年をまとめて送る | 1 検査に統合され年が潰れる | 回の概念（§4.2） |
| 納品先が検証用プレフィックス | Elith が見る場所に無い | 複製の口（§6.3） |
| ウェルネス年齢が出ない | 画面が空のまま | 年ごとに算出を実行（§5.3） |
| 報告書が空 | 未取込と誤解される | 理由を画面に出す（§7） |

## 10. 検証方針

- **スペシャル枠**: ダミーが出ないこと / 判定に admin が混ざらないこと / 除外が効くこと
- **複数年**: 5 回積んで artifact が 5 件・日付が 5 通り・推移グラフに 5 点出ること。
  `date_source: 'today'` の回が**止まる**こと
- **納品**: 0 項目・`today` の回が**納品されない**こと。年ごとに正しいパスへ出ること
- いずれも **退行注入で落ちること**まで確認する（本リポジトリの規律）
