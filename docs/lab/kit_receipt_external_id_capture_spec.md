## 1. 設計原則（厳守）

1. **Wellfort 内部の主キーは `lab_tests.id` を維持する。** 外部検査会社のIDを内部主キーへ置き換えない。
2. 外部IDは **`external_test_id` / `external_barcode` 等の相関キー**として保持する（上位 §4-5.1）。
3. **0 件・複数件・重複・不一致は自動確定しない。** `review_required` に落として人が見る。
4. 撮影画像は**証跡**として扱い、**公開URLに置かない**。
5. **ユーザーが所有する検査以外へ外部IDを登録できないこと**（サーバ側で再検証）。
6. **既存スキーマ・既存API・既存RLS を調査し、再利用できるものを優先する。**
   新規テーブル／列は**必要性を示してから**追加する。
7. **読取値はユーザーの確認操作を経てから確定する。** 自動で登録しない。
8. **仕様に無い外部IDを推測で作らない。** 桁数・prefix は実物で確定するまでコードに固定しない（§5.1）。

## 2. 取得対象（実物の仕様）

### 2.1 ① プリベント（P0）

| 項目 | 内容 |
|---|---|
| 先方名称 | **バーコードNo.** |
| 表示例 | `704000xxx` |
| 物理 | 検体に貼付される **1次元バーコード**と、その近傍に印字された「**ユーザーID**」 |
| 紐づけ先 | 対象の `lab_tests.id` |
| 下流 | **プリベント向け問診CSV を生成する前に、このIDが確定していること**（§7 ゲート） |

**【UI の確定事項】QR コードを撮影対象にしない。**
同梱書面には QR コードも印字されているが、**こちらが要るのは 1次元バーコードと「ユーザーID」の印字**である。
ガイドでユーザーに QR を撮影対象と誤認させると、**読めない画像が集まり続ける**（ユーザーは「撮れた」と思っている）。

#### 2.1.1 実物で確認できたこと（2026-10-13・現物 1 枚）

発注者から**実物の「シール台紙」1 枚**（写真）を受領。**写真はリポジトリに入れていない**
（ユーザーID と**パスワード**が写っているため）。

| 見えたこと | 内容 |
|---|---|
| 書面の名前 | **「シール台紙」**（同梱書面＝シールの台紙） |
| ID のラベル | **「ユーザーID」** |
| 桁 | **`704000` ＋ 3 桁の計 9 桁**。→ **`labid.prevent_pattern` の既定 `^704000[0-9]{3}$` は実物と一致**。変更不要 |
| **頭の `704`** | **Wellfort 法人を表す**（先方の説明・2026-10-21）。→ **当社のキットの番号は必ず `704` で始まる**＝**読み取りが成功したかの検査に使える**（§2.1.3） |
| バーコード | ユーザーIDの**すぐ下**。**印字は `A` ＋ 数字 ＋ `A`**（§2.1.2） |
| QR | **ある。** ログイン用で、`preventme.co.jp/pb/alapds/entry/` の URL とセット |
| **パスワード** | **同じ台紙に印字されている**（英字と数字が混ざった短い文字列） |
| シール | 台紙のブロックは**貼ってしまうと台紙から無くなる**（採尿容器・封筒に貼る） |

**帰結として決めたこと**
1. **撮影はシールを貼る前に。** ガイドと図に明記した（貼ったあとでは撮れない）。
2. **パスワードと URL を読ませない。** プロンプトで明示的に禁止した。
   証跡画像は S3 に残るので、ここが緩むと**資格情報が応答と台帳に流れる**。
   → **証跡画像の保存期間の判断（§12 の宿題）の重みが上がった。**
3. 検査名は **ALA-PDS**（URL の `/alapds/`）＝ 既存の `cancer_urine` の理解と整合。

#### 2.1.2 【実装の不具合】`A…A` でバーコードが毎回捨てられていた（2026-10-13・修正済み）

実物のバーコードの下には **`A` ＋ ユーザーID ＋ `A`** が印字されている。
Codabar (NW-7) は **A〜D を start/stop に使う**ので、デコーダがそれを含めて返す。

`normalizeExternalId` は `^[0-9]+$` でしか通さないため、**`A704000123A` は `null`**（実測）。
つまり **バーコード側が常に捨てられ、印字の OCR だけが残って毎回 `single_source`
＝ `review_required`** になる。**撮影はできるのに 1 件も `confirmed` にならない**状態だった。

→ **中身が全部数字のときだけ、start/stop を 1 文字ずつ剥がす**（`[A-Da-d]?` ＋ 数字 ＋ `[A-Da-d]?`）。

| | 挙動 | なぜ |
|---|---|---|
| `A704000123A` / `a…a` / `B…C` / 片側だけ | **剥がす** | Codabar の start/stop |
| `7O4000123`（**間に**英字） | **null のまま** | `O`→`0` の補正は別の番号に化ける（従来どおり） |
| `AA704000123A`（2 文字） | **null** | 想定外は確定させない |
| `*704000123*`（Code39） | **null** | **実物で見ていないので入れない。** 出たら `review_required` に落ちる＝黙って別の値になるより安全な側 |



#### 2.1.3 【2026-10-21・先方の説明】頭の `704` は Wellfort 法人を表す

> 発注者: **「ユーザーIDの頭の『704』は、プリベント社では、Wellfort の法人を表しているとのことなので、
> 読み取りが成功したかのチエックにも利用して」**

**当社の検査キットの番号は必ず `704` で始まる**ので、読み取り結果がそうなっていなければ
**別の数字を読んだ疑いが濃い**（台紙には URL・パスワード・管理用の記号も印字されている）。

**期待パターン（`labid.prevent_pattern` ＝ `^704000[0-9]{3}$`）とは別物として扱う。**

| | 期待パターン | **発行元の接頭辞** |
|---|---|---|
| 置き場所 | `labid.prevent_pattern` | **`labid.prevent_org_prefix`（既定 `704`）** |
| 根拠 | 仕様書の**表示例**。総桁数は**実物 1 枚でしか見ていない** | **先方から説明を受けた事実** |
| 形式が違う実物が出たら | **緩める**（admin が即日パターンを直す） | **緩めない** |
| 実装 | `matchesExpectedPattern()` | **`matchesOrgPrefix()`** |

**3 か所で使う。**

| # | 使うところ | 挙動 |
|---|---|---|
| 1 | **バーコードと印字が食い違ったとき**（`evaluateExternalId`） | **`704` で始まる側を採る**（＝どちらの読み取りが成功したか）。両方そう／両方そうでないときは**従来どおりバーコード**。**どちらを採っても `barcode_ocr_mismatch` は残す**（接頭辞が合ったことは「正しい番号だ」という保証ではない＝自動確定させない） |
| 2 | **採った値の検査**（同） | 外れたら **`org_prefix_mismatch` ＋ `review_required`**。**登録は止めない**（撮影そのものを失わせない）。画面は「この検査キットの番号ではないかもしれません」と出し、**図へ戻す** |
| 3 | **問診CSV の fail-closed ゲート**（`checkPreventQuestionnaireGate`） | **`confirmed` の行でもブロック**（`org_prefix_mismatch`）。admin の訂正で値が差し替わった回・接頭辞の設定が後から変わった回に効く |

**やらないこと**

- **足りない接頭辞をこちらで補わない**（`04000261` に `7` を足す等）。別の番号に化ける＝捏造。
- **ゲートで期待パターンを再判定しない**（従来どおり）。再判定するのは**ハードな不変条件**だけで、
  接頭辞は構造ガードと同じ性質。**総桁数を含む形式例はそうではない。**
- **デメカルに接頭辞を置かない。** この概念を先方から確認していないので、
  想像で置くと**全件が `review_required` になる**（既定は空＝判定しない）。
- **設定の打ち間違いで全件を止めない。** 空・数字でない接頭辞は「判定しない」へ倒す
  （値は数字だけなので、数字でない接頭辞は必ず不一致になる。そこで止めると 1 文字のミスで
  問診CSV が全部出せなくなる）。

**画面の文言はサーバが返した接頭辞を使う**（`read` 応答の `org_prefix`）。
画面に `704` を焼くと、app_config を変えたときに**「704 で始まります」と言いながら別の接頭辞で判定する**。
**接頭辞は秘密ではない** — 同じ値が本人の台紙に印字されているし、画面の図（ダミー `704000123`）にも出ている。

**検証**: ③' に 22 件・⑦ に 6 件・⑪ に 10 件追加。

#### 4.4.1 【方針転換 2026-10-13】カメラは**アプリ内**で開く（`<input capture>` を使わない）

**Android Chrome の実機で破綻した。** アプリ内の「カメラで撮影」を押すと
`<input type="file" capture="environment">` が**端末のカメラアプリ**を開くが、
**そのカメラがバーコードを自動検出し、「この番号を調べる」側へ遷移してしまう**。
`<input capture>` は **OS が写真ファイルを返したときだけ**処理が始まるので、
カメラを別の方法で抜けると**アプリ側では何も起きない**（エラーも出ない）＝
「読み取った数字がブラウザに出るだけで、アプリに戻らない」。

| | 直す前 | 直した後 |
|---|---|---|
| カメラ | `<input type="file" capture="environment">`（OS のカメラアプリ） | **アプリ内カメラ**（`initCameraScan` の `onShot`。`/scan` と同じ実装を流用） |
| OS のバーコード検出 | **割り込まれる** | カメラアプリを開かないので**割り込む余地が無い** |
| 「写真を選ぶ」 | `capture` なし | 変えない（**`capture` を付けない**＝ここからも OS のカメラを開かない）<br>**→ 2026-10-21 に撤去（§4.4.2）** |
| 権限拒否・カメラ無し | ブラウザが勝手にファイル選択へ落とす | **こちらで明示的に**「写真を選ぶ」へ誘導する<br>**→ 2026-10-21 以降は撮り直し／スマートフォンへ（手入力は置かない・§4.4.2）** |
| PC | ボタンを出さない（`touch-only`） | 変えない ＋ **JS でも `(pointer: coarse)` を見る**（CSS を外されても起動しない） |

**これは §4.4 の「`getUserMedia` を使わない」を上書きする。** 当時の理由は
「権限拒否時にブラウザが自動でファイル選択へ落ちる」だったが、
**バーコードを撮る機能で OS のバーコード検出に割り込まれる**方が重く、
注意書きでは直らない（文言も挙動も端末ごとに違う）。
`/scan` が本番で使っている方式なので、**実装は流用でき追加依存もゼロ**。

#### 4.4.2 【2026-10-21・発注者指示】入口は撮影だけ。「写真を選ぶ」も「手で入力」も置かない

> 発注者指示（1 回目）: **「『写真を選ぶ』ボタンは削除」**
> 発注者指示（2 回目）: **「番号を手で入力する　は、削除！　チェックデジットもないのに、
> 重要な検査IDを手入力させる対応はありえない」**

##### ① 「写真を選ぶ」の撤去

**主経路は撮影なのに、同格のボタンが 2 つ並んでいた。** 撤去して、入口を
**アプリ内カメラ 1 つ**にする。

##### ② 手入力の撤去（1 回目の直しで入れてしまったものを取り消す）

1 回目は「外しただけだと行き止まりになる」（§5.1）という理由で
**「番号を手で入力する」を置いた。これが誤り。**

**この番号にはチェックディジットが無い**（有無そのものが未確認・§2.3）。だから
**1 桁打ち間違えても「正しい形の別の番号」になる**。形式検証も `704` の接頭辞検査も通り、
`confirmed` ＋ `linked` になり、**画面も台帳も正常に見えたまま別の検査に紐づく**。
検知できるのは、その番号が**他の検査に既に登録されていた**偶然の回だけ（`conflict`）。

**撮影には無い失敗の仕方**である点が要点:

| | 誤りの出方 | 検知 |
|---|---|---|
| 撮影 | 読めない／別の数字を読む | **形式検証・接頭辞検査・バーコードと印字の突合**が拾う。拾えなくても**証跡画像が残る**ので admin が照合できる |
| 手入力 | **正しい形の別の番号**になる | **何も拾えない。証跡画像も無い** |

→ **手入力は経路ごと撤去する。**「番号を直す」ボタンも同じ理由で撤去（手で直せば同じこと）。

##### 「行き止まりにしない」の満たし方を変える

**誤りを混ぜる逃げ道を置くことでは満たさない。**

| 場面 | 1 回目（誤り） | 現行 |
|---|---|---|
| PC（カメラボタンが無い） | 手入力へ | **QR でスマートフォンへ送る**（§4.5 の導線が唯一の口） |
| カメラの権限を拒否 | 案内と同時に入力欄を開く | 「許可してからもう一度」と出して**撮り直しへ戻す** |
| S3 が落ちた・通信断 | 手入力へ落とす | 「通信をお確かめのうえ撮り直してください」 |
| 読み取れなかった | 入力欄を開く | **どこを撮るか**＋「明るい場所で、影や反射が入らないように撮り直す」 |

### 4.5 PC では QR でスマートフォンへ送る（発注者指示 2026-10-12・実装済み）

カメラは `touch-only` なので **PC には撮影ボタンそのものが無い**（要件 F-A5）。
そのままだと「用紙は手元にあるのに撮れない」で行き止まりになるので、
**`/scan` と同じ流儀**で同じ画面を開くための QR を出す（`scan.astro:140-168` と同じ形）。

| | 決めたこと | なぜ |
|---|---|---|
| 出す条件 | `.pointer-only`（= `(pointer: coarse)` で消える・カメラの `touch-only` と対） | スマホに QR を出すと**自分の画面を自分で読む**案内になる |
| 符号化する URL | **固定パス `/kit` の公開 URL**（`publicOrigin()`） | `publicUrl()`（現在の URL）だとクエリや代理表示のパスを**機械が読める形で**持ち出す。`/kit` に出荷ごとの URL は無いので deep link の余地もない |
| uid | **入れない。** スマホ側で改めてサインインしてもらう | `?u=` は 2026-09-29 に撤去済み（`scan.astro:23-28` と同じ扱い） |
| QR の SVG | ページに **`<symbol>` を 1 つ**置き、各ブロックは `<use>` で参照 | パスは実測 **3.2KB**。出荷は最大 10 件なので展開すると無駄に重い |
| URL のテキスト | **サーバ側で `value` に入れる。`location.href` で上書きしない** | 上書きすると QR と文字が食い違い、代理表示のパスがコピー欄に入る |
| コピー失敗時 | 選択状態にして手でコピーしてもらう | 行き止まりにしない（§5.1 と同じ） |

**2026-10-21 に「写真を選ぶ」と手入力を撤去した**ので、**PC から登録する手段は無い**。
この導線が**唯一の口**になった（用紙が手元にある人をスマートフォンへ送る）。
**ここを落とすと PC は行き止まりになる**ので、`canHandOff` の 3 点が揃わない回は
導線ごと出さない（＝読めない QR を出さない）という既存の扱いのまま。

**実測（2026-10-12・ローカルの実ブラウザ）**: PC 1280 = カメラボタン非表示 / QR 160×160 で描画
（暗い画素 25.5% ＝ `<use>` が実際にモジュールを描いている）/ スマホ 393 = カメラボタン表示・QR 非表示。

**検証**: `verify:external-id-capture` の ⑬ に 8 件追加（**退行注入 7 種**とも名指しで落ちる）。
ここは**静かに壊れる** — QR に文脈が混ざっても、スマホに QR が出ても、画面は「それなり」に見える。

## 5. ID 読取

### 5.1 プリベント

優先順位:

1. **1次元バーコードのデコード**
2. 印字された「ユーザーID」の **OCR**
3. ~~必要時のみ**手入力補正**~~ → **利用者の手入力は撤去（§4.4.2・2026-10-21）**。
   `manual` が残るのは **§12.1 の admin 訂正**の経路だけ

両方取得できた場合は**一致確認**する。

| 状況 | 挙動 |
|---|---|
| 一致 | 自動**候補**として確認画面へ（自動確定はしない） |
| **不一致** | **自動登録しない。** 再撮影またはレビュー |
| 片方だけ取得 | 信頼度・形式チェックの後、**ユーザー確認を必須**にする |
| **読めない／形が違う** | **撮り直す。手入力へ逃がさない**（チェックディジットが無いので打ち間違いが「正しい形の別の番号」になる・§4.4.2） |
| **QR だけ読めた／対象バーコードが読めない** | 「対象の番号を読み取れませんでした」として**再撮影**（QR の値は**使わない・保存しない**） |
| **`704` で始まらない** | **読み取りに失敗した疑い**。`org_prefix_mismatch` で `review_required`・画面は図へ戻す（**候補は消さない**・§2.1.3） |

**【2026-10-21】頭の `704` は Wellfort 法人を表す**（先方の説明）ので、
**読み取りが成功したかの検査に使う**（§2.1.3）。バーコードと印字が食い違ったら
**`704` で始まる側を採り**、採った値が外れていたら `org_prefix_mismatch` で `review_required`。
**登録は止めない**（撮影そのものを失わせない）。

**`704000xxx` は現時点の業務上の形式例。** 桁数／`704` の後ろはコードへ固定しない。
**期待パターン = app_config `labid.prevent_pattern`**（admin から即日変更可・外れても登録は通り `review_required`）、
**ハードな構造ガード = 共通 validator `passesStructuralGuard()`**（数字のみ 4〜20 桁）に分けてある（§2.3）。
実物の書面 1 枚で許容範囲を確定したら、app_config の値を直す（コード変更・再デプロイは不要）。

### 5.2 デメカル

## 6. 確認・登録

### 6.1 確認画面

表示するもの:

- 検査名
- 読み取った外部ID
- 「この番号で登録する」／「撮り直す」／（必要な場合のみ）「番号を修正する」

**登録前にユーザーへ番号を見せ、確認操作を必須にする。**

登録成功後:

- 「受取確認が完了しました」
- 登録した外部IDの**末尾等、必要最小限**の確認情報
- 検査進捗画面への戻り導線

**外部IDの全文を不必要な画面・ログ・分析イベントへ露出させない。**

### 6.2 撮影画像の保存（**既存基盤を流用する**）

**`scan-upload-ticket.ts` の形をそのまま流用する**（`src/lib/scan-upload-ticket.ts:14-31`）。理由:

- **キーはサーバが採番**し、クライアントは PUT 先を選べない。
- **完全一致の validator**（`isScanUploadKey` 相当）でしか読まない → 同じバケットの **Elith 納品 JSON を読み出せない**。
- Content-Type と ContentLength を**署名に固定** → 別形式・サイズ超過へのすり替えを **S3 自身が拒否**する。
- 期限 15 分。
- **Vercel Functions のリクエストボディ上限 4.5MB を関数に通さずに回避できる**（既に本番で実績がある経路）。

**`putOriginal()`（`originals-storage.ts:103`）は使わない。** あちらは **Object Lock ＋ 10 年保管の「検査原本」**用で、
**削除も上書きもできない**。撮影のやり直しが常態である受取時の画像を入れると、**消せないゴミが積み上がる**。
撮影画像は**検査原本ではなく読取の証跡**なので、別のプレフィックスに置く。

**`test_artifact_files` も使わない。** あれは `diagnosis.test_artifacts`（= 検査結果 1 回分）にぶら下がる表で
（`supabase/migrations/20260601000010_schemas_and_tables.sql:213-226`）、**受取時点では結果 artifact がまだ無い**。
`file_kind` の CHECK に値を足す migration も要るので、無理に寄せない。

**必須条件**

- **private のみ。公開URLを DB へ恒久保存しない。**
- 表示が必要なら**短時間の signed URL**。
- MIME・最大サイズ・画像寸法を制限し、**サーバ側で Content-Type だけでなく実体も検証**する
  （`genoplan-fetch.ts:263-266` が PDF マジックバイトを見ているのと同じ規律）。
- EXIF の位置情報があれば削除を検討する。
- **保存期間は §9 の確認事項**。既存の医療関連画像／検査証跡ポリシーに合わせる。
  既存ルールが無いので**こちらで勝手に決めない**。

### 6.3 登録API の必須条件

実際の API 形状は既存コードを読んで決めるが、以下は必須。

- **認証済みユーザーのみ**（`denyAnonymous`）。
- **代理表示中は書かせない**（`denyReadOnlyWrite`）／**共有閲覧からは叩かせない**（`denyForShare`）。
  → **`self-report.ts:26-40` の 3 段ガードをそのまま使う**。新しい認可を発明しない。
- **対象ユーザーは `viewer.writeTargetUid` が決める。** **body の uid を認可根拠にしない**
  （`self-report.ts:49-54` が「他人の uid を書けばその人の配送状態を変えられた」として明示的に禁じている）。
- 対象の検査が**当該ユーザーの所有**であることを**サーバ側で確認**する。
- **provider と test_type の整合**を検証する。
- 正規化済み外部IDの**形式検証**（§5.1 の validator）。
- **同一 provider 内の重複を検出**する（`unique (lab_company_id, external_test_id)` に依存できるのは案 A/B のとき。
  案 C では別途の一意制約が要る＝§3.2）。
- **既登録IDの上書きは通常ユーザー操作では不可。**
- **同時二重送信に対して idempotent。**
- 受取状態の更新と ID 紐づけの**整合性を壊さない**（受取は `orders` が正本・§3.1）。
- **service_role をブラウザへ露出しない。**
- 監査ログに**秘密値や画像を丸ごと書かない**。

### 6.4 バーコードデコードの方式（**既存依存で足りるかの検討**）

**現状、バーコードをデコードできるライブラリは入っていない**（§3.1 の最終行）。選択肢:

| 案 | 内容 | iOS Safari | 追加依存 | 評価 |
|---|---|---|---|---|
| **案 1** | ブラウザの **`BarcodeDetector`** API | **非対応**（WebKit に無い） | **0** | **単独では不可**。主要利用者はスマホで、iPhone が落ちると機能が成立しない |
| **案 2** | **`@zxing/library`** 等を同梱 | 対応 | **+1（数百KB）** | 動くが bundle が増える。`CLAUDE.md` の「追加依存なし方針」に逆行 |
| **案 3** | **撮影画像をサーバへ渡し、既存の Gemini 経路で読む** | 対応（撮るだけ） | **0** | **本線として推奨**。`scan.astro` → S3 → Gemini が**既に本番で動いている同じ形**で、端末差が出ない |

**`interview-cycle.ts` にゲートを足していないこと**も機械で見ている

#### 何が起きていたか（2026-10-21 実測）

画面は `mode:'register'` のとき、**サーバが読み取って返した候補を `manual` フィールドで送り返して**
いた（`external-id-capture.ts` の `register()`）。`evaluateExternalId` は `manual` が入っていれば
**無条件に `manual_entry` を積む**（`external-test-id.ts`）ので、

```
status = review_required / reasons = ["manual_entry"] / decode = manual
問診CSV ゲート: ブロック (capture_not_confirmed)
```

**＝ どんなにきれいに読めても `confirmed` にならない。** §7.1 のゲートは
`status='confirmed'` を要求するので、**この経路で登録した番号は 1 件も問診CSV へ出なかった。**

- **本番は無傷だった**: `labid.prevent_capture` が既定 off なので、まだ誰も通っていない。
- **`verify:external-id-capture` が緑だったのは正しい**: ③ は `evaluateExternalId` を
  barcode / ocr で直接呼んでおり、**画面が実際に送る payload（`manual` だけ）を
  1 度も通していなかった**。→ ⑰ で**画面が送る形**を通すようにした（下記）。

#### 検討した 3 案（**どれも「誰を信じるか」の判断を含む**ので発注者に出した）

| 案 | 中身 | 判断 |
|---|---|---|
| (a) `read` が `barcode` / `printed` を別々に返し、画面が register でそのまま送り返す | 変更が小さい | **却下**。画面が嘘をつける＝一致する 2 値を送れば誰でも `confirmed` を作れ、ゲートの前提が崩れる |
| (b) register で**証跡画像をもう一度読む** | 画面を信じない。値が必ず証跡に基づく | 不採用（Gemini 呼び出しが 1 回増える） |
| **(c) `read` の結果を `evidenceKey` でサーバ側に控え、register で引く** | 画面を信じない・追加の読み取りも無い | **採用（発注者判断 2026-10-22）** |

#### 実装（案 (c)）

| ファイル | 役割 |
|---|---|
| `src/lib/external-id-read-cache.ts` | **控えの読み書き 1 か所**。`rememberRead()` / `recallRead()` / `readCacheKey()` / `READ_CACHE_TTL_MS` |
| `api/kit/[id]/external-id.ts` `read` | 候補を返す**前に**控える。控えられなければ **503** で撮り直しへ |
| 同 `register` | **body の値を拒否**し、`recallRead()` で引いた控えだけから評価する |
| `src/scripts/external-id-capture.ts` | **番号を送らない**。読み取りの生値を持つ state も撤去 |

**控え先は証跡画像の隣の S3**（`<evidenceKey>.read.json`）。

- **migration を足さない** → 発注者の DB 適用を待たずに入る。
- **証跡と同じ prefix・同じ寿命**。保存期間は §9 の D-3 で未決なので、あとで決めた
  ライフサイクルが**画像と控えの両方に同時に効く**（別の場所に置くと片方だけ残る）。
- **プロセス内メモリに置いてはいけない** — Vercel の serverless は `read` と `register` が
  **別インスタンスに載り得る**ので、控えが黙って消え「撮れたのに登録できない」が
  再現しにくい形で出る。
- 控えのキーは**検証済みの証跡キーから導くだけ**。`.read.json` は `createEvidenceTicket` が
  発行しない拡張子で `isEvidenceKey` も通さない → **ブラウザは PUT も読み出しもできない**。
- **納品 JSON のキーでは控えも読み出しもできない**（`isEvidenceKey` を書き込み側にも掛ける）。

**控えるのは読み取りの生値（`barcode` / `printed`）だけ。判定は控えない。**
`register` が `evaluateExternalId` を**呼び直す**ので、判定の置き場所は 1 か所のまま
（控えに `status` を入れると `labid.*` を直したあとの回に**古い判定が貼り付く**）。

**結び付きを全部確かめる。** 控えには `uid` / `shipmentRef` / `provider` を書き、
`register` で**全部一致**を要求する（1 つでも違えば **409 `read_result_mismatch`**）。
証跡キーは推測不能な UUID だが、**漏れた 1 本で他人・別回・別検査の登録に使われない**ように
形だけでなく結び付きで止める（追加検査の `invalid_original_binding` と同じ規律）。

**引けない回は撮り直しへ（fail-closed）。** 控えが無い / 壊れている / 知らない版 /
期限切れ（**TTL 60 分**・未来日時と読めない日時も期限切れ扱い＝無期限の控えを作らない）は
すべて 409 で止め、「もう一度撮影してください」と出す。

**body が値を持ってきたら 400 `client_supplied_value` で落とす（黙って無視しない）。**
将来クライアントが送り始めたときに**その場で見える**ようにしておく。
この 400 は**控えを引くより前・保存より前**に置く。

**`confirmedValue` は突き合わせ専用。** 画面に出ていた値とサーバの採った値が食い違う回
（別タブ・前の撮影の確認画面）は **409 `confirmation_mismatch`**。
**値の出どころではない**ので、ここを評価の入力にしてはいけない。

**あわせて直した文言**: `read` が読めなかったときの案内から「番号を手で入力してください」を
外した（§4.4.2 で経路ごと撤去済みなのに、サーバの `detail` だけ残っていた）。

#### 検証

`verify:external-id-capture` の **⑰**（計 486 件のうち 50 件）。

- **控えの往復を実物で回す** — S3 はメモリへ差し替え、**鍵の検証は実物の `isEvidenceKey`**。
  往復 / 結び付き 3 種 / 期限 3 種 / 無い・壊れ・知らない版 / 納品 JSON のキー /
  S3 失敗で **throw せず** `ok:false`。
- **API が画面から値を採らないこと** — 評価の入力が `recalled.read.*` だけ・`manual:` が無い・
  400 の位置・`read` が**控えてから**候補を返すこと。
- **画面が値を送らないこと** — payload に `manual`/`barcode`/`printed` が無い。
- **④ 画面が送る形で `confirmed` になり、ゲートが通ること**（`allowed:true` / `reason:'ok'`）。
  同時に**旧実装の payload では `manual_entry` でブロックされること**も固定した
  — ここが抜けていたのが、435 件の検査がこの不具合を見逃した理由。

**退行注入 14 種**とも名指しで落ちることを確認済み（画面が `manual` で送り返す＝元の不具合 /
body の値を評価へ渡す / 400 を外す / 控えを引かない / 結び付きを見ない / 期限を見ない /
未来日時を通す / キー検証を外す / 判定も控える / 控える前に候補を返す / S3 失敗を throw にする /
控えが無くても通す / 400 を保存のあとへ動かす / `confirmedValue` を値の出どころにする）。
**うち 1 件（S3 失敗を throw）は注入して初めて検査の穴が見つかり、検査側を直した**
（throw だとスクリプトごと落ちて名指しの FAIL にならなかった）。

#### 残っていること

- **本番での通し確認は未実施**（この環境に S3 も Gemini キーも無い）。
  `labid.prevent_capture` を on にする前に、実機で 撮影 → 読取 → 登録 を 1 回通し、
  台帳が **`confirmed` ＋ `linked`** になることを確かめる。
- **TTL 60 分の妥当性は実機の操作時間を見てから**（短いと撮り直しが増え、長いと控えが残る）。

#### 案 A — 撮ったその場で番号を出す（ネットワーク 0 回）

実装 `src/scripts/external-id-barcode.ts` ＋ `external-id-capture.ts`。

- 撮影直後に**端末の中だけ**でデコードし、**番号と確認画面を先に出す**。

- **表示だけ。登録の値にしない** — §12.2（発注者判断 案 (c)）のとおり、
  登録に使うのは**サーバが `evidenceKey` で控えた読み取り結果だけ**。

  の 2 つにしか使わない。
- **番号が先に出るので、サーバの読み取りが終わる前に「登録」を押せる。**
  → `register` は**走っている読み取り（`c.pending`）を待つ**。
  待たずに送ると控えが無く「もう一度撮影してください」＝**読めているのに撮り直させる**。
- **サーバが先に答えた回は画面を触らない**（`turn.serverDone`）。
  遅れて届いた端末側の値でサーバの値を上書きしないため。
  食い違ったときは**黙って差し替えず**「サーバで読み直した番号に差し替えました。」を出す。
- **正規化を 2 か所に置かない** — 画面も `normalizeExternalId()` を import する
  （`A` で挟まれた Codabar の start/stop を剥がす規則は `external-test-id.ts` が唯一の本体）。
- wasm は **`?url` で資産化**され、**ハッシュ付き URL** で配られる
  （build 実測: `dist/client/_astro/zbar.*.wasm`）＝ 2 回目以降はキャッシュ。

#### 案 C — サーバも決定論を先に試す

実装 `src/lib/barcode-decode.ts`（sharp → グレースケール → `scanGrayBuffer`）。

- **既定は Gemini と並行**（`Promise.all`）。決定論ぶんの待ち時間は増えない。
  狙いは 3 つ:
  1. **バーコード側の値が LLM の読みより確かになる** — 突き合わせが
     「機械が読んだバーコード × OCR した印字」になる（LLM が読んだ 2 つより強い）。
  2. **Gemini が落ちた回でも読み取りが続く** — 従来は `422` で撮り直しだった。
  3. `labid.decode_skip_llm` を on にすれば **Gemini を呼ばない**（待ち時間が消える）。
- **`labid.decode_skip_llm` は 2026-10-22 に既定 on（§12.4.1）**、さらに同日
  **「`single_source` でも確定とする」裁定（§12.4.2）**が出たので、
  **正常系は `confirmed` になり問診CSV のゲートも通る**。
  （この節を書いた時点では既定 off で、「全件 `review_required` になるので
  裁定が要る」と書いていた。その裁定が §12.4.2。）
  判断の材料だった事実は変わらない: symbology のデコードは start/stop とバーのパターンが
  合わないと値を返さないので**幻覚しない**。ただし **Codabar にチェックディジットは
  必須でない**ので、`704` 接頭辞（§2.1.3）と桁パターンの 2 つが**残る検査すべて**になる。
- **QR は読まない・返さない**（§2.1）。zbar は QR も読むので
  **1 次元の allow-list で弾いてから `decode()` する**（文字にしてから捨てない）。

#### 12.4.2 【裁定 2026-10-22・発注者指示】最初に読めた状態で確定にする（`single_source` は確定を妨げない）

> 発注者指示: **「裁定待ち 2 件 ： 片方しか、、、、 の表示を止めて、最初に読めた状態で確定にして。

##### 変えたのは 2 か所だけ

| | 変更 |
|---|---|
| 判定 | `external-test-id.ts` に **`NON_BLOCKING_REASONS = ['single_source']`** を置き、`status` を **allow-list** で決める（`reasons.some(blocksAutoConfirm) ? 'review_required' : 'confirmed'`）。**理由コードは消さない**（台帳と監査に残る） |

##### 「桁数と冒頭の 3 桁」の確認状況（発注者の問いへの回答）

#### 置き場所（責務分界どおり）

| | 何 |
|---|---|
| 画面 | wellfort-site `src/pages/admin/external-id-captures.astro`（サイドバー「検査連携」） |
| 中継 | wellfort-site `src/pages/api/admin/external-id-captures/[action].ts`（allow-list = `list` / `detail` / `correct` / `discard`） |
| 処理 | Scan-Chat-AI `src/lib/external-id-admin.ts` ＋ `src/pages/api/admin/external-id-captures/{list,detail,correct,discard}.ts`（Bearer `ADMIN_API_KEY`） |
| 設定 | Scan-Chat-AI `src/lib/external-id-admin-config.ts`（`labid.*` の読み方を 3 つの API へ写さないための 1 か所） |
| 証跡の表示 | `external-id-evidence.ts` の **`createEvidenceViewUrl()`**（presigned GET・**5 分**） |

**migration は 1 本も足していない。** 受け皿（`previous_value` / `corrected_at` /
`corrected_by` / `correction_reason`）は `20261011000010` に在る。

#### 守った線（§12.1 の 4 点）

1. **`status` を直に `confirmed` へ書く口を作らない。** 確認も訂正も
   `persistExternalIdCapture()` を通す（`correction: { by, reason }` つき）。
   だから**重複判定・紐付け・旧行の `superseded` 化が二重にならない**。
2. **`lab_test_link_status` を手で `linked` にしない。** 紐付けの成否は関数の戻り値。
   **`conflict` は admin でも自動で奪わない**（実測: 確定を押しても
   `conflict` / `review_required` / ゲート不通過のまま返る）。
3. **ゲートに 1 行も触っていない。** むしろ**実関数 `checkPreventQuestionnaireGate` を
   一覧の各行に当てて**、「確定したのに先へ進めない」理由をそのまま画面へ出す。
   `confirmed` でも `deferred` / `conflict` / 接頭辞違いなら「確定したが止まっている」と表示する。
4. **理由は必須・操作者は digest。** 理由が空なら**問い合わせも書き込みも 0 件**で 400。
   操作者は中継が渡す**サーバ検証済み email** → **Scan 側の `adminIdentity()`**（鍵つき HMAC）。
   **素の email は DB にもログにも応答にも出さない**（§8.4）。

#### できること

| 操作 | 何が起きるか | どの例外系の出口か |
|---|---|---|
| **写真と一致したので確定する** | 値はそのまま `confirmed` で入れ直す（旧行は `superseded`・`previous_value` に同じ値が残る）。紐付けも**その場でやり直す** | `barcode_ocr_mismatch` / `pattern_mismatch` / `pattern_unknown` / `manual_entry` / **`deferred`**（材料が後から揃った回はこれで `linked` になる） |
| **この番号に訂正して確定する** | 新しい値で入れ直す（`previous_value` に旧値） | 誤読。**再撮影が第一選択**（§8.3）だが、利用者に頼めない回の最後の手段 |
| **この撮影を無効にする** | その行を **`superseded` にするだけ** | **`conflict`**。同じ番号が別の行に在る限りどちらも確定できないので、誤登録の方を外す |

- **一括の口は作らない**（1 リクエスト = 1 行）。**0 件／複数件を自動確定しない。**
- 見ていた行が既に `superseded` なら **409**（撮り直し・別の admin の訂正が入った回に、
  古い画面の判断で上書きしない）。
- **全文と証跡写真は「1 行を開いたとき」だけ**。一覧はマスク（末尾 4 桁）で、
  **S3 のキーも返さない**（在るかどうかだけ）。
- **写真が見られない回は確定させない**よう画面に明示する（署名に失敗した理由も出す）。

#### `discard` が `persistExternalIdCapture` を通らない理由（唯一の例外）

§12.1 が禁じているのは **`confirmed` にする口**と **`lab_test_link_status` を手で
`linked` にする口**で、理由は「重複判定と紐付けを二重に持たない」こと。`discard` は

- **書く列は 4 つだけ**（`status='superseded'` / `corrected_at` / `corrected_by` /
  `correction_reason`）。`confirmed` も link も 1 バイトも書かない
- **`lab_tests` を触らない**

ので、その二重化は起きない。`persistExternalIdCapture` が撮り直しのときに実行している
**同じ 1 行の更新**（`external-id-persist.ts:191-196`）と同じ。
**行は消さない** — 消すと `previous_value` の鎖が切れて前の番号が辿れなくなる。
検査（⑳-j / ⑳-k）が「update は 1 か所だけ・書く値は `superseded` だけ」を固定している。
