## 第 1 章 補助事業の概要と開発背景

### 1.1 事業の目的

本補助事業は、株式会社ウェルフォート (以下「当社」) が提供する個人向け健康管理サービスの抜本的なデジタル化・自動化を実現するシステム開発である。

具体的には、

- ① **健康診断・血液検査・がんリスク検査・遺伝子検査・AI 疾病発症予測の 5 種類の検査データ** を生成 AI による読取および API で統合管理する **Web アプリケーション**
- ② 各ユーザーの検査結果・生活習慣データを基に LLM (大規模言語モデル) と RAG (検索拡張生成) を用いて **約 2 万字のパーソナライズ健康アドバイスを自動生成する AI 推論システム**

の 2 つのシステムを開発した。

> **v2.0 からの変更**: 対象検査を 4 種 → **5 種** に更新した。v2.0 作成後、検査会社 LAiF 社の「AI 疾病発症予測」(ICD-10 準拠 18 疾患カテゴリの発症率予測) をサービスラインナップに追加したことに伴い、同検査票の読取・管理機能を実装した。

### 1.2 現状の課題

当社は本事業着手前、以下の課題により事業拡大が困難な状況にあった。

| No | 課題 | 着手前の影響 | 放置した場合のリスク |
|---|---|---|---|
| ① | 検査データのバラバラ管理 (紙・PDF・CSV 等の複数形式) | スタッフが手作業で転記、1 件 15〜30 分を要する | 会員増加に対してオペレーションがスケールしない |
| ② | 健康アドバイスの人手作成 | 専門家が 1 件数時間かけて作成、月間対応件数に限界 | サービス品質のばらつき / ボトルネックによる機会損失 |
| ③ | 検査データの分散・時系列管理不可 | ユーザーが自分の健康推移を把握できない | サービス付加価値低下 / 継続率の悪化 |
| ④ | 検査キット管理・督促対応が属人的 | 担当者の手動対応でコスト大 | 対応漏れによる顧客離脱・業務品質の不均一化 |

### 1.3 本事業による解決策と革新性

| 課題 | 本事業での解決 | 実装状況 |
|---|---|---|
| ① 手作業転記 | 検査票を撮影・アップロードするだけで生成 AI が構造化データへ自動変換。医療機関ごとに異なる帳票レイアウトにテンプレート非依存で対応 | **実装済** (F-1) |
| ② 人手作成 | 検査値・生活習慣データを AI 推論システムへ受け渡し、約 2 万字の健康アドバイスを自動生成 | **実装済** (F-2 / 第 4 章) |
| ③ 時系列管理不可 | 検査値を正規化して蓄積し、項目別の経年推移グラフを提供。検査原本も長期保管 | **実装済** (F-5 / F-12) |
| ④ 属人的なキット管理 | 受注・出荷指示・進捗を一元管理し、出荷指示を営業日判定つきで自動送信 | **実装済** (F-6) |

### 2.3 稼働環境 (実装)

| 層 | 採用 | 備考 |
|---|---|---|
| アプリ実行環境 | Vercel (サーバーレス関数・リージョン `iad1`) | 関数タイムアウト 60 秒 / 定期処理 (cron) による非同期処理を併設 (スキャン読取=毎分 / AI 解析事業者への納品=毎日 23:00 JST / 受領取込=毎日 09:00 JST) |
| データベース | Supabase (PostgreSQL) | 2 スキーマ分割。マイグレーション 28 本 |
| オブジェクトストレージ | AWS S3 | ① 検査原本用 (東京リージョン `ap-northeast-1`・保存時暗号化・10 年保管の書込ロック) ② AI 解析事業者連携用 (`wellfort-ai-input`) の 2 系統 |
| フロントエンド | Astro v5 + TypeScript + Tailwind CSS | サーバーサイドレンダリング |
| 生成 AI | Google Gemini (検査票読取 / 音声対話) | モデルは管理画面から無停止で切替可 |

> **v2.0 からの変更 (方式変更)**: v2.0 の構成図には「Edge Function (5 種)」「S3 バッチ連携 + HMAC 署名」と記載していた。実装では **Edge Function は現時点で 13 種** (当アプリ 1 種 + 連携先サイト 12 種) であり、AI 解析事業者への受け渡しは **HMAC 署名ではなく「規定パスへの書込 + 書込後の読戻し検証」** 方式を採用した。理由は、受け渡しが同一 AWS アカウント内の S3 を介した非公開のバッチ連携であり、署名検証よりも**書込内容が実際に意図どおり保存されたことを毎回検証する**方が、納品漏れ・内容欠損という実際に起こりうる障害に対して有効と判断したためである。

### 3.4 AI 疾病予防報告書の表示方式 (F-7 / F-12)

v2.0 では「a サマリー / b 要注意抜粋 / c 全編 (原本 PDF 埋込)」の 3 モードを計画したが、実装では **ダイジェスト + 全編の 2 層構成**に変更した。

| 変更点 | 理由 |
|---|---|
| 3 モード → 2 層 (ダイジェスト + 全編) | 「a サマリー」と「b 要注意抜粋」の内容が実データで大きく重複し、利用者が 2 つのモードを使い分ける理由が無かった |
| 「要注意」という語を使わない | がんの早期発見を主軸とするサービスで所見に「要注意」と赤字で出すと「がんの疑い」と読まれるため。表記は AI 解析事業者の原文の判定表現に従う |
| 原本 PDF 埋込 → 受領 PDF は原本として保管し、表示は受領 JSON から生成 | 受領 PDF は JSON の部分集合であり、箇条書き構造が失われていた (実測: JSON 19,870 字 / PDF 19,827 字) ため、JSON から生成する方が素材として上位と判断した |

**生成にあたっての制約 (重要)**: 本報告書は AI 解析事業者の出力を**可読化**するものであり、**当社が内容を創作・要約・言い換えすることはしない**。紙面に出る全文が受領 JSON の部分文字列であることを自動検証で機械的に担保している (第 9 章参照)。

### 4.3 AI レポート出力仕様 (受領実績)

|---|---|---|---|
| 1 | アブストラクト | `abstract` | 冒頭の総括として全文表示 |
| 2 | 総評 | `summary` | 全編 |
| 3 | 検査値フィードバック | `blood_analysis` | 検査値一覧 + 全編 |
| 4 | 食事アドバイス | `diet` | ダイジェスト + 全編 |
| 5 | 運動アドバイス | `exercise` | ダイジェスト + 全編 |
| 6 | 睡眠・ストレス管理 | `sleep` | ダイジェスト + 全編 |
| 7 | ライフスタイル総合 | `lifestyle` | ダイジェスト + 全編 |
| 8 | 医療受診の目安 | `medical_visit` | ダイジェスト + 全編 |
| 9 | 必要な栄養素・サプリ情報 | `nutrients` | ダイジェスト + 全編 |

### 5.2 ファイル管理構成 (実装)

v2.0 は S3 を `raw/` `analysis/` `logs/` の 3 層で構成する計画であった。実装では**用途別に 2 バケットへ分離**する構成を採用した。

| 用途 | 実装 | v2.0 記載との対応 |
|---|---|---|
| 検査原本の長期保管 | 専用バケット・**東京リージョン (`ap-northeast-1`)**・プレフィックス `raw/`・保存時暗号化 (SSE-S3)・**Object Lock による 10 年保管 (削除不可)** | `raw/` に相当。**実装済** |
| AI 解析事業者への受け渡し | バケット `wellfort-ai-input`・規定パス `user/{client_id}/date/{YYYY_MM_DD}/` | v2.0 に記載なし (必要に応じ追加) |
| スキャン一時画像 | 同バケットの `scan-uploads/` 配下・**ライフサイクルで 1 日後に自動削除** | v2.0 に記載なし (F-16 に伴い追加) |
| 時系列解析・集計データ | **未実装 (Phase 2)** | `analysis/` に相当 |
| 操作・監査ログ (10 年保存) | **一部実装**。共有 URL のアクセスログ (`shared_access_logs`)、納品実行記録 (`elith_delivery_runs`)、検査原本の 10 年保管は実装。**全操作を対象とする汎用監査ログは未実装 (Phase 2)** | `logs/` に相当 |

> **Phase 2 とした理由**: `analysis/` (学習用集計) は AI 解析事業者側の品質改善サイクルが確立してから設計する方が適切と判断した。汎用監査ログは、記録対象・保管形式・閲覧権限の設計が未了であり、中途半端な実装では監査証跡として機能しないため、総合テスト工程で設計のうえ実装する。

### 5.3 AI 学習・フィードバックポリシー

**基盤 LLM の重みパラメータの直接更新 (再学習) は行わない。** この方針は v2.0 から変更していない。

| 項目 | 方針 |
|---|---|
| 学習対象データ | AI アドバイスの構成・行動変化指標 (匿名化済)・検査 / 生活習慣データ。**個人情報および生成全文テキストは使用しない** |
| 改善方式 | プロンプト選択・重み付け調整、RAG ランキング最適化 |
| 影響範囲 | 生成ロジック・出力傾向の選択のみ。過去に生成済みのアドバイスが遡って変更されることはない |
| 将来対応予定 | ウェアラブルデバイス連携 (Phase 2) |

## 第 8 章 用語定義

| 用語 | 定義 |
|---|---|
| LLM | 大規模言語モデル。大量のテキストデータで学習し自然な文章を生成する AI モデル |
| RAG | 検索拡張生成。外部の知識ベース (ガイドライン等) を検索して LLM の生成精度を高める技術 |

| 健診標準フォーマット (KMAT) | 日本医学健康管理評価協議会が策定した健診項目の標準マスタ。項目名の表記ゆれを吸収するために使用 |

| 誤読抑制ゲート | 未実施項目への基準値の流し込み等を決定論的に検出・抑制する処理群 |
| 3 省 2 ガイドライン | 厚生労働省「医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン」 |
| AI 駆動開発 | AI コーディングエージェントを全面活用した開発手法 |

### 9.4 自動検証の実施状況

本システムは、**57 本の自動検証スクリプト**により継続的に品質を検証している。主なものは以下。

| 検証 | 内容 |
|---|---|
| 読取精度の回帰照合 | 検査票の様式別に**人手で起こした正解データ 5 本**と読取結果を決定論的に照合。項目値の一致率・誤った値の混入・欠落を計測 |
| 報告書の逐語検証 | 報告書の紙面に出る全文が**受領 JSON の部分文字列であること**を機械的に確認 (当社が内容を創作していないことの担保) |
| 紙面契約の検証 | 報告書のデザイン見本と実装を突き合わせ、どのカードが・どの見出しで・どの文を・どの順で出るかを固定 |
| 画面実測 | 実ブラウザで複数の画面幅を開き、行長・紙面幅・横スクロールの有無を実測 |
| 個人情報の非露出検証 | URL・保存キー・ログに個人情報が出ないことを確認 |
| 型検査 | TypeScript の静的検査 (`astro check`) |

これらはプルリクエストごとに自動実行される (GitHub Actions)。

### A.2 当社での可読化 (F-12)

受領した上記のような文章は、1 章がまるごと 1 段落 (改行なし・600 字超) で届く。当社は**内容を一切変更せず**、以下の処理のみを行って表示する。

| 処理 | 内容 | 文字の増減 |
|---|---|---|
| 要点の選択 | どの文をダイジェストのカードに出すかを選ぶ (選ばれなかった文は全編に保持) | なし |
| 段落割り | 2 文ごとに空行を入れて段落に分ける | なし |
| 主題の強調 | 文頭の主題提示部 (「〜について」「〜は」等) を文法的に拾って太字にする | なし (`**` を挿すのみ) |
