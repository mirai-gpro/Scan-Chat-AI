## 第 1 章 補助事業の概要と開発背景

### 1.1 事業の目的

本補助事業は、株式会社ウェルフォート（以下「発注者」）が提供する個人向け健康管理サービスの抜本的なデジタル化・自動化を実現するシステム開発である。

当社の受注範囲は、**健康診断・血液検査・がんリスク検査・遺伝子検査・AI 疾病予測報告書の 5 種類の検査データ**を生成 AI による読取および連携により統合管理する **Web アプリケーション**の開発である。

> **v2.0 からの変更**: 対象検査を 4 種 → **5 種** に更新した。v2.0 作成後、検査会社 LAiF 社の「AI 疾病発症予測」をサービスラインナップに追加したことに伴い、同報告書の読取・管理機能を実装した（F-13）。

### 1.2 v2.0 時点の課題と本事業での解決

| No | v2.0 で挙げた課題 | 本事業での解決 | 実装状況 |
|---|---|---|---|
| ① | 検査データのバラバラ管理（紙・PDF・CSV 等） | 検査票を撮影・アップロードするだけで生成 AI が構造化データへ自動変換。医療機関ごとに異なる帳票レイアウトにテンプレート非依存で対応 | **実装済**（F-1） |
| ② | 健康アドバイスの人手作成 | 検査値・生活習慣データを外部 AI 解析システムへ受け渡す機能、および受領結果を可読化して表示する機能を実装 | **実装済**（F-2 / F-12） |
| ③ | 検査データの分散・時系列管理不可 | 検査値を正規化して蓄積し、項目別の経年推移グラフを提供。検査原本も長期保管 | **実装済**（F-5 / F-11） |
| ④ | 検査キット管理・督促対応が属人的 | 受注・出荷指示・進捗を一元管理し、出荷指示を営業日判定つきで自動送信 | **実装済**（F-6） |

### 2.3 稼働環境

| 層 | 採用技術 | 備考 |
|---|---|---|
| アプリ実行環境 | Vercel（サーバーレス関数） | 関数タイムアウト 60 秒。定期処理（cron）による非同期処理を併設（スキャン読取＝毎分／外部連携データの書き出し＝毎日 23:00 JST／受領データ取込＝毎日 09:00 JST） |
| データベース | Supabase（PostgreSQL） | 2 スキーマ分割。マイグレーション 27 本 |
| オブジェクトストレージ | AWS S3 | ① 検査原本用（**保存時暗号化・10 年保管の書込ロック**）② 外部連携用 ③ スキャン一時領域（1 日で自動削除） |
| フロントエンド | Astro v5 + TypeScript + Tailwind CSS | サーバーサイドレンダリング |
| 生成 AI（検査票読取・音声対話） | Google Gemini | モデルは管理画面から無停止で切替可 |

> **開発中の仕様改善**: v2.0 は「AWS アカウント設計、VPC・サブネット・ルーティング・セキュリティグループ設計、IAM 権限設計、RDS/Aurora DB 設計、S3 ストレージ階層設計、本番/ステージング環境分離、バックアップ運用設計」を前提としていた。実装では **アプリ実行環境 ＋ データベース ＋ オブジェクトストレージの 3 層構成**を採用した。ネットワーク分離・権限設計・環境分離（本番／プレビュー）・バックアップ運用・ストレージ階層（原本保管／連携用／一時領域）という設計要求はすべて充足しており、**金額の変更はない**。検査原本に 10 年保管の書込ロックを設定するため、保管用と連携用のストレージを物理的に分離する必要があった。

| 構成 | **ダイジェスト（要点カード）＋ 全編（折りたたみ）の 2 層** |
| 表紙 | 氏名・作成日・ウェルネス年齢（実年齢との比較数直線） |
| 冒頭 | 受領 JSON のアブストラクトを**全文そのまま**表示 |
| ダイジェスト | 章ごとに要点カードを表示。カード下端から全編の該当章へ遷移（遷移先の章は自動で開く） |
| 全編 | 受領した全文を章ごとに折りたたんで保持。既定は閉じた状態 |
| 検査値 | **項目名と値の 2 列のみ**。当社は判定・基準値の欄を作らない（受領データに判定フィールドが無いため） |
| 印刷 | 印刷専用ビュー。全章展開・操作ボタン非表示・ページ番号つき |
| 保存 | 端末（Windows / Mac / iPhone / Android）を判別し、それぞれの PDF 保存手順を表示 |

#### 3.4.2 可読化処理の内容（当社が行う処理の全て）

**当社は受領文の内容を創作・要約・言い換えしない。** 行う処理は以下の 3 つのみであり、**文字の増減を伴わない**。

| 処理 | 内容 | 文字の増減 |
|---|---|---|
| 要点の選択 | どの文をダイジェストのカードに出すかを選ぶ（選ばれなかった文は全編に保持） | なし |
| 段落割り | 2 文ごとに空行を入れて段落に分ける | なし |
| 主題の強調 | 文頭の主題提示部を文法的に拾って太字にする | なし（強調記号を挿すのみ） |

**この制約は自動検証で機械的に担保している。** 報告書の紙面に出る全文が受領 JSON の部分文字列であることを検証するスクリプトを CI に組み込んでおり、当社が文言を追加・改変するとビルドが失敗する。

実測: 受領本文 20,046 字 → ダイジェスト 1,478 字（削減率 92.6%）、全編は全文保持。

> **開発中の仕様改善**: v2.0 の「3 モード表示（a サマリー／b 要注意抜粋／c 全編〈原本 PDF 埋込〉）」は、**ダイジェスト＋全編の 2 層**に改善した。a と b の内容が実データで大きく重複し、利用者が使い分ける理由がなかったためである。また、受領した組版済み PDF は受領 JSON の部分集合で箇条書き構造が失われていたため、**受領 JSON から生成する**方式に改めた（組版済み PDF は原本として保管）。

## 付録 B 開発過程における仕様改善の一覧

本付録は、**v2.0（2026 年 5 月時点の計画）に対し、開発期間中の実機検証を踏まえて改善した点**を一覧にしたものである。**いずれも v2.0 の目的を損なうものではなく、金額の変更も生じていない。**

### B.1 実現手段を改善した項目

| # | 項目 | v2.0 の計画 | 改善後（実装） | 改善の理由 |
|---|---|---|---|---|
| 1 | 検査票読取モデル | Gemini 2.5 Flash | **Gemini 3.1 Flash Lite**（管理画面から切替可・2.5 Flash も選択肢に残す） | 混雑時の安定性で優位と実測。切替可能としたことで将来のモデル更新にも追随できる |
| 2 | アップロード上限 | 4 MB | **10 MB** | ブラウザからストレージへの直接アップロード経路を実装。4 MB では実際の検査票（多ページ PDF）が通らない事例があった |
| 3 | AI 問診 | 5 セクション 17 質問 | **9 セクション 36 設問**（条件分岐 11 問） | 検査会社の上りフォームに必要な項目を網羅するため拡充。条件分岐により利用者の回答負担は増やしていない |
| 4 | 音声認識 | 音声 API ＋ 別の音声認識エンジンの併用 | **音声 API のみ** | 単一経路に統一した方が発話の途切れ・二重発話が起きないことを実機検証で確認 |
| 5 | 外部連携の検証方式 | 署名方式 ＋ キュー方式の併用 | **規定パスへの書き出し ＋ 書込後の読戻し検証** | 同一アカウント内の非公開バッチ連携のため、署名検証より**送信内容が意図どおり保存されたことを毎回検証する**方が、納品漏れ・内容欠損という実際に起こりうる障害に有効と判断 |
| 6 | 連携結果の受信方式 | webhook による自動受信 | **管理画面からの取込 ＋ 世代管理** | 受領物が組版済みファイルを含むため、内容を確認してから反映できる運用の方が適切と判断 |
| 7 | 顧客 ID 管理 | 外部 CRM との API 連携 | **自社データベースで実現** | 外部 CRM へ個人情報を出さない構成のほうが個人情報保護上有利 |
| 8 | クラウド基盤 | 単一クラウドでの構成 | **アプリ実行環境 ＋ データベース ＋ オブジェクトストレージの 3 層構成** | 検査原本に 10 年保管の書込ロックを設定するため、保管用と連携用のストレージを物理的に分離する必要があった |
| 9 | 報告書の表示 | 3 モード（サマリー／抜粋／全編） | **ダイジェスト ＋ 全編の 2 層** | サマリーと抜粋の内容が実データで大きく重複し、利用者が使い分ける理由がなかった |
| 10 | 報告書の素材 | 受領した組版済みファイルを埋め込み | **受領データから生成**（組版済みファイルは原本として保管） | 組版済みファイルは受領データの部分集合で、箇条書き構造が失われていた |
| 11 | 報告書内のページ参照 | 各項目から原本の該当ページへ直接遷移 | **該当章への遷移**（原本のページ参照は行わない） | 受領データにページ位置の情報が含まれないため、遷移先を特定できない |
| 12 | 問診結果の保存 | 設問 × 回答をデータベースに保持 | **完了日時と設問数のみ** | 回答に医療情報が含まれるため、保管場所を外部連携データ 1 か所に限定した |
| 13 | 検査原本のファイル種別 | 個人情報除去済み原本 | **未除去の原本** | 個人情報の分離は外部連携データ側で担保しているため、原本は忠実に保管する方針とした |
| 14 | ストレージ構成 | 3 層（原本 / 解析 / ログ） | **用途別に分離**（原本保管 / 連携用 / 一時領域） | 上記 8 と同じ理由 |
| 15 | ダッシュボード | 4 種の UI 手法すべてをダッシュボードに配置 | **3 種を配置、対話型コーチは専用画面に独立** | ダッシュボード上にプレビューを置くと本題が下へ押し出されるため |
| 16 | 進捗の通知 | 段階別の自動通知 | **お知らせ配信 ＋ 進捗セクションによる未実施項目の提示** | 利用者が「次に何をすればよいか」を把握できる状態を、まず画面上で確実に実現した。メールによる自動配信は 9.3 のとおり次期フェーズ |
| 17 | 処理完了予定の提示 | 処理完了予定時刻を画面に表示 | **送信完了時点で確定表示**（非同期処理に改善したため） | 処理完了を待たせない方式に改めたため、予定時刻の提示が不要になった |
| 18 | 利用者単位のデータ容量上限 | 1 利用者 100 MB 上限 | **上限を設けず、保管設計で対応** | 検査原本は 10 年保管（削除不可）、スキャン一時画像は 1 日で自動削除とする設計に改め、利用者単位の上限管理は不要とした |
| 19 | 血液検査の CSV | 利用者がアップロード | **検査会社から取得し管理画面で取込**（3.3.1 の入力情報 2） | 検査会社から直接取得できるため、利用者に操作させる必要がなくなった |
| 20 | F-2 の機能名称 | 連携先事業者名を含む名称 | **「外部 AI 解析システムとのデータ連携」** | 本書は当社受注範囲のみを対象とするため名称を改めた。**機能 ID（F-2）は v2.0 と同一である** |
