# 臨時診断バッチ — 不採用・リバート精査待ち

> **重要: このフォルダ内の仕様書は不採用（ボツ）です。現行仕様・本番仕様の根拠として使用しないでください。**
>
> `ad_hoc_diagnosis_batch_spec.md` は経緯確認・差分監査のためだけに保存しています。内容を修正して再利用するのではなく、必要な臨時診断機能は**本番パイプラインの実コード・本番の正本仕様・実データから再設計**してください。

## 1. この文書群をボツにした理由

2026-09-10〜09-13 の臨時診断バッチ対応では、臨時バッチ側の仕様を先に固定し、その仕様を前提に実装・テスト・修正を重ねた結果、**本番の検査パイプラインと整合しない前提、実データで確認されていない前提、臨時バッチ独自の状態判定**が混入しました。

レビュー中に、仕様書に書かれた内容を本番仕様と誤認する事例も繰り返し発生しました。代表例として、Genoplan の過去の実測ページ数を処理仕様上の固定条件のように扱う誤認、実際の問診 XLSX の列構成を十分に確認しないまま写像・完了判定を作った問題などがあります。

このため、`docs/lab/ad_hoc_diagnosis_batch_spec.md` を「部分修正して正本に戻す」方針は採りません。**仕様書そのものを不採用**とし、このフォルダへ退避します。

## 2. 新担当者が基準にするもの

臨時診断バッチ仕様から本番を推測してはいけません。確認順序は必ず次の通りにしてください。

1. **本番で実際に動くコード**
2. **本番の正本仕様書**
3. **Production の実データ、実ファイル、実 API レスポンス**
4. その事実を基に、臨時診断に必要な差分だけを設計
5. このフォルダの旧仕様は、過去に何を作ってしまったかを調べる場合だけ参照

本番 E2E の入口は `docs/lab/lab_data_pipeline_master_spec.md`。検査会社からの受取方式は `docs/lab/lab_data_reception_overview.md`。各検査の実装については、これらから参照される本番コードを実際に追ってください。

**このフォルダの文書を理由に、本番コード、本番データ、本番仕様の挙動を変更しないこと。**

## 3. 関連実装・コミットはリバート精査対象

臨時診断バッチ仕様を前提として作成されたコード、API、DB migration、CI、管理 UI 連携等は、**新担当者が本番処理と突き合わせて精査し、不要なものをリバート／撤去する必要があります。**

ただし、これは「臨時診断関連コミットをまとめて機械的に revert する」という意味ではありません。

現ブランチ `claude/clever-cray-ngg0h6` は、この記録作成直前に **B2.2 の merge commit `7d3cacdc61fc32ddd7dd05af8950724e67e732ce`** まで戻してあります。B3/B3.1/B3.2 で行った後続の試行は、このブランチの現在の HEAD には含めていません。

履歴上の調査起点として、少なくとも次の PR／系列があります。

- PR #213: `feature/ad-hoc-diagnosis-batch`
- PR #220: 臨時診断バッチ Phase A（S3 write guard）
- PR #222: Phase B2.1（大容量 ZIP の分割処理）
- PR #223: Phase B2.2（S3 Range Reader throughput）

**上記は「この PR をそのまま revert せよ」というリストではありません。** 各 PR・各 commit の changed files を確認し、本番機能との共有部分、後続変更、DB 適用状況を確認した上で、実際の撤去単位を決めてください。

## 4. リバート時の最重要注意 — 巻き添え事故を起こさない

ここ最近、リバートや巻き戻しで**関係のない本番変更まで巻き添えにする事故が複数回発生**しています。本件では特に慎重に扱ってください。

### 禁止

- merge commit / PR を中身を見ずに一括 revert する
- commit message に `ad-hoc` とあるだけで、その commit 全体を削除する
- `src/lib/ad-hoc-diagnosis/` を消せば完了と考える
- migration ファイルを削除するだけで DB が元に戻ったと考える
- 本番で既に利用している共通処理まで「臨時診断で呼んでいた」という理由で戻す
- Scan-Chat-AI だけを見て、wellfort-site 側の対応関係を確認せずに戻す
- shared / merged branch を安易に force reset する

### 必須の確認手順

1. **リバート前の基準点を確定する。** 臨時診断着手前の commit と現在 HEAD を比較する。
2. **changed files をファイル単位で分類する。**
   - 臨時診断専用
   - 本番機能との共有
   - 臨時診断を契機に直したが本番にも必要
   - 無関係な同時変更
3. **本番コードの参照関係を検索する。** 削除候補が他の本番 API / cron / scan / Elith 処理から参照されていないことを確認する。
4. **DB migration の適用状況を Production で実測する。** 適用済み migration はファイル削除で戻さない。必要なら現在の DB 状態を確認した上で、明示的な後続 migration を設計する。
5. **Production データの有無を確認する。** 臨時診断テーブルや S3 一時領域に実データがある場合、コード削除より先に保持・削除方針を決める。
6. **wellfort-site 側の UI/API 呼出も対で確認する。** Scan-Chat-AI だけ戻して UI を壊さない。
7. **小さい単位で戻し、各段階で build/test と本番既存機能の回帰を確認する。** 一括リバート後に原因を探す方法を採らない。
8. **本番の既存専門処理を保護する。** 健診スキャン、Genoplan の本番受取／解析、Elith assembly/wrapping、S3 共通処理、HealthAge 等は、臨時診断側が再利用していたという理由だけで変更・削除しない。

## 6. 事実と仮定を混ぜない

再設計・リバート判断では、実測値を仕様へ昇格させないでください。

- ある PDF が 208 ページだった → 「その PDF が 208 ページだった」という事実
- 別の PDF が 210 ページだった → 「別個体は 210 ページだった」という事実
- そこから「Genoplan は 208〜210 ページが正常」という仕様を作る → **禁止。正本または実装上の契約が確認できない限り仮定**

同様に、日付、問診列、人物同定、重複判定、必須項目、ready 条件についても、臨時バッチ仕様を根拠に補完しないでください。
