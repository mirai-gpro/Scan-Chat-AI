# がんリスク検査 (ALA-PDS) を後から追加してダッシュボードに出す手順

**版**: 1.0 (2026-09-30)
**対象**: 検査は実施済みなのに **Welltect のダッシュボードに出ていない** がんリスク検査の回を、
原本 PDF から後追いで登録する運用。
**実施者**: Wellfort 管理者（`/admin` にサインインできる人）
**必要なもの**: 該当回の**原本 PDF** と、対象者の **diagnostic_user_id**

---

## 0. 結論（先に読む）

**コードの変更は要りません。既存の admin 画面 2 つだけで完結します。**

```
①  /admin/elith-batch    … PDF をスキャン → 検査(artifact) を作り、数値を保存する
                             → ダッシュボードに「回」が出る／数値とグラフが出る
②  /admin/lab-results    … 同じ PDF を原本として付ける
                             → 「データ」の画面に原本 PDF が表示される
③  確認
```

**順番が重要。②→① の順ではできません。** `/admin/lab-results` は
**既存の検査に原本を足す口**で、**検査そのものは作らない**ためです
（`src/pages/api/admin/lab-results/register.ts` の設計・`allow_create` を UI から送っていない）。

---

## 1. なぜこの手順が要るか（2026-09-30 の実例）

本田さんのがんリスク検査で、**2 回分がまるごと DB に入っていなかった**。

| 受診日 | 方式 | DB | 状況 |
|---|---|---|---|
| 2026-06-04 | ALA-PDS | **無** | 未登録 |
| 2025-08-04 | ALA-PDS | **無** | 未登録 |
| 2025-01-06 | ALA-PDS | 有 | `17a22f15-ac50-4e00-863f-0ee59d3e358b` |
| 2024-09-02 | Noah4 | 有 | `ff1cae06-24a7-4c9f-93dd-7bafb8492ef9` |
| 2024-06-10 | Noah4 | 有 | `766e7f86-81ea-4560-aa1c-3d74cf79f347` |
| 2023-08-03 | Noah4 | 有 | `9b6bafd0-02d5-4865-92b1-377de1814913` |

**症状**: ダッシュボードのがんリスク検査が古い回しか出ない。グラフが出ない。

**先に `/admin/lab-results` へ PDF を上げると必ず止まる**（実測）:

```
artifact_not_found / active な cancer_urine が見つかりません。
既存に付けるなら test_artifact_id を、新規に作るなら allow_create を指定してください。
```

→ **これは想定どおりの挙動**。原本を付ける先（検査）がまだ無いだけ。**①を先にやる。**

### 現状を確かめる小技

`/admin/lab-results` で **受診日を空欄**にして実行すると、
`artifact_ambiguous` のエラーに **その方の active な検査が ID と受診日つきで全部並ぶ**。
**DB に何が入っているかを知る一番早い方法**（Production DB を直接見られない人でも分かる）。

## 2. 手順① `/admin/elith-batch` でスキャンする（回を作る・数値を入れる）

**1 ファイルずつ、回数分くり返す。** まとめて選ばない。

| 欄 | 入れる値 |
|---|---|
| フォーマット | **CancerRiskAssessmentData** |
| client_id | **`fixed`** を選び、対象者の **diagnostic_user_id** を入れる |
| **受診日** | **その回の受付日**（例 `2026-06-04`） |
| 既存 artifact ID | **空欄**（新しい回を作るので） |
| ファイル | その回の原本 PDF 1 本 |

### 受診日は必ず入れる（**ここを飛ばすと 1 件消える**）

ALA-PDS の PDF は**ファイル名が報告日**のことがある
（例 `260612ALAPDS…` = 報告日 2026.06.12 / 受付日は 2026.06.04）。

受診日を空欄にすると読み取り結果の日付で積まれ、**2 件が同じ日付になった瞬間に
S3 のキーが衝突して片方が上書きで消える**
（キー = `{format_id}_date_{YYYY_MM_DD}_user_{client_id}.json`）。
過去に実際に起きたため、`/admin/elith-batch` に受診日欄が足されている
（`wellfort-site/src/pages/admin/elith-batch.astro` の 2026-09-28 のコメント）。

**受付日は PDF の「■ 受付日」に印字されている。** 報告日と取り違えないこと。

### 実行後に必ず見るもの

- 結果行の **`dashboard.rows` が 0 でないこと** … 0 なら数値が保存されていない
- 結果行の **`test_date`** が指定した受付日になっていること
- 結果行の **`date_source`** … `today` になっていたら受診日の指定が効いていない

### 副作用（承知のうえで使う）

`/admin/elith-batch` は **Elith 向け JSON も S3 へ書きます**。この経路と一体で切り離せません
（`src/pages/api/admin/elith-scan.ts:192` の `putFiles`）。
**Elith へ出したくない場合はこの手順を使えません** — 別途相談すること。

## 3. 手順② `/admin/lab-results` で原本 PDF を付ける

①で回ができたので、今度は通る。**これも 1 本ずつ。**

| 欄 | 入れる値 |
|---|---|
| 検査会社 | **プリベント（がんリスク検査）** |
| 診断ユーザーID | 対象者の **diagnostic_user_id** |
| 受診日 | その回の受付日（①と同じ） |
| 検査 ID（artifact） | **空欄**（uid × 検査会社 × 受診日 で 1 件に特定される） |
| 既に原本があるとき差し替える | 既に原本が付いているときだけ ✓ |
| ファイル | 同じ原本 PDF |

- **診断ユーザーID を必ず入れる。** 空欄だと `00000000-0000-0000-0000-000000000000`（顧客未割当）に
  付き、**誰の画面にも出ない**。
- `sha256` と `size_bytes` は**サーバが S3 の実体から算出**する（ブラウザの申告は使わない）。
- **`external_test_id`（検査 ID・K0326 等）はこの口では入らない。** `register` は
  `test_artifacts` を一切 UPDATE しない設計（既存の `display_mode` 等を壊さないため）。

## 4. 手順③ 確認（ここまでやって完了）

ダッシュボード → **がんリスク検査**

| 見るもの | 期待 |
|---|---|
| カード | **最新 = 追加した最新回の受診日** |
| 「データ」 | その回の `/result/<id>` が開く |
| その画面 | **「検査結果の数値」**に 尿中のポルフィリン量 / インデックス値 / リスクランク |
| 同 | **原本 PDF が画面内に表示**（iframe）＋「原本を開く」でも同じ PDF |
| 「過去データ」 | 全回分が受診日の降順で並び、**過去回も同じように数値と原本が出る** |
| 「グラフ」 | **ALA-PDS の最新 2 件だけ**が点になる（§6） |

**「DB に行が入った」で完了にしない。** 画面で上の 6 つを目で見るところまでが完了条件。

## 6. コード側の前提（`808e27a` で対応済み・参考）

この手順が成立するために、2026-09-30 に入れた対応。**運用で意識する必要はないが、
挙動の理由を知るために書いておく。**

| 対応 | 中身 |
|---|---|
| **ALA-PDS の方式判定** (`src/lib/ala-pds.ts`) | **日付でなく項目名**で判定。「尿中のポルフィリン量」（「の」有無の 2 表記）と「インデックス値」の**両方**を持つ回だけを ALA とする。**完全一致のみ**（部分一致にすると別項目を巻き込む） |
| **推移グラフは ALA の最新 2 件だけ** | Noah4（BMI・塩分・尿糖…）と ALA は**測っている物が違う**ので 1 本の線に混ぜない。Noah4 は回ごと落ちる。**ALA が 1 件も無い方は絞らない**（グラフを黙って空にしない） |
| **`/result/[id]` に「検査結果の数値」** | 以前は `scan_md`（利用者のアプリ内スキャンだけが書く）と原本 PDF しか出しておらず、**admin 取込の検査は値が画面のどこにも出ていなかった**。`test_artifacts.measurements` を読むようにした |
| **インデックス値の数値化** | `"0.9 / 8.0"` → `value_num = 0.9`。これが無いとグラフに点が乗らない。**`value` は原本表記のまま**（書き換えない） |
| 表示名 | 画面は **「尿中のポルフィリン量」** に統一（DB の `item_name` は原本のまま） |

検査 = `npm run verify:ala-pds`（決定論・推移グラフ・保存・**実際の SSR HTML** の 4 層）。

## 7. 詰まったときの切り分け

| 症状 | 原因 | 対処 |
|---|---|---|
| `artifact_not_found`（②で） | その受診日の検査がまだ無い | **①を先にやる**。受診日の指定ミスも疑う |
| `artifact_ambiguous`（②で） | 受診日を空欄にした／同じ日に複数ある | エラーに出た候補の ID を「検査 ID（artifact）」に入れ直す |
| `artifact_user_mismatch` | 指定した artifact が別人のもの | uid と artifact の組を確認 |
| 数値が画面に出ない | ①の `dashboard.rows` が 0 | ①をやり直す。読み取りに失敗している |
| グラフが出ない | ALA の回が 1 件しか無い | **推移は 2 回目から**。もう 1 回分を登録する |
| グラフに BMI・塩分が出る | ALA 判定が効いていない | その回の項目名を確認（「尿中のポルフィリン量」と「インデックス値」が揃っているか） |
| 日付が 2 件とも同じ | **受診日を入れ忘れた** | §2 の警告どおり。片方が消えているので登録し直す |
| 画面には出るが値が PDF と違う | 読み取りミス | §5 の照合表と突き合わせ、合わなければ採用しない |

## 8. やってはいけないこと

- **②→① の順でやらない**（必ず止まる）
- **受診日を空欄のまま①を実行しない**（回が上書きで消える）
- **診断ユーザーID を空欄のまま②を実行しない**（誰の画面にも出ない行ができる）
- **artifact の UUID を推測で入れない**。分からなければ②を受診日空欄で実行して候補を出させる
- **PDF と違う値を手で入れない**（原本表記を書き換えない・計算し直さない）

## 9. 【追記 2026-09-30】同じ受診日が重複して表示されたとき

**症状**: ダッシュボード → 「データ」→「過去データ」に**同じ受診日が 2 つ並ぶ**。
グラフでも同じ日に点が 2 つ乗る。カード自体は最新 1 件しか出さないので正常に見える。

**原因は 2 つある**（どちらもコード側は 2026-09-30 に修正済み）。

| # | 何が起きていたか |
|---|---|
| ① | **ユーザーのスキャンを送り直すと行が増えていた** — `saveScanResult` が無条件 insert で、admin バッチにはあった「同日の差し替え」が無かった。**複数年アップロードは再アップロードが前提**なので必ず踏む |
| ② | **「過去データ」の一覧が `status` を見ていなかった** — 差し替え前 (superseded)・取り下げ後 (withdrawn) の回まで並んでいた |

**既に入ってしまった重複行の片付け**:
`supabase/cleanup_duplicate_health_checkups.sql` を**上から順に**実行する。
STEP 1（SELECT だけ）で消える行を確認してから STEP 3 を流すこと。

- **各 (人・検査種別・受診日・取込元) の最新 1 件を残す**
- **原本ファイルが付いている行は消さない**（`test_artifact_files` は cascade。
  消すと 10 年保管の原本の記録ごと消える）→ `superseded` に落とすだけ
- `measurement_values` は cascade で一緒に消える（残すとグラフに幽霊の点が出る）

**確認**: `GET /api/debug/viewer?k=<PROBE_UPLOAD_TOKEN>&u=<uid>` の
`health_checkup_years` で **`active_rows` と受診日の種類数が一致**すること。
そのうえで画面の「過去データ」とグラフを目で見る。
