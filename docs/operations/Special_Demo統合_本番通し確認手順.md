## 1. 切り分けの基本 — `/api/debug/viewer` の読み方

**この 3 ブロックだけ見る。** 画面を見ただけでは「資格が無い」と「モードが real」を区別できない。

| 鍵 | 意味 |
|---|---|
| `mode.effective` | **いまどちらを表示しているか**（`real` / `demo`） |
| `mode.forced_demo` | **admin がデモ表示に指定しているか**。`false` ＋ `effective:'demo'` は**既定**でデモ（デモの資格だけの枠 / 未サインイン） |
| `mode.dual` | 両方の資格を持つか |
| `report.can_demo` / `report.can_real` | その uid が持つ**資格**。**両方 true は正常な Dual**（裁定 6） |
| `report.dual_capability` | 同上（資格の側の Dual） |
| `report.is_special` | スペシャル枠（実データの枠）か |
| `report.demo_enabled` | **いまダミーを出すか**（`shouldUseDemoData` の結果） |
| `report.effective_uid` | 表示中の uid |
| `artifacts.using_demo_data` | 検査データがダミー由来か |

**要点 =「資格」と「いま出るか」は別物**。
`can_demo:true` なのに `demo_enabled:false` は、**Real を表示中**という正常な状態（Dual の既定）。
全停止（`PUBLIC_DEMO_FALLBACK=false`）だと**資格そのものが落ちる**（`can_demo:false`）。

## 2. A. 統合管理画面（PR-E・7 項目）

画面 = wellfort-site **`/admin/experience-accounts`**（サイドバー「設定」→
**「デモ／スペシャルアカウント」**）。

| # | 操作 | 期待 |
|---|---|---|
| **A-1** | メールだけで登録 | 資格の列が **「実データ」**。uid が発行されて行に出る |
| **A-2** | 「デモも見せる」にチェックして登録 | 資格が **「両方（Dual）」**・**uid は 1 つだけ**（2 行に割れない） |
| **A-3** | 既存の行で［デモも見せる］→ メールを再入力 | **一致すれば**追加される |
| **A-3′** | 同じ操作で**別人のアドレス**を入れる | **何も送られない**（ブラウザ内で SHA-256 を突き合わせて送信前に止める）。行は 1 文字も変わらない |
| **A-4** | ［デモを外す］ | **実データ側は変わらない**（資格の列が「実データ」になる） |
| **A-5** | uid 直接の行で［実データを外す］／［デモを外す］ | **それぞれの名簿にだけ**効く（デモを外したのにスペシャル側が消える、が起きない） |
| **A-6** | 旧 URL `/admin/demo-accounts` / `/admin/special-accounts` を開く | **302 → `/admin/experience-accounts`**。旧画面の中身は出ない |
| **A-7** | 既存機能 ［追加検査データ］［共有URL設定］［Elith納品］［メール変更］ | **従来どおり動く**（統合で機能を落としていないことの確認） |

**A-3′ がいちばん大事**: ここを取り違えると**別人にダミーが出て、この行は何も変わらない**ので
画面を見ても気づけない。

## 4. C. 表示モード（PR-C ＋ §4.2.3・7 項目）

**切替は利用者側に無い**（発注者指示 2026-10-22）。相手はマスコミ・大口クライアントなので、
本人の画面に「デモ / 実データ」の切替は出さない。**admin が管理画面で決める** —
`/admin/experience-accounts` の列「**いま出る画面**」の ［デモを出す］／［実データを出す］。
反映は **最大 45 秒**（app_config の TTL・再デプロイ不要）。

| # | 操作 | 期待 |
|---|---|---|
| **C-1** | Dual のアカウントでログインした**直後** | **Real**（`mode.effective:'real'` / `mode.forced_demo:false`）。**ダッシュボードに切替 UI が 1 px も無い** |
| **C-2** | 管理画面で その人を ［デモを出す］ → 本人が開き直す | 検査結果・推移グラフ・お知らせが**ダミー**（`artifacts.using_demo_data:true` / `mode.forced_demo:true`） |
| **C-3** | 管理画面で ［実データを出す］ → 本人が開き直す | **同じ uid の実データ**に戻る（切替で実データを変更・削除・re-key しない＝裁定 3） |
| **C-4** | **デモ表示にした状態**で `/dashboard` と `/scan` を見る | **単品購入の枠（`singlePurchase`）と複数年の枠（`multiYear`）が出ない**（Special 専用 UI は `effectiveMode === 'real'` のときだけ＝裁定 3） |
| **C-5** | 一般の顧客（Demo 資格なし）でログイン | `mode.effective:'real'`・切替 UI なし・管理一覧にも出てこない |
| **C-6** | admin 代理表示（`/admin-view/<ctx>/…`）で Dual を開く | **本人が見るのと同じ画面**（デモ表示にしていれば admin にもデモが見える）。閲覧者の種別でモードは変わらない |
| **C-7** | 管理画面で **デモの資格が無い人**を ［デモを出す］ | **却下され理由が出る**（「デモの資格が無い」）。表示は実データのまま＝**資格 → 表示 の順** |

**既定の表**（admin が指定していないとき）= Dual は `real` / Demo だけの枠は `demo` /
一般顧客は `real` / 未サインインは `demo`。**§4.2.3 で既定は 1 つも変えていない**ので、
admin が指定しなければ PR-C 前と同じ挙動。

> **旧 Cookie が残っている人**: `welltect_mode` は**誰も読まなくなった**ので、
> admin の指定（既定は real）に従う。能動的な削除はしていない（30 日で失効）。
> **`POST /api/session/view-mode` は存在しないので 404**。

## 5. D. 書込み監査（PR-D）

**Demo 表示中に本番のデータへ書かないこと**の確認。2 つの分類で期待が違う。

### 分類 A（Demo では no-op・画面は進む）

| # | 操作 | 期待 |
|---|---|---|
| **D-1** | Demo 表示中に**重要なお知らせの既読**を押す | **エラーが出ない**（以前は押した瞬間に 400 `invalid notice id`）。`user_notices` は変わらない |
| **D-2** | Demo 表示中に**キットの自己申告**（受取済／返送しました）を押す | 画面は進むが**本番の出荷は変わらない** |

デモのお知らせ ID = `d0000000-0000-4000-8001-000000000001` / `…0002`、
デモの出荷 ID = `d0000000-0000-4000-8000-000000000001` 〜 `…0006`。

### 分類 B（Demo では 403・擬似成功を返さない＝裁定 4）

| # | 操作 | 期待 |
|---|---|---|
| **D-3** | Demo 表示中に **AIスキャンを送信** | **403 `demo_mode_write_blocked`**。画面に「デモ表示中は本番のデータに保存しません。実データとして記録するには、表示を「実データ」へ切り替えてください。」 |
| **D-4** | Demo 表示中に **AI問診を完走** | 完了の記録が本番に残らない（**画面には何も出ない** — 下の申し送り参照） |
| **D-5** | **Real へ切り替えてから**同じスキャンを送信 | **従来どおり保存される**（ゲートが広すぎないことの確認） |
| **D-6** | **一般の顧客**（Demo 資格なし）でスキャンを送信 | **止まらない**。ゲートは Demo 資格を持つ人の Demo 表示だけに効く |

**D-6 を飛ばさないこと** — ここが壊れると**利用者が保存できなくなるのに、
デモで試している側には何も起きない**ので気づきにくい。

対象 4 本 = `/api/scan/save` / `/api/scan/jobs` / `/api/scan/export` / `/api/interview/export`。

## 6. E. バーコードのデモ読取テスト（PR-A）

`labid.prevent_capture` は本番で**既に on**。

| # | 操作 | 期待 |
|---|---|---|
| **E-1** | **Demo 表示中**に、デモのがんリスク出荷（発送済み）の撮影ブロックから撮影・登録 | 「**読取テスト完了／デモモードのため番号は保存されません／もう一度撮影する**」。応答は `demo: true` ＋**マスクだけ**（全文は返らない）。**何度でも繰り返せる** |
| **E-2** | 直後に `customer.lab_test_id_captures` を見る | **行が増えていない**（絶対条件 8） |
| **E-3** | **Real の利用者**が**本物の出荷**で登録 | 従来どおり台帳に入る（デモ扱いにならない） |

条件は **`effectiveMode === 'demo'` ∧ デモの出荷 ID** の**両方**。片方だけでは no-op にならない
（デモ資格の人が本物の出荷を登録できる／本物の利用者が偽の成功を受け取らない）。

## 7. 落ちたときの切り分け

| 症状 | 最初に見るところ |
|---|---|
| 統合画面が「一覧を取得できません」 | **デプロイ順**。Scan 側（API）が入っているか。`GET /api/admin/experience-accounts` を token 無しで叩いて **401** が返るか（404 なら Scan 側が古い） |
| 登録したのに資格が立たない | **app_config の TTL 45 秒**。45 秒待って `/api/debug/viewer` を見る。それでも `can_*` が false なら uid が未発行か除外リストに入っている（画面に「除外中」と出る） |
| 管理画面に切替ボタンが出ない | その行に**デモの資格が無い**（`displayChangeable:false`）。uid 未発行 / 除外中 / デモ未登録 / uid 食い違い のどれか。資格の列に理由が出る |
| 切り替えたのに画面が変わらない | ①**45 秒待つ**（app_config の TTL）②本人が**開き直す**（SSR なので再読込が要る）③`mode.forced_demo` が true か ④`report.demo_enabled` と **`PUBLIC_DEMO_FALLBACK`**（全停止）|
| 管理画面は「デモ」なのに本人は実データ | `mode.forced_demo` を見る。**false なら指定が保存されていない** — 管理画面の却下理由（「デモの資格が無い」）を読む |
| `/api/session/view-mode` が 404 | **正常**。利用者がモードを書く口は撤去した（§4.2.3）|
| Demo なのに実データが出る | `report.effective_uid` と `artifacts.using_demo_data`。**代理表示のタブで見ていないか**を先に確認 |
| 本人がログインできない（409） | **uid 競合**。統合画面の先頭に出ているはず。**自動統合しないのが仕様**なので、どちらを本物にするかは人が決める |
