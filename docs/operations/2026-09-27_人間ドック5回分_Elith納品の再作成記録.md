## 1. 何が起きていたか (一行)

**51 ページの人間ドック PDF のうち、先頭 9 ページぶんしか読まれていなかった。**
残りの 41〜45 ページは**警告もエラーも出ないまま消え**、読めた範囲から作った JSON が
そのまま Elith へ納品されていた。

発端は Wellfort からのレビュー指摘:

> 2026 年 8 月の eGFR 68.5 がクレアチニン値と合わない。
> 8 月 19 日のクレアチニンは 1.05 mg/dL で、日本人の推算式 (55 歳男性) で計算すると
> 約 58 になり、68.5 にはなりません。

## 2. 原因の連鎖 (実測で確定した順)

| # | 事実 | 根拠 |
|---|---|---|
| 1 | **68.5 という値は 5 冊の原本 PDF のどこにも無い** | 176 ページぶんを全文検索して 0 件 |
| 2 | 2026-08-19 の真の値は **Cr 1.24 / eGFR 48.5** | 原本 (健康院クリニック 検査結果報告書) |
| 3 | 原本 6 枚とも JSN 2009 式 `194 × Cr^-1.094 × Age^-0.287` に **±0.0 で一致** | 転記前の原本で検算 |
| 4 | → 値の破壊は**原本と Elith の間**で起きている | 1〜3 から |
| 5 | 同じ 1 枚の票から作られた 2 つの artifact のうち**片方だけが壊れていた** | 下表 |

同一の検査票から作られた 2 つの artifact の比較 (項目単位で原本と突き合わせた実測):

| 生成経路 | 今回列と一致 | 前回列を拾った | 前々回列を拾った | 紙に無い値 |
|---|---|---|---|---|
| アプリのスキャン (PDF をそのまま送る) | **40** | 0 | 0 | 1 |
| admin バッチ (10 ページを 1 枚の JPEG に連結) | 11 | 11 | 4 | **10** |

**「列がまるごと 1 つずれた」のではない**。行ごとに今回/前回/前々回がばらばらに混ざり、
さらに紙に無い値が 10 件生じていた。**縦に潰した 1 枚画像から読ませたことによる崩れ**で、
特定の列を機械的に戻せる形ではない。

### なぜ 41〜45 ページが消えたのか

`wellfort-site` の `/admin/elith-batch` が PDF を 1 枚の縦連結 JPEG にしていた。そこに
**2 段の打ち切り**があった。

```js
var maxPages = Math.min(pdf.numPages, 10);      // ① 先頭 10 ページだけ描く
...
big.height = Math.min(totalH, 16000);           // ② 高さ 16000px で切る
```

1240px 幅の A4 は約 1754px なので、②で **10 枚目も途中から切れる**。
実効 **9.13 ページ**。51 ページなら 41〜45 ページが落ちる。
**どちらの打ち切りもログにも画面にも出ない。**

### なぜ同じ票が 2 回処理されていたのか

当初この検体は「スペシャルアカウントの複数年アップロード」(アプリのスキャン機能) で
本人が 5 つの PDF を上げた。ところが JSON が 1 つしかできなかったため、急ぎ
admin の Elith バッチで処理し直した。**先に入った (正しい) スキャン結果と、
後から入った (壊れた) バッチ結果が両方 DB に残っていた。**

## 3. 併せて見つかった不具合 (この復旧の妨げになったもの)

1. **admin バッチは `test_artifacts` に 1 行も保存できていなかった。**
   `persistAdminBatchHc()` が `source='admin_batch'` で insert するが、CHECK 制約は
   `('user_upload','wellfort_lab')` のままで、insert が毎回 23514 で失敗していた。
   失敗は API 応答の `dashboard.reason` にしか出ず、admin 画面がその欄を描いていなかったので
   **画面は ✅ のまま**だった。
2. **`measurement_values` を読むクエリが `test_artifacts.status` を見ていなかった。**
   superseded に落とした回の値が、そのまま「読み取り結果」と推移グラフに混ざる。
3. 2025-08-20 の artifact に **基準値の下限を値として拾った行が 7 件** あった
   (基準吸い上げ。`fabgate.refbleed` は既定 off)。
4. 納品側に**問診 JSON が 4 重複**していた。

§7 のとおり 1・2 はこの日にコードを直した。3・4 は未着手 (§8)。

## 4. 復旧の方針

- **`client_id` は変えない** (`7251458a-…`)。Elith 側の既存フォルダをそのまま使う。
- **値は原本 PDF から人手で起こす**。壊れたスキャン結果を機械的に補正しない
  (どの行がどの列から来たか復元できないため、補正は推測になる)。
  → `docs/scan/golden/` と同じ規律 (「golden は必ず元画像から人手で起こす」)。
- **納品 JSON は 1 年 = 1 ファイル**。5 回ぶんで HealthCheckupData 5 + HealthAgeData 5。
- **消すのは人間ドックとウェルネス年齢だけ**。がんリスク・遺伝子・LAiF・問診は触らない。

### 転記の範囲 (発注者判断)

| 判断 | 内容 |
|---|---|
| 範囲 | **血液中心 + 身体計測**。加えて**尿検査・便検査**を含める |
| 形式 | 本番のスキャンが書くのと同じ 9 列 Markdown (`markdownClean` と同形) |
| 「キャンセル」の扱い | 原本の表記のまま残す |
| 脂肪酸分画 (p10) | **5 回分すべてに追加する** (前回の納品に入っていたため、外すと後退になる) |

転記した行数: 2024-09-03 = 124 / 2024-12-11 = 105 / 2025-08-20 = 123 /
2025-12-24 = 106 / 2026-08-19 = 123。

**転記しなかったもの** (指示が無いので足していない): 内臓脂肪面積 241 cm² ・
カルシウムスコア 0.0 (p9)、骨密度・CAVI/ABI・LOX-index・眼底 (p21 以降)。

## 5. 実際の手順 (この順でないと壊れる)

### ① DB: 検査値を入れ直す (Supabase SQL Editor)

`03_test_artifacts_v2.sql` を 1 トランザクションで実行。中身は 4 段:

1. 既存の active な人間ドックを **`superseded` に落とす** (**消さない** = 監査のため)
2. 原本から起こした 5 回分を `status='active'` で insert
   (`source='wellfort_lab'` / `imported_by='wellfort_manual'`。
   **当時 `admin_batch` は CHECK 違反で入らなかった** — §7-1 で解消済み)
3. superseded になった行の `measurement_values` を削除
   (当時は §3-2 が未修正で、消さないと推移グラフが古い値を拾ったため。
   **§7-2 を入れた今は、この削除は不要**)
4. COMMIT 前に件数を目視

### ② S3: 古い納品 JSON を消す

**バケットはバージョニングが有効**なので、削除は削除マーカーが付くだけで復元できる。

```bash
# 消す前に必ず一覧を取る
aws s3 ls s3://wellfort-ai-input/user/7251458a-1ef5-412a-b590-ebdbe202b4fd/date/ \
  --recursive --region ap-northeast-1

# HealthCheckupData_ / HealthAgeData_ だけを消す (17 件)
#   ※ GeneticTestResultData / LifestyleQuestionnaireData / CancerRiskAssessmentData は消さない
aws s3 rm s3://wellfort-ai-input/<key> --region ap-northeast-1
```

> **踏んだ落とし穴が 2 つある。**
> 1. スクリプト (`delete-elith-hc.sh`) を用意したが、CloudShell へ**本文を 1 行ずつ貼り付けた**
>    ため配列が壊れ、KEEP が 9 件のはずが 2 件になった。**スクリプトはファイルとして
>    アップロードして実行する**こと。今回は途中でスクリプトを諦め、`aws s3 rm` を直接並べた。
> 2. 納品側の `GeneticTestResultData` を「ボタンで作り直される」と思って消したが、
>    **作り直されない**。`deliverReadySpecialAccounts` の `manualMapping` は
>    **HealthCheckupData と LifestyleQuestionnaireData の 2 つだけ**を持つ。
>    削除マーカーを外して復旧した:
>    ```bash
>    aws s3api delete-object --bucket wellfort-ai-input \
>      --key user/.../GeneticTestResultData_....json \
>      --version-id "DlD99nG.yJZ4GR0pbwraFh9FF7vRyAeS" --region ap-northeast-1
>    # → {"DeleteMarker": true} が返れば復元されている
>    ```

### ③ DB: 納品記録を消す

```sql
DELETE FROM diagnosis.elith_deliveries
 WHERE diagnostic_user_id = '7251458a-1ef5-412a-b590-ebdbe202b4fd';
```

これをやらないと、毎晩 23:00 の cron (`GET /api/cron/elith-deliver`・`skipDelivered:true`) が
「全ての回が納品済み」と判断して**丸ごとスキップ**する。

### ④ 納品を作り直す

`/admin/special-accounts` の **「Elith納品を一括作成」** を押す
(`POST /api/admin/special-accounts/deliver`・`deliveryPrefix: ''`)。

- `materializeHealthCheckups` が `test_artifacts` (status='active') から
  **年ごとに 1 つずつ** HealthCheckupData を作り直す (AI は呼ばない = 決定論)。
- ウェルネス年齢も年ごとに算出して同じ date フォルダへ入る。
- **手動ボタンと 23:00 の cron で二重にはならない** — 納品済みの回は
  `skipDelivered` で cron 側がスキップする。

### 1 と 2 で運用がどう変わるか

- 51 ページの PDF を 1 つ選んでも **51 枚に展開して 1 枚ずつ読む**。
  1 枚あたり 3 秒の待ち + 読み取り時間がかかるので、**51 ページなら 15 分以上**。
  始める前に「ファイル N 件 → M 枚に展開しました」と枚数を出す。
  途中で失敗しても、同じファイルを選んで「実行」を押し直せば続きから再開する (従来どおり)。
- 展開後 12 枚を超える回は **🔍 画像照合を省略**する
  (51 枚ぶんの画像は 30MB を超え、照合リクエストが 4.5MB 上限を確実に超えるため)。
  **🎯 ゴールデン照合は画像を使わないので枚数に関係なく使える。** 行に理由を出す。
- 人間ドック以外 (がんリスク等) で 1 枚に収まらない PDF を渡すと、**エラーで止まる**。
  部分的な JSON を作って納品するより止める方が安全、という判断。

### 発注者の操作が 1 つ要る

**マイグレーション `20260927000010_test_artifacts_source_admin_batch.sql` の適用**
(`supabase db push`)。これを当てるまでは admin バッチの DB 保存は失敗し続けるが、
**S3 への Elith 納品には影響しない** (別経路)。適用前でも 1b の表示は出るので、
失敗していることは画面で分かる。
