## 0. 本書の位置づけ

**デモ用アカウント（`docs/operations/デモ用アカウント_仕様書.md`）とは目的が逆である。**
仕組みは似ているが、**混ぜてはいけない**。本書はその線引きを固定するためにある。

| | デモ用アカウント | **スペシャルアカウント** |
|---|---|---|
| 目的 | UI 確認・PR・お披露目 | **実際の検査データを扱う** |
| 見えるもの | **ダミー**（`demo-data.ts`） | **本人の実データ** |
| 渡す相手 | 記者・パートナー（社外） | 本人 |
| 登録の重み | 軽い（何度でも） | **重い（実データが紐づく）** |
| 全停止スイッチ | `PUBLIC_DEMO_FALLBACK=false` | **持たない**（§7） |

**同じ枠に入れてはいけない理由**: デモ枠に入れると `demoFallbackEnabled()` が真になり、
**本人の画面に他人名義のダミー検査結果が出る**（`src/lib/demo-data.ts:66-69`）。
実データを扱う本枠では致命的。

## 1. 目的

EC で購入していない人に、**本人の実データで**アプリを使ってもらう。

- HP マイページ → Web アプリへログインできる
- スキャン・AI 問診が本人のデータとして保存される
- Elith 納品・報告書の表示まで、通常の顧客と同じ経路を通る

**初回は 1 名だが、同種の依頼が続く前提で汎用に作る**（発注者指示 2026-09-15）。

## 2. なぜ仕組みが要るか

`api/auth/resolve.ts` は EC 顧客を引けないと未連携で早期 return する。
そのままでは**入口で弾かれる**。デモ枠が同じ問題を
`resolveDemoUidByEmail()` で回避しており（`api/auth/resolve.ts:180`）、本枠も同じ位置に置く。

## 3. 判定

```ts
isSpecialAccount(uid?: string | null): boolean
```

- **判定はこれ 1 つ。** 閲覧者が admin かどうかは**見ない**（デモ枠で踏んだ誤り）
- 引数は**表示中の** `diagnostic_user_id`。admin が `?u=` で代理表示しているときは相手の uid
- **毎リクエストは uid だけで判定**する（メールを持ち込まない＝同期関数のまま保てる）

---

## 4. 登録は Google アカウント（メール）、判定は uid

人は自分の `diagnostic_user_id` を知らない。**登録はメール、判定は uid** に分ける
（デモ枠と同じ理由）。

### 4.1 保存するもの

1 行 = `<sha256> <マスク> <uid|-> # メモ` の 4 つだけ。

- **メールの現物は保存しない。** ハッシュとマスク（`r***@example.com`）のみ
- 氏名は扱わない
- **`uid` はメール登録のその場で発行する**（2026-10-05 の仕様変更・下記 §4.1.1）

#### 4.1.1 uid はメール登録時に発行する（2026-10-05・発注者指示）

**本人の初回ログインを `diagnostic_user_id` の発行条件にしてはいけない。**

旧仕様:

```
メールで登録 → uid は空 → 本人が初回サインイン → uid を採番
→ メール行と special.account_uids へ保存
```

新仕様:

```
メールで登録 → **その場で diagnostic_user_id を発行**
→ メール行と special.account_uids の両方へ保存
→ **本人がまだログインしていなくても検査データを事前登録できる**
→ 後日本人が Sign up / Sign in
→ 事前発行済み uid に Auth identity を紐付ける
```

**なぜ変えたか**: admin 画面の［追加検査データ］［共有URL設定］［Elith納品］は
**uid が無いと押せない**。旧仕様では本人が来るまでデータを入れられず、
「本人のログイン前に健診・遺伝子・報告書を準備する」運用（トランスコスモス 10 名）が
成立しなかった。

**⚠️ ここで作るのは `diagnostic_user_id` だけ。** 以下は**作らない**:

```
Supabase Auth user / password / Google identity / auth_user_id / google_sub
```

Supabase Auth アカウントは、**本人が Web アプリで Sign up / Sign in したときに
従来どおり作成・認証される**。**admin が Auth ユーザーを代理作成したり、
仮パスワードを設定したりは絶対にしない。**

**冪等**（同じメールを登録し直しても uid を作り直さない）:

| メール行 | uid | 動作 |
|---|---|---|
| ある | ある | **そのまま維持**（label / DOB / sex の更新でも変えない） |
| ある | 空 | **ここで 1 度だけ**発行して新仕様へ移行（legacy の救済） |
| ない | — | 発行して行を作り、`special.account_uids` へも足す |

**legacy 行（uid 空）の扱い**: GET しただけでは書き換えない。**一括 migration は行わない。**
管理画面から**同じメールで登録し直したときに発行**される（画面には
「ID が未発行です（登録し直すと発行されます）」と出す）。

**uid の衝突を作らない (fail-closed)**: `crypto.randomUUID()` の衝突確率は無視できるが、
**既存 uid を上書きする実装にはしない**。`special.account_uids` ＋ メール行 ＋
組み込み / env の uid を集めて `mintSpecialUid()` に渡し、当たったら引き直す。
引き直しは最大 `MINT_ATTEMPTS`（8）回。**全部外したときに衝突 uid を返してはならない**
（2026-10-05 hardening）。以前は最後の候補をそのまま返しており、返した瞬間に
「既存 uid と衝突しない」という契約が破れ、**別人の uid へ相乗りした行**ができる。
`mintSpecialUid()` は `null` を返し、admin API は **`503 uid_generation_failed`** で中止する
—— `setConfig()` を呼ばず、`special.account_emails` / `special.account_uids` の
**どちらも 1 文字も変更しない**（legacy 行の救済経路も同じ）。

**両方へ書く**: メール行だけに uid を書くと資格が立たない。
`special.account_emails` と `special.account_uids` を**同じリクエストの
1 回の `setConfig(updates, …)` にまとめて**渡す（片方だけ保存される形を作らない）。

**削除**: メール登録を Delete すると、事前発行済み uid も
`special.account_uids` から外れる（従来どおり）。
**その uid に入っている検査データは自動削除しない** — 実データの削除は別の重大操作。

### 4.2 uid の採番（3 段・最後の手段が新規発行）

```
① メール行に記録済みの uid
② その Google アカウントの既存 uid（app_users にある場合）
③ 新規発行（crypto.randomUUID）
```

**この順序は変えない。** 新仕様（§4.1.1）では登録時に uid を発行済みなので
**① がほぼ必ず当たる**。②③ は**新仕様より前に登録した行（uid 空）の救済**として残す。

②を飛ばすと、既に行がある人で UNIQUE 制約に衝突する（デモ枠の実装コメントに記録あり）。

**一度決めた uid は変えない。** 毎回変わると `app_users` に行が増え、履歴も繋がらない。
**新仕様ではこれがさらに重い** — 事前発行した uid に**既に実データが入っている**ので、
変えると本人の健康データが誰にも結び付かなくなる（§4.2.1）。

#### 4.2.1 事前発行 uid と `linkedUid` の競合は fail-closed で止める

`/api/auth/resolve` には、`linkedUid`（`app_users` を `auth_user_id` / `google_sub` で
引いた既存の束縛）が解決した uid と食い違うときに**既存 uid へ寄せる分岐**がある。
スペシャル枠は「顧客DB由来でない」ので、従来はこの分岐で**黙って張り替わっていた**。

新仕様では**それが事故になる**:

```
special 登録時 UID-A → UID-A に健診・遺伝子を投入 → 本人サインイン
→ 既存 linkedUid = UID-B → 黙って UID-B に切り替える
→ **UID-A の健康データと本人の認証が分離する**
```

| ケース | 動作 |
|---|---|
| 事前発行 UID-A ／ `linkedUid = null` | **A を使う** |
| 事前発行 UID-A ／ `linkedUid = A` | **A を使う**（張り替えなし） |
| 事前発行 UID-A ／ `linkedUid = B`（A ≠ B） | **何も書かずに 409** |

409 のときは **A→B も B→A も張り替えず、既存データの自動移行もしない**。
`app_users` の既存行・special の資格・検査データは**1 つも変更しない**
（detach / upsert / `linkDemoEmail` / `linkSpecialEmail` / viewer Cookie のいずれにも到達しない）。

**ガードの位置は `issueAdminCred()` より前**（2026-10-05 hardening）。以前は張り替え分岐の中、
つまり `issueAdminCred()` の**後ろ**にあった。本線の書き込みには届いていなかったが
**admin credential だけは set / delete されており**、「何も書かない」が成立していなかった。
前へ移したので **admin credential も 0 回**。

**照会に失敗した回を「事前発行なし」と同一視しない**（同 hardening）。
`specialPreassignedUidByEmail()` は `{ ok: true, uid }` / `{ ok: false }` を返す。
失敗を `null` で返していたときは、app_config の取得が落ちた回が「登録されていない人」と
**見分けが付かず**、ガードが素通りして**ちょうど守りたかった張り替えが起きた**。
引けなければ**何も書かずに 503**（既存 uid へ張り替えない）。
`uid: null`（登録なし / legacy の `uid=''` 行）は従来どおり素通りして救済に入る。

応答は利用者向けの文言のみ（生の DB エラー・内部情報は返さない）:

```
アカウント連携情報が既存のIDと競合している
```

**判定は推論に頼らない。** `specialPreassignedUidByEmail(email)` で
**事前発行済みかを直接引いて**突き合わせる。`resolveSpecialUidByEmail` の
戻り値から逆算すると、そちらの優先順位を 1 行変えた瞬間に**静かに効かなくなる**。

**デモ枠は従来どおり**（ダミーなので張り替えても実害が無い）。
解決順序（実顧客 → local/linked → staging → **スペシャル** → デモ → 未連携）も変えない。

#### 4.2.2 `uid` が在ることは「本人がサインインした」ことではない

`listSpecialAccounts()` が返す **`uidAllocated`** は
**「`diagnostic_user_id` が発行されて資格一覧にも載っているか」**。
新仕様では**登録直後から true**になる。

旧コードは同じ値を `linked` と呼び、コメントで
`linked = その人がもうサインインしたか` と説明していた。**これはもう成り立たない。**
`linked` は `uidAllocated` の **deprecated な別名**として残してあるが
（既存の API 形を壊さないため）、**「サインイン済み」の意味では使わない**。

本人の認証状況を知りたいなら **`diagnosis.app_users.auth_user_id`** 等、
**実際の Auth 紐付けを根拠にする**。`listSpecialAccounts()` は app_config しか
見ないので、その判定はここでは出せない。

**consumer の実測（2026-10-05）**: `linked` を読む実装は**この型定義以外に 0 件**
（wellfort-site の admin 画面は `uid` の有無だけを見ている）。

## 5. 供給元の和と除外リスト

```
出す uid = (組み込み ∪ env ∪ app_config) − 除外リスト
```

| 供給元 | 反映 | 用途 |
|---|---|---|
| `BUILTIN_SPECIAL_UIDS` | 要デプロイ | **原則として空にしておく**（下記） |
| env `SPECIAL_ALLOWED_UIDS` | 要デプロイ | DB 障害時の保険 |
| app_config `special.account_uids` | **admin から即時**（TTL 45 秒） | 通常はここ |

- **上書きでなく和。** 上書きだと 1 件登録した瞬間に他が消える
- **除外は和のあと。** 先に引くと config 側で足し直せてしまう
- **`BUILTIN` を名簿として育てない。** デモ枠と違い実データが紐づくので、
  **コードに焼き込むのは避け、原則 app_config で管理**する

## 6. サインイン時の橋渡し

`api/auth/resolve.ts` の **未連携 early return より前**に置く。後ろだと到達しない。

```
① 実顧客として引けるか（resolve-customer）→ 引ければそれ
② 引けない → スペシャル枠か（linkSpecialEmail / resolveSpecialUidByEmail）
③ それでも無ければ → デモ枠か（既存）
④ どれでも無ければ → 未連携（従来どおり）
```

**②を③より先に置く。** 両方に誤って登録された場合、**実データ側を優先してダミーを出さない**ため。

- 呼ぶのは `sb.auth.getUser()` が返した**サーバ検証済みの email** だけ。
  クライアントの申告で登録できてはならない（誰でも有効化できてしまう）
- **失敗しても例外を投げない。** サインインの経路なので、登録の失敗でサインインが壊れる方が害が大きい
- `refreshConfig()` は **TTL を尊重**する（強制リフレッシュしない）。
  全ユーザーが通る経路なので、毎回 DB 往復が増える

## 6.1 メール＋パスワード認証（2026-10-05・発注者指示）

**目的**: スペシャルアカウントは EC 購入を伴わない招待枠なので、Google アカウントを
持たない / 使いたくない相手にも渡せるようにする。**Google 認証は従来どおり残す。**

### 6.1.1 どの Supabase を使うか

**Scan-Chat-AI 自身の Supabase Auth**（診断アプリ側プロジェクト）。
**HP/EC（`wellfort-site`）のパスワードは共有しない** — 別プロジェクトであり、
Auth 連携もしない。利用者は**このアプリでパスワードを登録する**。

### 6.1.2 本人解決の口は増やさない

`POST /api/auth/resolve` が **Google / メール＋パスワード の共通合流点**。
メール認証専用の本人解決 API は作らない。§6 の解決順序
（実顧客 → local/linked → staging → スペシャル → デモ → 未連携）は **1 つも動かしていない**。
`findLinkedUid` / `resolveSpecialUidByEmail` / `linkSpecialEmail` のロジックと
シグネチャも**変えていない**。

本人判定に使うのは **`sb.auth.getUser()` が返したサーバ検証済みの `user.email`** だけ。
**クライアントが申告したメールアドレスは本人判定に使わない。**

### 6.1.3 【最重要】「持っている Identity」と「今回の認証方式」は別物

ここを混同すると、Google Identity を持つ人の password セッションを
「Google で入った」と誤判定し、§6.1.4 の拒否が効かなくなる。

| 概念 | 何から決めるか | 意味 |
|---|---|---|
| `hasGoogleIdentity` | `getUser()` の `app_metadata.provider` / `providers` / `identities` | **その人が Google Identity を持っているか** |
| `currentAuthMethod` | アクセストークンの **`amr`** | **今回のセッションが何で認証されたか** |

`app_metadata.provider` は公式に「**最初にサインアップに使った** provider」であり、
`providers` は**紐づいている全部**。どちらも「今回」を表さない。
`app_metadata` は Admin API でしか書けないので値としては信用できるが、
**問いが違う**ので今回の方式判定には使えない。

**`amr` の読み方**（`authMethodFromAmr`）:

| `amr[].method` | 判定 |
|---|---|
| `oauth` / `oauth_provider/...` / `sso/...` | `oauth` |
| `password` / `email/signup` | `password` |
| `magiclink` / `otp` / `totp` / `mfa/*` 等 | `other` |
| `token_refresh` | **無視**（更新の記録で元の方式を表さない） |
| 取れない / oauth と password が同時に立つ | `unknown` |

取得は **`sb.auth.getClaims(accessToken)` を優先**（`@supabase/auth-js` 2.106.1 に在る）。
使えない環境では、**`getUser()` の検証が通った後に限り**同じトークンの payload を復号して
`amr` だけを読む。**未検証の JWT を `getUser()` より前に信用しない** — `sub` と `email` が
`getUser()` の結果と一致することを確かめてから使う。**新しい依存は足していない。**

**`unknown` では何も止めない。** 止めるのは `password` と**確定した**ときだけで、
既存の Google ログインを 1 回も巻き込まないため。

### 6.1.4 禁じる切り替えは**一方向だけ**

> **Google 認証で既に利用済みのユーザーが、後から同じメールアドレスで
> メール＋パスワード認証を設定・利用するケース**を拒否する。

**逆（メール認証 → 後から Google）は禁じない。** 双方向を見張る `auth_provider` の
ような仕組みは作らない（DB 変更も無い）。

**拒否は 2 つの条件だけ**（`resolve.ts` の `issueAdminCred` より**前**・2026-10-05 是正）:

1. `diagnosticUserId` が決まっている ＋ **今回の方式が `password`**
   （`amr` 由来・`unknown` では止めない）
2. その uid の **`app_users.google_sub` が存在する**（= Google 利用済み）

→ **HTTP 409**。このとき
**`auth_user_id` / `google_sub` / `diagnostic_user_id` / スペシャル枠の email↔uid を
1 つも書き換えず、Cookie も 1 枚も発行しない**（detach / upsert / `linkSpecialEmail` の
いずれにも到達しない）。

### 6.1.4.1 **`auth_user_id` が同じか違うかは拒否条件にしない**

**禁じているのは「Google 利用済みの人がメール＋パスワード認証を使うこと自体」であって、
「認証 ID が張り替わること」ではない。** 両者を混同すると取り逃す:

- **本番 `diagnosis.app_users` 実測（2026-10-05）**: `google_sub` あり **24 件**。
  うち `auth_user_id` あり **11 件** / **`auth_user_id` が NULL のものが 13 件**。
  `auth_user_id` を条件に入れると、**この 13 件は password 認証を拒否できない**。
- 同じ auth user に後からパスワードを付けた回も `auth_user_id` が一致するので素通りする。

→ 判定は **`row?.google_sub` の有無だけ**。`auth_user_id` の値は見ない。

**照会が落ちたら通さない（fail-closed）**: 「Google 済かどうか不明」なので
**何も書かずに 503**。この照会は **`password` セッションのときだけ**走る。

**なぜ書き込みの前で止めるか**: `findLinkedUid` は `auth_user_id` / `google_sub` でしか
引けないので、**別の auth user で来た password セッションは `linkedUid` に当たらない**。
すると張り替え分岐を素通りし、`upsert` が既存行の `auth_user_id` / `google_sub` を
**無言で書き換える**。

### 6.1.5 `google_sub` の扱い

**「今回 Google で認証した」ときだけ書く。** `password` と確定したセッションでは書かない。
`amr` が取れなかった回（`unknown`）は**従来どおりの挙動**に倒す
（Google Identity があれば書く）ので、既存 Google ユーザーの動作は変わらない。
**書く値そのものの式は変えていない。**

## 6.2 HP マイページから来た初回利用者の導線（2026-10-05・発注者指示）

### 6.2.1 何が起きていたか

HP（`wellfort-site`）と Web アプリ（Scan-Chat-AI）は **別の Supabase Auth
プロジェクト**。HP で認証済みでも**こちらには認証ユーザーが居ない**。それなのに
Web アプリは「サインイン」を先に出していたため、初回利用者が HP のメール＋
パスワードを入れて `Invalid login credentials` になっていた（実測 2026-10-05）。

**正しい言い方 = 初回なら「新規登録（Sign up）」／登録済みなら「ログイン（Sign in）」。**
「新規サインイン」という概念は作らない。

### 6.2.2 渡すのは入口種別 1 つだけ

HP マイページのリンクに **`?entry=wellfort-mypage`** を付ける
（wellfort-site `src/pages/mypage.astro`）。

- **PII をクエリに載せない** — `?email=` / `?u=` / `?customer_id=` / auth user id 等。
  **URL 履歴・アクセスログ・Referer に個人情報が出る。**
  `?u=<diagnostic_user_id>` を外した 2026-09-29 の判断と同じ理由。
- **HP 側のメールアドレスを Web アプリへ自動転送しない。**
- JS で href を組み立て直さない（2026-09-29 に外したのは markup ではなく
  `loadProfile()` の書き換えだった。同じ形で戻ってこないよう機械で見張る）。

### 6.2.3 `entry` は UI 分岐専用。認証には一切使わない

誰でも付けられるクエリなので、**「`entry` が在る → 本人確認済み → `resolve` を省略」は
絶対にやらない**。認証後は従来どおり
**Supabase Auth → `access_token` → `POST /api/auth/resolve` → サーバが `getUser()` で検証**
を必ず通る。`resolve.ts` も `EmailPasswordAuth.astro` も **`entry` を 1 文字も読まない**。

### 6.2.4 画面の切り替え

`entry=wellfort-mypage` のときだけ:

| | 通常アクセス | HP マイページ経由 |
|---|---|---|
| 見出し | サインイン | Webアプリを利用する |
| 初期表示 | ログイン | **新規登録** |
| 主ボタン | サインイン / 新規登録 | アカウントを作成する / ログインする |

- **初期表示は SSR の `hidden` 属性で決める**（`hidden={fromMypage}` /
  `hidden={!fromMypage}`）。JS で切り替えると **JS が落ちた環境で従来の順序に戻る**。
- 判定は**完全一致**（`=== 'wellfort-mypage'`）。前方一致や「`entry` が在れば」にすると
  想定外の値で画面が変わる。
- **登録済みの人の出口（ログインへ戻る導線）は常に残す。** 片道にすると、登録済みの人が
  もう一度 signUp して「確認メールを送信しました」で止まる。
- **Google（One Tap / 公式ボタン）は entry でも消えない。** 入口を 1 つに減らさない。
- **実装は `src/components/SignInPanel.astro` だけ**（表示の器）。§6.1 の認証処理
  （`EmailPasswordAuth.astro`）と `/api/auth/resolve` は 1 行も変えていない。

### 6.2.5 メール存在の事前照会 API は作らない

未認証で「このメールは Scan 側に登録済みか」を聞ける口を作ると **User Enumeration**。
初回かどうかは**利用者に 2 つの入口から選ばせる**（§6.1.7 の方針そのまま）。

### 6.2.6 検証

| | 何を見るか |
|---|---|
| `npm run verify:email-auth` ⑪（M-01〜M-32） | 完全一致判定・初期表示の `hidden`・戻る導線・Google が消えない・`/` の 302 がクエリを保つ・`resolve` が `entry` を読まない・存在照会 API が無い |
| `npm run verify:screen` ⑦ | **実画面**で初期表示（entry 有/無）・1 クリック両方向の切替・URL のクエリが `entry` だけ |
| wellfort-site `npm run verify:webapp-entry` | リンクに `entry` が在ること・PII が URL に無いこと・JS が href を書き換えないこと |

**退行注入 20 種**（`entry` を落とす / 値を変える / `?email=` `?u=` を足す / `hidden` を
取り違える / 戻る導線を消す / Google を条件に入れる / `resolve` が `entry` を読む /
存在照会 API を足す 等）で名指しに落ちることを確認済み。

## 7. ダミーを出さない保証（**live コードへの唯一の変更**）

`demoFallbackEnabled()`（`src/lib/demo-data.ts:66-69`）に **1 行足す**。

```ts
export function demoFallbackEnabled(uid?: string | null): boolean {
  if (demoDisabledGlobally()) return false;
  if (isSpecialAccount(uid)) return false; // ← 追加：スペシャル枠にダミーは出さない
  return isDemoAccount(uid);
```

**なぜ足すか**: 両方に登録される事故が起き得る。そのとき**実データの利用者にダミーが出る**のは

ものだが、本枠を止めると**その人がログインできなくなる**（EC 顧客ではないため）。
緊急停止は**除外リストに 1 件入れる**（admin から即時）で足りる。

## 8.1 生年月日・性別（ウェルネス年齢用・2026-09-24・発注者指示）

**発注者指示**:「スペシャルアカウントの登録の際に生年月日と性別は登録項目に加えよう。
**生年月日の表示はブラインドにして**」。

**なぜ要るか**: スペシャルアカウントは EC 購入が無く `customer_profiles` に生年月日を持たない。
ウェルネス年齢（`computeWellnessAge`）は**実年齢が必須**なので、DOB が無いと算出できず
Elith 納品で「算出不能(不足: 年齢)」になる（実測）。登録時に控えて年齢ソースにする。

- **専用キー `special.account_dob` に隔離する**。1 行 = `<メール sha256> <YYYY-MM-DD> <male|female>`。
  - メール本体 `special.account_emails` と**混ぜない** — あちらは admin 画面へ生テキスト（emailsRaw）を
    返して編集させるので、生年月日を載せると**ブラインド表示が崩れる**。
  - 登録時点では uid はまだ無い（サインイン前）ので **メールの sha256 で控える**。
    uid からの参照はサインイン済みの email 行（uid↔hash）を辿る（`specialSubjectByUid(uid)`）。
  - **共有の純粋関数には手を入れない**（§9.1）。DOB は special 専用の追加
    （`parseDobEntries` / `serializeDobEntries` / `specialSubjectByUid` / `normSexToken`）。
- **生年月日はブラウザへ生で返さない**（＝ブラインド）。API GET / POST は `present()` を通し、
  生テキスト（dobRaw）を落として **`has_dob`（登録済みか）+ `dob_masked`（`****-**-**`）+ `sex`** だけを
  添える。一覧では `****-**-**` と性別ラベルだけを表示する。性別は PII 度が低いので出す。
- **任意項目**。空なら送らない（既存を空で上書きしない）。同じメールで登録し直すと上書き。
  メールを外す（remove_email）と同じハッシュの DOB 行も一緒に消す（PII を残さない）。
  **uid 直接追加（詳細欄）の経路には DOB を付けない** — メール登録が主経路のため。
- **暦日として実在しない日付（`2026-02-31` 等）・1900 未満/未来は捨てる**（捏造しない）。
  API 側 `validDob` と保存の解析 `isRealDob` の二段で弾く。
- **年齢の優先順位**（`elith-delivery.ts` の subject resolver）:
  **customer_profiles → 登録 DOB（`specialSubjectByUid`）→ age_at_test → scan_md 抽出**。
  customer が正で、欠けた項目だけ登録値で補う。これで DOB 登録済みの回は算出不能が解消する。

## 10. 検証（`npm run verify:special-accounts`）

**ここは静かに壊れる。** 目視では守れない。

1. **スペシャル枠にダミーが 1 件も出ない**（`demoFallbackEnabled` が必ず false）
2. 両方に登録されていても**ダミーが出ない**（§7 の 1 行が効く）
3. 判定に **admin が現れない**（引数が uid 1 つであること）
4. 除外リストが**和のあと**に効く／「戻す」で復帰する
5. **保存物のどこにもメール現物が出ない**（テキスト検査でなく**実際に動かす**）
6. サインインの橋渡しが **early return より前**にある
7. uid 採番が 3 段（記録済み → 既存 → 新規）で、**一度決めた uid が変わらない**
8. **メール登録のその場で有効な UUID が返る**（§4.1.1・⑨ は API を実際に動かす）
9. **再登録・label 変更・DOB/sex 更新で uid が変わらない**（冪等）
10. legacy の uid 空行は **GET では書き換えず、再登録で 1 度だけ**発行される
11. 同じリクエストに複数メールがあっても**それぞれ固有 uid**／`special.account_uids` にも全件入る
12. メール Delete で**資格も外れる**（検査データは消さない）
13. **Auth ユーザー / password / `google_sub` を作っていない**
14. 事前発行 uid と `linkedUid` の競合で **何も書かずに 409**（§4.2.1・`verify:email-auth` ⑫）
15. 競合時に `app_users` / special の資格 / Cookie を **1 つも変更しない**
16. 通常顧客・デモ枠・legacy 行に**退行がない**（解決順序を変えていない）

**退行注入でそれぞれが名指しで落ちること**まで確認する。
注入が落ちなかった検査は、**効かない検査なので差し替える**（本リポジトリの規律）。

## 14. ダッシュボードは「単品購入」の形にする（2026-09-15・発注者指示）

**入口が違えば進捗も違う。埋まらない枠を並べない。**

スペシャルアカウントは EC で購入していないので、**サブスク契約も検査キットも構造的に存在しない**。
材料は自分でスキャンした検診・人間ドック ＋ AI問診だけで、これは CLAUDE.md の
「報告書は 2 タイプある」の**タイプ2（単品購入）** と同じ形。

### 14.1 切り替えの判定

`isSpecialAccount(uid)` **1 本**（`dashboard.astro`）。

**件数で判定しない。** 「キットが 0 件なら単品購入」にすると、実顧客でも連携前は 0 件なので
**コースプランの人の画面が黙って変わる**（デモ枠で同型の実障害を踏んでいる＝§2 の
「実データの有無は条件ではない」）。

### 14.2 進捗は 1 つのセクションに統合する（発注者指示 2026-09-15）

「検査キットだけの進捗管理ではなく、スキャンや AI 問診も含めた進捗管理に」。
**コースプランでも、最初に検診・人間ドックのスキャンと AI 問診が要る**ので、
キットの進捗だけでは「次に何をすればよいか」が分からなかった。

実装 = `ProgressSection.astro`（見出し「進捗」）。**入口で中身が変わる**:

| | コースプラン | 単品購入（スペシャル） |
|---|---|---|
| 並び | ① AI問診 → ② スキャン → **③ 検査キット** → ④ 報告書 | ① AI問診 → ② スキャン → ③ 報告書 |
| プラン名バッジ | 契約から（`subscription.plan_name`） | **app_config `ui.single_purchase_plan_name`**（既定「AI疾病予防報告書（単品）」） |
| 「進捗の詳細を見る」（`/kit`） | 出す | **出さない**（押した先に自分に関係のあるものが 1 つも無い） |
| 検査結果 | 5 種すべて | **人間ドック / 健康診断 の 1 種だけ**（他 4 種は構造的に来ない） |
| 主要導線（AIスキャン / AI問診 の帯） | 出す | **出さない**（進捗の中のボタンと行き先が同じ） |

**キットの行は `KitProgressRows.astro` に一本化する。** 6 段ステッパーと自己申告ボタンは
`kit-self-report.ts` が `data-self-report` で拾う実装と組なので、
**写して 2 か所に増やすと片方だけ腐る**。`KitProgressCard.astro` は見出し + `KitProgressRows` の
薄い器として残してある（現在ダッシュボードからは使っていない）。

**置き場所は検査結果の上。** この入口の「次にすること」が本題で、検査結果は
その結果として後から埋まるもの。逆だと、まだ空のカードを越えた先に本題が来る。

**コースプランの検査カードの並びは 1 px も変えない** — 列指定は 5 枚のときの文字列を
そのまま残してある（枚数から列数を決める形にしたため）。

### 14.2.1 状態は「未実行」「完了済」の 2 語（発注者指示 2026-09-15）

- 未実行 … `status-action` ＋ `action` アイコン ＋ **「実行してください」と促す**。
  ボタンは「AI 問診を実行する」「スキャンを実行する」
- 完了済 … `status-ok` ＋ `ok` アイコン ＋ 日付（スキャンは回数も）。
  ボタンは「もう一度実行する」「別の年度を追加する」
- **アイコン + テキスト + 色の 3 点セット**で出す（UI 確定事項）。色だけで状態を表さない
- 報告書は **未着 / お届け済み**。届いていない回に「もうすぐできます」とは書かない

### 14.3 状態は DB の事実だけ

| ステップ | 根拠 |
|---|---|
| ① AI問診 | `diagnosis.interview_completions` の最新 |
| ② 検診・人間ドック | `test_artifacts` の `health_checkup` の件数 |
| ③ 報告書 | `diagnosis_results.received_at` |

**推測しない。** 届いていない報告書に「もうすぐできます」とは書かない（作成の時期を当社は知らない）。
**見つからない＝未回答**へ倒す（「たぶん済んでいる」側へ倒すと画面が言い切ってしまう）。

### 14.3.1 報告書が無いときはタイルをグレーアウトする（発注者指示 2026-09-15）

「まだ報告書が無いのに開けるのは変」。**そのとおりで、開いても `emptyVM`（帯だけの紙面）** にしかならない。

- **リンクにしない。** 色だけ灰色にすると、見た目は押せなさそうなのに押せてしまう。
  `aria-disabled="true"` の `<span>` にして支援技術にも伝える（検査カードの `.btn-pair-off` と同じ流儀）
- **brand 塗りをやめる。** この画面で唯一の brand 塗り＝主役なので、中身が無い回に主役として置かない
- **受領日の有無で決めない。** デモ用アカウントは行が無くてもサンプルを開けるので、
  受領日だけで判定すると**デモの入口が塞がる**。判定は `!!latestResult || demoShown`

`/report` を直接 URL で開いたときは従来どおり `emptyVM` を返す（塞がない）。
**入口を出さないだけで、紙面の仕様は変えていない。**

### 14.4 AI問診の完了をサーバに残した（migration 1 本）

**実測 2026-09-15**: 完了はどこにもサーバ側の記録が無かった。
`/api/interview/export` は S3 へ書くだけで Supabase への書き込みが **0 件**、
完了記録は端末の localStorage のみ（`session-store.ts` の `InterviewResult`）。
→ **スマホで問診 → PC で開くと「未回答」**に見え、①の状態を出す根拠が存在しなかった。

- マイグレーション `supabase/migrations/20260915000010_interview_completions.sql`（**前進で追加**）
- 書き込み口は `src/lib/interview-completion.ts` の `recordInterviewCompletion()` **だけ**
- **保存先は Cookie から解決した本人の uid**。`body.diagnosticUserId` の申告は使わない
  （他人の完了を作れてしまう。`/api/scan/save` と同じ規律）
- **回答の中身は保存しない** — 完了日時・設問数・`diagnostic_id` の 4 列だけ。
  answers には設問 `M-NAME`（服薬名）等の医療情報が入るので、**中身の置き場所は
  S3 の納品 JSON 1 か所のまま**にする（保管場所を増やさない）
- **S3 の成否と独立**に記録する（S3 未設定の環境で永久に「未回答」にならないように）
- **例外を投げない**（記録の失敗で問診の書き出しを 500 にしない）
- クライアント申告の完了日時は**未来・桁違いなら受信時刻へ倒す**（捏造でなく「受け取った時刻」）
- **`test_artifacts` の CHECK は触らない** — 問診は検査ではないので、値を足すと
  「検査結果 5 種」の一覧にも現れてしまう
