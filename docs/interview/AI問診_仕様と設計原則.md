## 0. 一行サマリ（これだけは絶対に外さない）

> **問診の「フロー・選択肢・回答データ」はプログラム(InterviewEngine)が制御してよい。
> しかし「音声のターン取り・割り込み・復唱・エコー・“誰がいつ何を喋るか”」は Live API/LLM に完全に委ね、プログラムで制御しない。**

Gemini Live API は VAD・割り込み・ターン取りをモデル(サーバ)側で管理する前提で設計されており、公式もフロー制御を LLM に委ねる方向を推奨。**これと戦うと必ず破綻する**（二重化・読み上げ途切れ・先走りのモグラ叩き）。

## 1. アーキテクチャ

- **問診進行**（質問順・分岐・完了・進捗）= クライアントの **`InterviewEngine`**（`interview-script.ts`）が確定的に制御。LLM に問診順を決めさせない → ループ・順序乱れ・選択肢欠落が構造的にゼロ。
- **回答UI**（chip / multi / **list** / matrix / slider / stepper / text）= プログラムが設問種別に応じて描画。タップ回答が一級市民。
- **中止と再開もプログラム側の責務**（フロー/データの範疇であり、音声のターン制御ではない）。
  「中止」は 3 択（①記憶して中止 ②全クリアして中止 ③問診に戻る）で、①は localStorage の
  `InterviewProgress` に途中経過を退避し、次回 `InterviewEngine.resume()` で続きから再開する。
  1 問ごとに保存するので、中止ボタンを押さない離脱（タブを閉じる・リロード）でも戻れる。
  - **`list` は旧 `wheel`（ホイール選択）の置換（2026-08・発注者承認）。** 件数で 3 段階に自動で切り替わる
    （〜7件=ボトムシート / 8〜12件=全画面 / 13件〜=全画面+検索+分類見出し）。実装 `src/scripts/chat/choice-picker.ts`。
    ホイールを廃止した理由・スクロール可視化の 3 点セット（見切れ / sticky 見出し / 残数）・
    フッター被りを構造で防ぐ理由は、同ファイル冒頭のコメントが正本。
- **音声**= **Gemini Live API**（`gemini-3.1-flash-live-preview`）。挨拶・質問読み上げ・回答の復唱・間・割り込みは **LLM が担う**。
- **回答データ** = engine が `AnswerValue` で構造化記録 → Elith `LifestyleQuestionnaireData` として出力。

## 2. 責務分界（最重要・これが全て）

| 領域 | 制御主体 | 補足 |
|---|---|---|
| 質問順・分岐・完了（フロー） | **プログラム(engine)** | 確定的。`recordAndAdvance` |
| 選択肢UI・ウィジェット描画 | **プログラム** | `renderChips` / `openListPicker` 等。設問種別で切替 |
| 回答データの記録・構造化 | **プログラム** | Elith 出力の源泉 |
| タップ回答の受付 | **プログラム** | 音声が無い＝Live API 自発応答なし＝安全 |
| **音声のターン取り / 割り込み / VAD** | **Live API/LLM** | **プログラムで握らない** |
| **音声時の復唱・次質問の“発話”** | **Live API/LLM** | **アプリから発話注入しない**（§4） |
| **エコー/回り込み対策** | **Live API** | マイクゲート等の半二重制御をしない |

> ✅ プログラム制御して良いのは **フロー・選択肢・データ・タップ**。
> ⛔ プログラム制御してはいけないのは **音声の「誰がいつ何を喋るか」**。

## 3. 絶対禁止事項（アンチパターン）と実績

以下は過去に実際に試して**回帰を生み、revert された**手法。二度とやらない。

| 禁止 | 何が起きるか | 実績コミット |
|---|---|---|
| **silent 分岐**（音声/タップで復唱依頼を出し分け） | 読み上げ途切れの回帰 | `f3d59e8`(投入)→`da74e70`(revert)。**再犯: PR #44(closed)**。**2026-09-04 に復唱自体を全廃して解消**（出し分ける対象が無くなった・§4） |
| **AI発話中のマイク送信ゲート（半二重）** | 読み上げの自己割り込み切断 | `f864966`(投入)→`da74e70`(revert) |
| **音声回答時に AI へ「復唱＋次質問」を発話注入** | **復唱/質問の二重化**（二重話者） | `f99f47e` で導入（§5） |
| プログラム側でのターン制御全般 | 途切れ・先走り・二重化 | 7/5 に4件投入→全 revert(`da74e70`) |

> 症状（二重化・途切れ）を見たら、**まず「これは LLM に委ねる領域か？」を判定**する。
> 「ここをコードのゲート/分岐で塞げば直る」と思ったら、それは高確率で**アンチパターンの再犯**。

### 3.1 境界 —「利用者が自分で切る」は禁止に当たらない（2026-09-17 確定・発注者指示）

禁じているのは**プログラムが勝手に判断してマイクを止めること**（AI 発話中の半二重ゲート、
VAD 誤検出よけ、独自の状態機械）。**利用者がボタンを押してマイクを切るのは別物**で、
これは UI であってターン制御ではない。

- 発端 = 実機で **テレビの音をかなり拾う**（2026-09-17）。マイクは開始から中止まで
  送りっぱなしなので、周囲の音が「回答」として確定し得る。
  静かな場所を想定し、それ以外は利用者が自分で切れるようにする。
- **境界を機械で固定してある**（`scripts/verify-interview-live-transport.mjs`）:
  切り替えの呼び出し元は**マイクボタンの click 1 か所だけ**で、`handleServerMessage`・
  マイク送信のコールバック・AI の再生終了からは呼べない。`mic-gate.ts` 自身も
  タイマーもイベント購読も持たない（持たせた瞬間に「プログラム側の制御」になる）。
  退行 5 種を注入して名指しで落ちることを確認済み。
- **止めるのは送信だけ**（発注者裁定）。端末のマイクは掴んだままにする = 戻すときに
  許諾ダイアログが出ない。代わりに **iOS の録音インジケータは点いたまま**になる。
- **AI の読み上げは止めない**（止まるのは送る方だけ）。画面も、切っている間は
  「そのまま話して回答できます」を引っ込める（切ってあるのに出ていたら嘘になる）。
- **前回の選択を持ち越さない**。静かな部屋と電車では答えが違うので、問診を始めるたび「オン」に戻す。
- 見た目 = 質問の下の帯（文言＋右端に 44×44px のボタン）。3 秒周期でゆっくり点滅し
  「いま録っている」を示す（0.33Hz・WCAG 2.3.1 の 3Hz を大きく下回る・
  `prefers-reduced-motion` で止まる）。**中止・スピーカーは触っていない。**
  青はこの部品だけのトークンで、`tailwind.config.mjs` の brand は変えていない。
- **未解決 = 拾った音が回答として確定し得ること自体**（`interpretVoiceAnswer` は
  自由記述を逐語で、スライダーを任意の数字で採る）。マイクを切れるようにしたのは
  利用者が自衛できるようにしただけで、**こちらは別途の判断待ち**。

## 4. 二重話者問題（現在の既知課題）— 定義・原因・正しい直し方

### 定義
音声で回答すると、**話者が2系統**になり復唱/質問が二重に読み上げられる：
- (a) **Live API の自発応答**（ユーザー音声に反応して復唱）— 会話モデルの本性
- (b) **アプリの注入**（`submitAnswer`→`sendToModel` で「復唱＋次質問」）

### 原因（コードで確定済）
- **`f99f47e`（2026-06-18）**が犯人の起点。設問刷新と同時に **`maybeHandleVoiceAnswer`/`interpretVoiceAnswer` を追加し、音声回答を「アプリ注入経路」に載せた**。
- それ以前は音声回答を **LLM が自分で処理**（自発応答＋`present_question` ツールで engine 同期）＝**1話者**で、二重化は発生していなかった。
- **選択肢UI・engine 駆動・タップ注入は f99f47e 以前から存在**し、問題を起こしていない。＝**engine 駆動が悪いのではなく、「音声のターン/発話をプログラムで握った」ことだけが悪い。**

### 【2026-09-04 確定・発注者指示】案1 を全経路へ — AI は質問だけを読み上げる

> **復唱をやめる。AI が喋るのは「質問」だけ。**
> ユーザーの回答についての発話（復唱・確認の聞き返し）は **音声・タップとも行わない**。
> 回答の確認は **画面の `✓ 回答` 表示**が担う（発話では担わない）。

- 音声回答は f99f47e 以降ずっと注入していたが、2026-08 に silent 分岐で注入を止めていた。
  今回**タップ回答からも復唱依頼を外す**ことで、**silent 分岐そのものが消える**（§3 の禁止に合流）。
  AI への依頼文は音声・タップとも「次の質問を読み上げる」1 種類だけになる。
- **副次効果として「先行表示」が構造的に消える。** 復唱が無ければ AI が喋るのは次の質問だけなので、
  画面も同時に次の質問へ切り替えれば**読み上げ対象と表示は必ず同一 Question ID**になる。
  → **プログラム側の状態機械（SPEAKING 等）も ID 照合も不要**。§3 の禁止に触れずに解決する。
- **`schedulePendingQuestion` は廃止**（`live-controller.ts`）。これは「AI 音声の最初の chunk」
  または「2 秒タイムアウト」で次の Q を描画していた仕掛けで、**復唱の *開始* で画面を次の質問に
  変えていた**ため「音声が再生中なのに次の選択肢が出る」の直接原因だった。UI と音声の結合を**外す**。
- **確認発話（「1日20本で合っていますか？」）は実装しない**（発注者判断 2026-09-04）。
  聞き返しは「はい/いいえ」の受け皿＝engine の状態追加を招き、ターン制御に近づく。
  AI は質問だけを読む、で一貫させる。
#### 4.1 直前の回答の確認バー ＋「訂正する」（発注者指示 2026-09-04・実装済み）

復唱を止めた直後に「**回答を目視で確認する前に、次の質問の選択肢がポップアップされて目視できない**」
という報告。**時間の問題ではない**ので、待ち時間では解決しない。

- **真因**: 選択式の設問は `applyQuestionToUI` が **150ms で選択画面を自動展開**する
  （`live-controller.ts`。タップ一手間を省くための既存仕様）。選択画面は `role="dialog"` で
  画面を覆うため、**回答が記録される `#chat-log` がその裏に隠れる**。
  → 2 秒待たせても、待ったあとに同じモーダルが覆う。**「一瞬だけ出す」方式は全部これで死ぬ。**
- **採った案（甲）＝ 消えないものを 1 つ置く**。`#qa-area` の先頭・**質問文より上**に
  `✓ 直前の回答 ／ 訂正する` のバーを常設し、**次に答えるまで消さない**（タイマーで消さない）。
  さらに**同じバーを選択画面のヘッダにも差し込む**（`openListPicker({ lastAnswer })`）ので、
  モーダルが覆っても回答は視界に残る。
- **「訂正する」= 1 問だけ戻す**。`InterviewEngine.rewindTo(id)` が**その設問の回答を消してから**
  `currentId` を戻す。分岐（`when`）はその回答に依存し得るので、消すことで `visiblePath()` が
  正しく計算し直される。**画面側は分岐を持たない**（§2 の責務分界どおり）。
  それ以前へ遡る導線は作らない。供給済（seeded）の設問へは戻さない。
- **ターン制御は足していない**。訂正後は**通常の設問表示と同じ経路**（`applyQuestionToUI` →
  同じ質問の読み上げ依頼）を通るだけなので、読み上げ対象と表示は変わらず同一 Question ID。
  状態機械も ID 照合も無い（§3 の禁止に触れない）。
- **チェック印は自作 SVG**（アイコン部品も絵文字も使わない）。
- **色の役割は 3 つだけ**（発注者指示 2026-09-04・モックで確認 → 実装）:
  **Medical Mist `#DCECEF`（問診ヘッダと同じ色）＝ いま答えるところ**（次の質問＋音声ガイダンス。
  `.qb`）/ **白＋薄い文字 `slate-600` ＝ 済んだこと**（前の回答。`.la`）/
  **teal の文字 ＝ 押せるもの**（「訂正する」だけ）。
  最初は逆で、**済んだ回答が teal で目立ち、いま答える質問は素の白**だった。
  teal はこの画面では操作の色（選択肢・ガイダンス・進捗）なので、前の回答に使うと
  「いま答える対象」に見える。
- **長い回答を省略しない**。複数選択の回答は 360px で `truncate` すると「ビール、…」になり
  **確認バーの意味が消える**（実測）。1 行目＝ラベルと操作 / 2 行目＝回答本文 の 2 行に組む。
- **並び順は 前の回答 → 質問 → 選択肢**。質問の下に置くと
  「次の質問 → 前の回答 → 次の質問の選択肢」となり、前の回答が次の質問の中に挟まって読めない
  （最初の実装がこれで、発注者から指摘を受けた）。モーダルの中でも同じ順で、
  バーはヘッダの最上段・**地を敷かず罫線だけ**。
- **回帰は `npm run verify:interview-ui`**（⑧⑨⑩⑪）。`rewindTo` は engine を実際に動かして
  「1 問だけ戻る／回答が消える／答え直すと元の次の設問へ」を実測する。

> **実装中に踏んだ CSS のバグ（再発防止）**: `global.css` の `.md-summary strong` が
> **閉じ括弧を失っており**、この一連の作業で足した `.vg*`（音声ガイダンスの波形）と `.la*`
> （確認バー）が**まるごとその入れ子**になって 1 つも当たっていなかった。
> markup もソース検査も全部 PASS したまま**見た目だけ死ぬ**壊れ方なので、
> `verify:interview-ui` に ⑪「**計算後のスタイルが当たっているか**」を追加した
> （色や余白の細部は見ない。当たっているかだけ）。

### （参考・旧記述）正しい直し方（合意方針＝案1・未実装）
> **フロー・選択肢・データの program 制御は維持**したまま、
> **音声回答時は AI へ発話を注入しない**（＝ Live API の自発応答を唯一の話者にする）。
> engine は transcript から回答を**裏で記録・前進**させるが、**復唱/次質問の `sendToModel` はしない**。
> 次質問を LLM に読ませる必要がある場合は、**Live API 公認の function calling**（LLM が関数を呼び、アプリは次質問を function の戻り値で返す＝**同一ターン・競合発話なし**）で行う。

- ＝ f99f47e が足した「音声→発話注入」**だけ**を外す。変更範囲は最小、確定性は不変。
- ⚠️ 音声UXはモデル・タイミング依存 → **実装は必ず実機確認**とセット。

## 5. 問診内容の仕様

## 6. Live API 設定・実装上の注意

- モデル: `MODELS.liveChat = gemini-3.1-flash-live-preview`（`src/lib/gemini.ts`・実値は app_config `live.model` が優先）。**preview モデルはサーバ挙動が予告なく変わり得る**（自発応答の強さ等）→ 二重化の“見え方”が時間で変動する要因。挙動が急変したら**モデル版の固定/変更**を第一に検討（これはターン制御ではなく“モデル選択”＝許容）。
- 接続設定（`live-controller.ts` の `ai.live.connect`）: `responseModalities:[AUDIO]` / `speechConfig ja-JP` / `inputAudioTranscription` / `outputAudioTranscription`。
- `realtimeInputConfig.activityHandling`: 現状 `NO_INTERRUPTION`。**turn/VAD 系の設定を安易にいじらない**（挙動が絡む）。変更するなら公式ドキュメント根拠＋実機確認をセットで。
- 重複発話ループ検出（`duplicateAssistantCount`）等の“保険”はあるが、これは最終防波堤であって設計の代替ではない。

## 6.1 発話命令の送信経路（2026-09-17 確定・一次資料で確認済み）

### 6.1.0 なぜ書き換えたか

実機から **④ 画面と音声のズレ**（画面は次の質問なのに音声は前の質問を読み続ける）と
**⑤ 音声の途切れ**が報告された。原因は**プログラムの作りの問題**で、モデルの問題ではない。

1. **同じ「質問を読ませる」操作なのに送信経路が 2 種類ある**
   （1 問目 = `sendClientContent` / 2 問目以降 = `sendRealtimeInput({ text })`）。
2. **受信 PCM にジッタバッファが無い**（到着ごとに `AudioContext` の未来時刻へ予約するだけ）。

### 6.1.1 経路の使い分け（確定）

| 送るもの | API | 理由 |
|---|---|---|
| **プログラム → モデルへの発話命令**（開始挨拶＋最初の質問 / 次の質問 / 訂正時の読み直し / 完了の一言） | **`sendClientContent({ turns:[{role:'user',parts:[{text}]}], turnComplete: true })`** | 順序が保証され、`turnComplete:true` が**前の生成を無条件に中断**する＝画面と音声が揃う |
| **マイク音声** | `sendRealtimeInput({ audio })` | 従来どおり |
| **利用者が入力したテキスト** | **発話命令と同じ経路に載せない**（下記 6.1.3） | `turnComplete:true` に載せると**入力しただけで読み上げが切れる** |

**一次資料（2026-09-17 に実確認）**
- `gemini-3.1-flash-live-preview` のモデルページ:
  「`send_client_content` is supported throughout the entire session lifecycle with explicit roles (`user` or `model`)」
  「Setting `turn_complete=true` unconditionally interrupts active model generation」
  → **3.1 のままで全質問を `sendClientContent` にしてよい**（3.8 へ上げる必要は無い）。
- capabilities:
  「`send_realtime_input` is optimized for responsiveness at the expense of deterministic ordering」
  → `sendRealtimeInput({ text })` は**非対応ではない**（`BidiGenerateContentRealtimeInput.text` は正式に存在）。
  **問題は「順序が保証されない経路を、確定した発話命令に使っていた」こと。**

### 6.1.2 これは「プログラムによるターン制御」ではない

§3 が禁じているのは**独自の会話状態機械・半二重制御**（マイクゲート / `SPEAKING` 状態 /
音声の開始・終了で UI を進める / silent 分岐）である。
**Live API が公式に提供するターン境界（`turnComplete`）を使うことは禁止事項に当たらない。**
UI は従来どおり**音声を待たない**（回答確定と同時に次の質問を描画する）。

### 6.1.3 利用者のテキストは発話命令に混ぜない

`sendToModel()` に 5 用途が相乗りしていた。**発話命令の 3 件だけ**を新しい
`sendModelTurn()`（= ClientContent）へ移す。

| 箇所 | 用途 | 経路 |
|---|---|---|
| `live-controller.ts` 訂正時 | 同じ質問を読み直させる | **`sendModelTurn`** |
| 同 完了時 | 「お疲れさまでした」 | **`sendModelTurn`** |
| 同 次の質問 | 次の質問を読ませる | **`sendModelTurn`** |
| 同 未開始時の自由発話 | 利用者の発話 | `sendRealtimeInput({ text })` のまま |
| 同 フォールバック入力欄 | **テキストでの回答** | `sendRealtimeInput({ text })` のまま |

> フォールバック入力は本来「補助的なテキスト回答」であり、回答は `InterviewEngine` が受け取る。
> **モデルへ送る必然性は薄い**ので、将来 `submitAnswer()` へ直結させる案がある（今回は変えない）。

### 6.1.4 実機で確認できたこと（2026-09-17・観測ログの実測）

**`NO_INTERRUPTION` は `turnComplete:true` の中断を妨げない。** 実測値:

| 見たもの | 実測 |
|---|---|
| `MODEL_TURN_SEND` → `SERVER_INTERRUPTED` | **46 ms**（前の読み上げが残っていた回） |
| 直後の `AUDIO_FLUSH` | 46 ms の 1 ms 後（溜まっていた**約 3.4 秒ぶん**の旧音声を破棄） |
| `UI_APPLY` → `AUDIO_FIRST_CHUNK`（画面と音声のズレ） | **776 ms / 797 ms**（§11.1 の許容「数百 ms」の範囲） |
| 前の生成が既に終わっていた回 | `SERVER_INTERRUPTED` は**来ない**（切る対象が無い＝正しい挙動） |

→ 一次資料に 1 か所で書かれていなかった点は、**実測で解決**した（`NO_INTERRUPTION` は
ユーザー activity による barge-in のみを抑止し、ClientContent の明示中断は通る）。

## 6.2 音声再生（PCM）— bounded buffer（2026-09-17 決定・未実装）

現行 `LiveAudioManager.playPcm()` は到着ごとに未来時刻へ予約するだけで、
**ジッタバッファも最大先行量も持たない**。これが ⑤ の独立した原因になり得る。

- 受信 PCM を JS 側の小さなキューに入れ、**短い look-ahead だけ** `AudioContext` へ schedule する。
- 実装開始値（**公式の推奨値ではない。実機で調整する**）: 初期 140ms / look-ahead 150ms / 最大先行 300ms。
- `nextPlaybackTime < currentTime` は **underflow として記録**する。
- `serverContent.interrupted` で**再生中 source・未再生キュー・予約済み source を全部破棄**する。
- 出力は **24kHz PCM**（Live API 公式）。ただし **iOS Safari で `new AudioContext({ sampleRate: 24000 })` を
  前提に固定しない** — Web Audio 仕様上、デバイスのレートと異なると**ブラウザが resample し遅延が増え得る**。
  `new AudioContext()`（native rate）との A/B を後段で行う。

P3    gemini-3.1-flash-live-preview → gemini-3.8-live → proactive audio を重点検証

**3.8 固有の注意（一次資料で確認済み・2026-09-17）**

- **proactive audio は恒久的に ON**。3.8 モデルページ:
  「Proactive audio is now permanently enabled. Setting `proactive_audio: false` returns an error.」
  → **`false` を指定してはいけない**（エラーになる）。JS SDK の構造は
  `config.proactivity?: ProactivityConfig` の中に `proactiveAudio?: boolean`（`genai.d.ts` 実測）。
  **3.8 では `proactivity` 自体を指定しない。**
- proactive audio は「内容が関連しないと判断したら**応答しない**」機能
  （capabilities: "Gemini can proactively decide not to respond if the content is not relevant"）。
  本アプリは**渡した質問を必ず読む**ことが前提なので、**3.8 移行の最大の Go/No-Go 項目**。
  → **合格条件に「プログラムが指定した質問を 100% 読み上げる」を追加する。**
  `sendClientContent(turnComplete:true)` を送ったのに **audio part も outputTranscription も
  一度も来ない回**を明示的な FAIL とする。**「ClientContent なら無視されない」保証は一次資料に無い。**
- `thinking_level` / `thinking_config` は 3.8 で**渡してはいけない**（当方は元々渡していない）。
- 非同期 function calling が既定（当方は `tools` 自体を渡していないので影響なし）。
- **3.1 は legacy preview だが shutdown date は未発表**（deprecations ページ: "No shutdown date announced"、
  replacement = `gemini-3.8-live`）。**急ぐ理由は無い。**
- ephemeral token は公式が **v1beta** と明記（現行コードは `v1alpha` で**実際に動いている**）。
  `v1alpha` の廃止日・3.8 が v1alpha で提供されるかは**未確認**。P2 で切り替える。

## 8. 用語

| 用語 | 定義 |
|---|---|
| 二重話者問題 | 音声回答時に (a)Live API 自発応答 と (b)アプリ注入 の**2系統が喋る**こと。二重化・途切れ・先走りの根 |
| アプリ注入 | `submitAnswer`→`sendToModel` で AI に「復唱＋次質問」を発話させる依頼。**音声では禁止方向**（§4） |

| silent 分岐 | 音声(silent)とタップで注入内容を出し分ける実装。**禁止**（途切れ回帰） |
