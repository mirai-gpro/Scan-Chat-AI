## 1. 結論（先に要点）

0. **【最重要・読み取り経路は 1 本ではない】** `/kit`・ダッシュボードのキット表示には **3 経路**がある
   （`bridge` / `customer` / `demo`）。どれを使うかは **env で決まる**（`isBridgeConfigured()`）。
   **したがって「どの DB のどの表を見ていたか」を先に確定しないと、原因の議論が成立しない**（§2.5）。
   **確定の方法はある** — `/dashboard` のデバッグ欄が `kit[source=…]` を既に表示している（`dashboard.astro:136`）。
1. **最新仕様の「契約 × 回 × キット」モデルは 1 テーブルも実装されていない**（§2.3）。
   ただし**「Git の migration が 1 セット＝両環境の実 DB が同じ」ではない**（§2.3 の限界）。
2. **`app_bridge.kit_shipment` は「キット」ではなく `orders` のミラー**である。同期関数が `id = orders.id` で
   入れるので、**「条件を満たす注文 1 件につき最大 1 行」**（＝1 キット 1 行ではない）（§2.4）。
3. **回（第 N 回）を表す列が bridge に無い**。`orders` 側には `subscription_id` と `billing_sequence` が**実在するのに**、bridge へ運ばれていない（§2.4・§4）。
4. **これは設計ミスというより、意図的な暫定策**だった。HP/EC 側にキット系テーブルが無いため、bridge v0.3 が「`kit_shipment` を `orders` 由来にする」と明示的に決めている（§5）。**暫定であることが、その後どこにも書かれていなかった**のが問題。
5. **同名に見えて別物のテーブルが 2 つあり、しかも別 DB に在る**（`app_bridge.kit_shipment` 単数 / `customer.kit_shipments` 複数）。
   **どちらも現役**（後者は bridge 未構成時のフォールバック）。仕様書の記述がこの 2 つを取り違えている箇所がある（§7）。
6. 事象「最大 10 件」「がん検査」「検査会社未定」は、いずれも**この構造から決定論的に導かれる**（§6）。

### 2.4 `app_bridge.kit_shipment` の実体 = `orders` のミラー

**定義**（`20260905000010_wellfort_baseline.sql:149-166`）— 全 12 列：

```
id / diagnostic_user_id / order_id / test_type / shipping_status /
instruction_sent_at / shipped_at / tracking_no / delivered_at /
user_received_at / user_returned_at / synced_at
```

テーブルコメントも `'検査キット発送・進捗（orders 由来）'`（同 `:166`）。

**供給元**（同 `:596-638` `app_bridge.refresh_kit_shipment`）：

```sql
INSERT INTO app_bridge.kit_shipment (...)
SELECT o.id, cp.diagnostic_user_id, o.order_number, tp.category, o.shipping_status, ...
FROM public.orders o
JOIN public.customer_profiles cp ON cp.user_id = o.user_id
LEFT JOIN public.test_products tp ON tp.id = o.test_product_id
WHERE o.user_id IS NOT NULL
  AND (p_since IS NULL OR o.updated_at >= p_since)
```

ここから読み取れること（すべて上記 SQL が根拠）：

- **`id = o.id`** … 主キーが注文の ID。**「条件を満たす注文 1 件につき最大 1 行」**。
  **`JOIN public.customer_profiles` は内部結合**なので、**対応する `customer_profiles` が無い注文は 1 行も作らない**
  （初版の「1 注文 = 1 行」は言い過ぎだった）。実際 staging は
  **`orders`=13 / `customer_profiles`=0 / `app_bridge.kit_shipment`=**0** と報告されている。
- **UPSERT のみで DELETE 同期が無い**（`ON CONFLICT ... DO UPDATE` だけ）。
  → 元の注文が消えたり結合対象から外れても、**古い行が残り得る**。
- **差分条件は `o.updated_at` だけ**。→ **`test_products.category` だけを直しても差分 refresh では反映されず、
  bridge に古い検査名が残り得る**。
- **`test_type = tp.category`** … 検査種別は `test_products.category` の**そのままの文字列**
  （日本語の商品カテゴリ。実例 `'がんリスク検査'`＝`wellfort-site/src/data/gancheck-products.ts:27`）。
  **アプリ側が期待する正準コードとは別の語彙**（§2.5.1）。
- **絞り込みは `o.user_id IS NOT NULL` だけ** … **`payment_status` も `shipping_status` も見ていない**。未決済の注文も行になる。
- **回（第 N 回）の列が無い** … `orders` には `subscription_id` / `billing_sequence` が**実在する**（本番の列一覧で確認）のに、**この SELECT が拾っていない**。
- **検査会社の列が無い** … HP/EC DB は検査会社マスタを持たない。

**この同期がいつ走るのかは、リポジトリからは特定できなかった（未確認）。**

- `app_bridge.refresh_all()` が 3 つの refresh を束ねている（baseline `:550-557`）。
- **`refresh_all` / `refresh_kit_shipment` を呼ぶコードは両リポジトリに 0 件**
  （`src/` / `supabase/functions/` / `.github/` を検索）。`orders` への同期トリガも **0 件**。
- 一方 **`pg_cron` は本番で有効**（baseline `:84`）。ただし**スケジュールの実体は `cron.job` のデータ**なので
  スキーマダンプには写らない。
- 設計側は「顧客・プラン=日次 / 発送=取込イベント駆動 or 15〜30分間隔」と決めている
  （`bridge_table_design_draft.md §6`）。

→ **駆動元の確定には DB を見る必要がある。** これが分からないと
**「行が増え続けるのか、ある時点のスナップショットなのか」が言えない**（§6.3）。

### 2.5 読み取り経路（アプリ側）— **3 経路あり、env で切り替わる**

**初版は「`/kit` は `app_bridge` だけを読む」と書いたが誤り。** 実際は 3 経路ある。

| `shipmentSource` | 読む先 | 条件 |
|---|---|---|
| `bridge` | **HP/EC DB** `app_bridge.kit_shipment` | `isBridgeConfigured()` が真 |
| `customer` | **アプリ DB** `customer.kit_shipments` | bridge の env が無いとき（**フォールバックとして現役**） |
| `demo` | 組み込みダミー | デモ用アカウント |

- 分岐は `dashboard-queries.ts:162`・`:177`（`usingBridge ? 'bridge' : 'customer'`）。
- 判定は **env 2 本が揃っているかだけ**（`supabase.ts:67-69`
  = `HP_BRIDGE_SUPABASE_URL` と `HP_BRIDGE_READONLY_KEY`）。**接続先がどの project かは見ていない。**
- **`customer` 経路は `lab_companies` を引いて `lab_name` を解決する**（`dashboard-queries.ts:224`・`:234`・`:239`）。
  **`limit(10)` は両経路にある**（bridge=`bridge-queries.ts:136` / customer=`dashboard-queries.ts:223`）。

> **【切り分けの決定打・コード変更不要】**
> **`/dashboard` のデバッグ欄が `kit[source=… n=… uid=…]` を既に表示している**（`dashboard.astro:136`）。
> **どの経路で表示されたかは、この 1 行を見れば確定する。**

以下は **`bridge` 経路**の記述である（`Scan-Chat-AI/src/lib/bridge-queries.ts:131-137`）：

```ts
bridge.from('kit_shipment').select('*')
  .eq('diagnostic_user_id', uid)
  .order('shipped_at', { ascending: false })
  .limit(10)
```

- **絞り込みは本人のみ**。**回・状態・決済状況のいずれでも絞っていない**。
- 直前の `subscription` は `.eq('status','active').limit(1)`（同 `:128-129`）で絞っているので、**キット側だけ無条件**という非対称になっている。
- `adaptShipment`（同 `:70-98`）が、bridge に無い列を **null 固定**で埋める：
  - `lab_received_at: null` / `lab_completed_at: null`（`:92-93`）
  - `lab_name: null`（`:97`・コメント「bridge 由来は検査会社名を持たない (HP 非保持)」）
  - `subscription_id / subscription_year / subscription_seq: null`（`:77-79`）
- 表示側は `lab_name` が null のとき **`検査会社未定`** と出す（`KitProgressCard.astro:75` / `kit.astro:170`）。

### 2.5.1 検査種別の語彙が食い違い、画面が DB の生文字列を出している（重要）

**アプリ側の正準コードは 5 つ**（`dashboard-queries.ts:471-478`）：

```
health_checkup / blood / genetics / cancer_urine / ai_prediction
```

**そして `testTypeLabel()` の最後の 1 行が、未知の値を素通しする**（同 `:479`）：

```ts
return map[type] ?? { name: type, icon: 'result' };
```

一方 bridge が入れる `test_type` は **`tp.category`（日本語の商品カテゴリ）**で、
`adaptShipment` は **変換せずそのまま渡す**（`bridge-queries.ts:76` `test_type: s.test_type`）。

→ **`category` の値が正準コードでない限り map に一致せず、`/kit` はその文字列をそのまま描く。**
正規化は経路のどこにも無い（実測 0 件）。
**（訂正）初版は「bridge 由来の全行がこうなる」と書いたが過剰断定。**
正しくは「**DB の `category` が偶然 5 つの正準コードのいずれかでない限りこうなる**」。
コード上の `category` の実例は日本語（`'がんリスク検査'`・`'検査パッケージ'`）で正準コードの使用例は 0 件だが、
**DB の全行がそうだと確認したわけではない**。

**この欠陥が今まで見つからなかった理由**: **デモデータは正準コードを使っている**
（`demo-data.ts:203-224` の `blood` / `cancer_urine` / `genetics` / `health_checkup` / `ai_prediction`）。
→ **デモでは正しいラベルが出て、本番でだけ生の文字列が出る。**

### 3.2 1 商品は複数の物理キットに展開される

| ミドル（50代以上） | 年3回(4カ月毎) | 初回のみ | 毎回 | — |
| ミドル（30・40代） | 年2回(6カ月毎) | — | 毎回 | — |

### 4.1 `billing_sequence` を「第 N 回」と同一視しない（2026-09-10 訂正）

  `successful_billing_count` / `billing_count` を更新している。

  とキットごとにルールが違う（§3.2）。**課金回数から発送回は導けない。**

→ 正しくは「**課金回数は在るが、キットの発送回の正本ではない**」。

## 5. なぜ今の形になったのか（経緯・重要）

**現行 bridge は「手抜き」ではなく、当時の実スキーマの制約に合わせた意図的な決定である。**

**ただし原典は Draft（叩き台）であり、「目標モデルへ置換するまでの暫定」とは明記していない**
（2026-09-10 訂正・初版は「暫定策」と書いたが、それは本書の解釈）。正確には:

> **当時の実スキーマ制約に合わせて意図的に採用された `orders` 由来の設計。
> 後続のサブスク駆動仕様から見ると、現在は移行対象の旧設計になっている。**
`docs/architecture/bridge_table_design_draft.md` v0.3 の冒頭に、はっきり書かれている：

> ⚠️ v0.3 重要修正: HP 側に `diagnostic_user_id` / `google_sub` / `kit_shipments` / `lab_tests` /
> `lab_companies` / `subscription_plans` は **存在しない**。実体は `customer_profiles`(+要列追加) /
> `orders` / `subscriptions` / `test_products`。

そのうえで同 §4-3 が「`app_bridge.kit_shipment` — 検査キット発送・進捗（**由来: `orders`**）」と定義し、
**`lab_received_at` / `lab_completed_at` は「削除」**（同 §4-3 末尾）＝
「検査側＝#2 `test_artifacts` から取得」と分担を決めている。

→ つまり **2 つの前提の上に成り立っている**：

- **(a) HP/EC 側にキット系テーブルが無い**間の暫定として `orders` を流用する。
- **(b) 検査完了ステージはアプリ DB 側から補う**（同 §4-3「検査完了ステージは #2(`test_artifacts`) から取得」）。

**そして (b) は実装されていない。** `adaptShipment` は null を入れるだけで、`test_artifacts` を参照していない（`bridge-queries.ts:92-93`）。
つまり **設計上「別経路で補う」とされた穴が、そのまま穴として残っている**。

**教訓として明記しておく**: 暫定策を入れるときは、**暫定である旨と、何を別経路で補う約束なのかを、実装側のコメントだけでなく仕様書側にも残す**。
今回はそれが bridge のドラフト 1 本にしか無く、後続の仕様書（§7）が「本実装」と誤読していた。

## 6. この構造が実際に何を起こしているか

事象＝`/kit` に「がん検査 / 検査会社未定」が最大 10 件並ぶ（2026-09-10 報告・対象注文 `WF-20260909-1WJKKK`）。

### 6.0 【前提】どの経路で表示されたかが未確定（2026-09-10 追記）

**以下の因果は「`bridge` 経路で表示された」場合のもの。まずそこを確定する必要がある**（§2.5）。

レビューでの staging 実測（報告値）:

| 観測 | 値 |
|---|---|
| 対象注文 `WF-20260909-1WJKKK` | staging に**実在**。`category=検査パッケージ` / `amazon` / `paid` / `preparing` |
| 同一 `user_id` の注文 | **13 件**（検査パッケージ 12 = paid 2 / **pending 10** ＋ サプリメント 1） |
| `wellfort-staging.app_bridge.kit_shipment` | **0 行**（`customer_profiles`=0 のため内部結合で 0） |
| `wellfort-staging` の `cron.job` に bridge 関連 | **0 件**（staging は「bridge cron なし」で確定） |

→ **観測された 10 件は staging の bridge からは生成できない。**

**この経路の候補は 2 つ**（どちらも `limit(10)` を持つ）:

- **`bridge` 経路が別 DB（本番）を向いていた** … `isBridgeConfigured()` は env の**有無**しか見ず、
  **接続先の project を見ない**（`supabase.ts:67-69`）。
- **`customer` 経路だった** … アプリ DB の `customer.kit_shipments`。

**ただし `customer` 経路では症状を説明しにくい（未確認の推論）**:
seed（`supabase/seed_kit_demo.sql:30-` ほか）は **`test_type` に正準コード**（`blood` / `cancer_urine`）と
**実在の `lab_company_id`** を入れており、同経路は `lab_companies` から名前を解決する（`dashboard-queries.ts:239`）。
→ この経路なら「**血液検査 / がんリスク**」＋**検査会社名**が出るはずで、
「**がん検査 / 検査会社未定**」にはなりにくい。
**症状は `bridge` 経路（かつ `lab_name` を持たない側）と整合する**が、**断定はしない**。

### 6.1 確定（コードのフローだけで言えること・**`bridge` 経路の場合**）

| 問い | 答え | 出典 |
|---|---|---|
| なぜ最大 **10** 件か | 読み取りが `.limit(10)`。**上限であって、キットが 10 個ある意味ではない** | `bridge-queries.ts:136` |
| その 10 件は何か | **その利用者の `orders` 1 行 = 1 行**。回でもキットでもない | `refresh_kit_shipment`（`id = o.id`） |
| なぜ未決済まで並ぶか | 同期にも読み取りにも `payment_status` の絞り込みが**無い** | 同 SQL の `WHERE` ／ `bridge-queries.ts:131-137` |
| なぜ注文が増えるか | `create-order` が**決済前に** `pending` で INSERT する（仕様違反） | `create-order/index.ts:233-242` ／ `ec_order_on_payment_success_spec.md §2.1` |
| `検査会社未定` はどこから | `adaptShipment` が `lab_name: null` 固定 → UI の fallback 文字列 | `bridge-queries.ts:97` ／ `KitProgressCard.astro:75`・`kit.astro:170` |
| **検査名が商品カテゴリのまま出るのは** | **正準コードと語彙が違い、`testTypeLabel` が未知の値を素通しする**。bridge 由来の**全行**がこうなる | `dashboard-queries.ts:479` ／ `bridge-queries.ts:76` ／ §2.5.1 |
| **「がん検査」という語はコードに無い** | 表示経路・商品データとも **0 件**（ヒットは LP・プライバシーポリシー・Figma 生 HTML のみ） | `grep` 実測（両リポジトリ `src/`） |
| 完了済みが「進行中」に見えるのは | `lab_completed_at` が **null 固定**で、完了判定の材料が存在しない | `bridge-queries.ts:93` |
| 本来は何行出るべきか | **契約 × その回のキット数**（例: 幹部プラン初回 = 3 行）。注文数とは無関係 | `kit_lifecycle_and_handoff_management_spec.md §1` |

### 6.2 「がん検査」という文字列について（2026-09-10 訂正）

**初版で「`test_products.category` 由来（高確度）」と書いたが、これは検証が不足していた。**
発注者の指摘 —「**現在の商品・検査プランに『がん検査』という検査項目は無い。
該当するのは がんリスク（尿）プリベント（ALA-PDS）だけ**」— を受けて文字列そのものを grep し、
**表示の仕組みの側が確定した**（§2.5.1）。

| | 内容 |
|---|---|
| **確定** | **「がん検査」はコードのどこにも無い**（両リポジトリ `src/` の実測。ヒットは LP・プライバシーポリシー・Figma 生 HTML のみで、表示経路・商品データには 0 件） |
| **確定** | **画面は DB の文字列をそのまま描く**。`testTypeLabel` が未知の値を素通しし、bridge は正準コードでない `tp.category` を渡すため（§2.5.1）。**したがって画面に出る検査名は、コードではなく DB の値そのもの** |
| **判明（staging 実測・レビュー報告）** | **`wellfort-staging.test_products` に `category='がん検査'` の商品が 8 件実在する。すべて旧 ALA-PDS 商品で `is_active=false`。** → 発注者の「現行カタログに無い」というご指摘と整合する（**旧商品として DB に残っている**） |
| **未確認** | **その 8 件が今回の 10 件の出どころか**は未確定。**対象ユーザーの staging 注文のカテゴリは `検査パッケージ` と `サプリメント` だけ**で `がん検査` は無い。→ **観測は別 DB（本番）を見ていた可能性が高い**（§6.0） |

**帰結**: 「がん検査」は**表示の付け方の問題ではなく、データの中身の問題**。
仮に語彙を正準コードへ揃えても（§8 案 A′）、**現行カタログに無い商品の行が並ぶこと自体は消えない**
（消えるのは「生の文字列がラベル面に出ること」だけ）。**どの注文行が並んでいるのかを実データで見る必要がある。**

### 6.3 未確認（DB 接続が要る）

- **bridge 同期の駆動元**（§2.4 末尾）。`cron.job` を見れば確定する。
- **`test_products.category` の実値**（＝画面に出ている文字列そのもの・§6.2）。
- 対象 `diagnostic_user_id` の `orders` 実行数と、その `payment_status` / `billing_sequence` の内訳。
- 10 件の内訳が「1 注文の重複」なのか「別注文が 10 件」なのか。
- Amazon Pay の決済方法選択で追加の `orders` が生成されているか（`docs/payment/amazon-pay-handoff-20260909.md` は**別件として分離**することを求めている。**今回の主因と決めつけない**）。

## 8. 埋め方（案・未着手）

**本節は選択肢の提示であって、決定ではない。** 着手前に §9 の判断が要る。

> **【重要・2026-09-10 訂正】案 A は初版の書き方のままでは実装できない。**
> **`app_bridge.kit_shipment` には `payment_status` も発送回も列が無い**（§2.4 の 12 列）。
> 読み取り側だけで「未決済を除外」「回基準で件数を絞る」は**materially 不可能**。
> 初版は自分で 12 列を列挙しておきながらこの矛盾に気づいていなかった。**案 A は下記のとおり縮小する。**

### 案 A：最小（bridge を直さず、見え方だけ整える）

- できるのは **件数と並びの制御だけ**（例: 安定した並び順の付与）。
  **`.order('shipped_at', desc)` は NULL・同値が多いと tie-breaker が無く「どの 10 件か」が保証されない**
  ので、少なくとも `id` 等での安定化は要る。
- ~~未決済・完了済を除外し、件数の上限を「回」基準にする~~ → **列が無いので不可**（上記）。
- **A′：検査種別の語彙を揃える**（§2.5.1）。`tp.category` → 正準コードへの写像を**1 箇所**に置く。
  **ただし A′ は根本策にならない（2026-09-10 訂正）**: サブスクのプラン商品は
  **`category='検査パッケージ'`** で、**1 商品が複数キットに展開される**（§3.2）。
  **`blood` / `cancer_urine` / `genetics` のどれか 1 つには写像できない**（そもそも 1 対 1 でない）。
  → A′ で直るのは**単品商品の見え方だけ**。**プラン契約の行は「検査パッケージ」のままか、誤った 1 種別になる。**
  **`testTypeLabel` の素通しフォールバックは残す**（消すと未知の種別が無言で消える）が、
  **未知の値を admin で見えるようにする** — でないと語彙のずれがまた静かに続く。
  **写像表は実 DB の `category` を見てから作る**（推測で作ると存在しない値を書くことになる＝捏造）。
- 変更範囲：`bridge-queries.ts` 中心。DB 変更なし。
- 効果：**10 件並ぶのは止まる**。検査名も商品カテゴリの生文字列でなくなる。
- 限界：**1 注文 = 1 キットのまま**なので、幹部プラン初回に 3 キットは出ない。検査会社も出ない。
  **表示の症状を隠すだけで、モデルの差は残る。**

### 案 B：中間（bridge に列を足す）

- `refresh_kit_shipment` の SELECT に **`o.subscription_id` と `o.payment_status` を足す**。
  **`billing_sequence` は課金回としてのみ運ぶ**（キットの発送回として使わない・§4.1）。
- **「運ぶだけ」ではない（2026-09-10 訂正）**。実際に要るのは
  **①テーブルへの列追加（migration） ②`refresh_kit_shipment` の変更 ③bridge の型
  ④`adaptShipment` ⑤読み取りクエリ ⑥全件 refresh と stale 行の後始末**（§2.4 の DELETE 同期なし）。
  初版の「コストは見た目より低い」は**楽観的すぎた**。
- 効果：**未決済を除外でき、契約で束ねられる**。
- 限界：**発送回は依然として出せない**（正本が無いため・§4.1）。
- 限界：キットの展開（1→3）と検査会社は**依然できない**（HP/EC DB にマスタが無いため）。

### 案 C：本筋（§3 の目標モデルを実装する）

- `test_kits` / `plan_compositions` / `plan_composition_items` ＋ `subscriptions.plan_composition_id`（`kit_lifecycle_and_handoff_management_spec.md §6.1` に DDL あり）。
- 続いて `kit_shipment_schedule` / `kit_lifecycle` / `lab_handoff`。
- 効果：§3 のすべてが成立する。UI 仕様（ゾーン A/B/C）も初めて実装可能になる。
- コスト：**最大**。契約中のサブスクへの遡及（既存契約にどの版を pin するか）が要る。

### 併せて必要（どの案でも）

- **`create-order` を仕様どおり「決済成立時のみ生成」へ直す**（`ec_order_on_payment_success_spec.md`）。
  ここを直さない限り、**未決済の注文は増え続ける**ので、下流でいくら絞っても対症療法にしかならない。
