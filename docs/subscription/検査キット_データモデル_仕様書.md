## 1. 結論（先に要点）

1. **最新仕様の「契約 × 回 × キット」モデルは、本番・staging とも 1 テーブルも実装されていない**（§2.3）。
2. **`/kit` が読んでいる `app_bridge.kit_shipment` は「キット」ではなく `orders` のミラー**である。同期関数が `id = orders.id` で 1 行を作るので、**「1 注文 = 1 キット」が構造として固定**されている（§2.4）。
3. **回（第 N 回）を表す列が bridge に無い**。`orders` 側には `subscription_id` と `billing_sequence` が**実在するのに**、bridge へ運ばれていない（§2.4・§4）。
4. **これは設計ミスというより、意図的な暫定策**だった。HP/EC 側にキット系テーブルが無いため、bridge v0.3 が「`kit_shipment` を `orders` 由来にする」と明示的に決めている（§5）。**暫定であることが、その後どこにも書かれていなかった**のが問題。
5. **同名に見えて別物のテーブルが 2 つある**（`app_bridge.kit_shipment` 単数 / `customer.kit_shipments` 複数）。**しかも別のデータベースに在る**。仕様書の記述がこの 2 つを取り違えている箇所がある（§7）。
6. 事象「最大 10 件」「がん検査」「検査会社未定」は、いずれも**この構造から決定論的に導かれる**（§6）。

### 2.4 `app_bridge.kit_shipment` の実体 = `orders` のミラー

**定義**（`20260905000010_wellfort_baseline.sql:149-166`）— 全 12 列：

```
id / diagnostic_user_id / order_id / test_type / shipping_status /
instruction_sent_at / shipped_at / tracking_no / delivered_at /
user_received_at / user_returned_at / synced_at
```

テーブルコメントも `'検査キット発送・進捗（orders 由来）'`（同 `:166`）。

**供給元**（同 `:596-638` `app_bridge.refresh_kit_shipment`）：

```sql
INSERT INTO app_bridge.kit_shipment (...)
SELECT o.id, cp.diagnostic_user_id, o.order_number, tp.category, o.shipping_status, ...
FROM public.orders o
JOIN public.customer_profiles cp ON cp.user_id = o.user_id
LEFT JOIN public.test_products tp ON tp.id = o.test_product_id
WHERE o.user_id IS NOT NULL
  AND (p_since IS NULL OR o.updated_at >= p_since)
```

ここから読み取れること（すべて上記 SQL が根拠）：

- **`id = o.id`** … 主キーが注文の ID。**1 注文 = 1 行**が構造として確定している。
- **`test_type = tp.category`** … 検査種別は `test_products.category` の**そのままの文字列**。
- **絞り込みは `o.user_id IS NOT NULL` だけ** … **`payment_status` も `shipping_status` も見ていない**。未決済の注文も行になる。
- **回（第 N 回）の列が無い** … `orders` には `subscription_id` / `billing_sequence` が**実在する**（本番の列一覧で確認）のに、**この SELECT が拾っていない**。
- **検査会社の列が無い** … HP/EC DB は検査会社マスタを持たない。

## 5. なぜ今の形になったのか（経緯・重要）

**現行 bridge は「手抜き」ではなく、当時の制約下での意図的な決定である。**
`docs/architecture/bridge_table_design_draft.md` v0.3 の冒頭に、はっきり書かれている：

> ⚠️ v0.3 重要修正: HP 側に `diagnostic_user_id` / `google_sub` / `kit_shipments` / `lab_tests` /
> `lab_companies` / `subscription_plans` は **存在しない**。実体は `customer_profiles`(+要列追加) /
> `orders` / `subscriptions` / `test_products`。

そのうえで同 §4-3 が「`app_bridge.kit_shipment` — 検査キット発送・進捗（**由来: `orders`**）」と定義し、
**`lab_received_at` / `lab_completed_at` は「削除」**（同 §4-3 末尾）＝
「検査側＝#2 `test_artifacts` から取得」と分担を決めている。

→ つまり **2 つの前提の上に成り立っている**：

- **(a) HP/EC 側にキット系テーブルが無い**間の暫定として `orders` を流用する。
- **(b) 検査完了ステージはアプリ DB 側から補う**（同 §4-3「検査完了ステージは #2(`test_artifacts`) から取得」）。

**そして (b) は実装されていない。** `adaptShipment` は null を入れるだけで、`test_artifacts` を参照していない（`bridge-queries.ts:92-93`）。
つまり **設計上「別経路で補う」とされた穴が、そのまま穴として残っている**。

**教訓として明記しておく**: 暫定策を入れるときは、**暫定である旨と、何を別経路で補う約束なのかを、実装側のコメントだけでなく仕様書側にも残す**。
今回はそれが bridge のドラフト 1 本にしか無く、後続の仕様書（§7）が「本実装」と誤読していた。

## 6. この構造が実際に何を起こしているか

事象＝`/kit` に「がん検査 / 検査会社未定」が最大 10 件並ぶ（2026-09-10 報告・対象注文 `WF-20260909-1WJKKK`）。

### 6.1 確定（コードのフローだけで言えること）

| 問い | 答え | 出典 |
|---|---|---|
| なぜ最大 **10** 件か | 読み取りが `.limit(10)`。**上限であって、キットが 10 個ある意味ではない** | `bridge-queries.ts:136` |
| その 10 件は何か | **その利用者の `orders` 1 行 = 1 行**。回でもキットでもない | `refresh_kit_shipment`（`id = o.id`） |
| なぜ未決済まで並ぶか | 同期にも読み取りにも `payment_status` の絞り込みが**無い** | 同 SQL の `WHERE` ／ `bridge-queries.ts:131-137` |
| なぜ注文が増えるか | `create-order` が**決済前に** `pending` で INSERT する（仕様違反） | `create-order/index.ts:233-242` ／ `ec_order_on_payment_success_spec.md §2.1` |
| `検査会社未定` はどこから | `adaptShipment` が `lab_name: null` 固定 → UI の fallback 文字列 | `bridge-queries.ts:97` ／ `KitProgressCard.astro:75`・`kit.astro:170` |
| 完了済みが「進行中」に見えるのは | `lab_completed_at` が **null 固定**で、完了判定の材料が存在しない | `bridge-queries.ts:93` |
| 本来は何行出るべきか | **契約 × その回のキット数**（例: 幹部プラン初回 = 3 行）。注文数とは無関係 | `kit_lifecycle_and_handoff_management_spec.md §1` |

### 6.2 高確度（未確認）

- **「がん検査」の出どころは `test_products.category`**。同期関数が `tp.category` を `test_type` に入れているため、構造上ここしかない。
  ただし**コード上の実例は `'がんリスク検査'`**（`wellfort-site/src/data/gancheck-products.ts:27`）で、報告された「がん検査」と**文字列が一致しない**。
  → **実 DB の `test_products.category` の値を見て確定する必要がある**（未確認）。

### 6.3 未確認（DB 接続が要る）

- 対象 `diagnostic_user_id` の `orders` 実行数と、その `payment_status` / `billing_sequence` の内訳。
- 10 件の内訳が「1 注文の重複」なのか「別注文が 10 件」なのか。
- Amazon Pay の決済方法選択で追加の `orders` が生成されているか（`docs/payment/amazon-pay-handoff-20260909.md` は**別件として分離**することを求めている。**今回の主因と決めつけない**）。

## 8. 埋め方（案・未着手）

### 案 A：最小（bridge を直さず、見え方だけ整える）

- 変更範囲：`bridge-queries.ts` のみ。DB 変更なし。
- 効果：**10 件並ぶのは止まる**。
- 限界：**1 注文 = 1 キットのまま**なので、幹部プラン初回に 3 キットは出ない。検査会社も出ない。
  **表示の症状を隠すだけで、モデルの差は残る。**

### 案 B：中間（bridge に「回」を運ぶ）

- `refresh_kit_shipment` の SELECT に **`o.subscription_id` / `o.billing_sequence` を足す**（**列は既に `orders` に在る**）。
- 併せて `payment_status` で絞る。
- 変更範囲：HP/EC DB の関数＋テーブルに列追加、bridge 型、読み取り側。
- 効果：**回で束ねられる**ようになり、未決済が消える。
- 限界：キットの展開（1→3）と検査会社は**依然できない**（HP/EC DB にマスタが無いため）。

### 案 C：本筋（§3 の目標モデルを実装する）

- `test_kits` / `plan_compositions` / `plan_composition_items` ＋ `subscriptions.plan_composition_id`（`kit_lifecycle_and_handoff_management_spec.md §6.1` に DDL あり）。
- 続いて `kit_shipment_schedule` / `kit_lifecycle` / `lab_handoff`。
- 効果：§3 のすべてが成立する。UI 仕様（ゾーン A/B/C）も初めて実装可能になる。
- コスト：**最大**。契約中のサブスクへの遡及（既存契約にどの版を pin するか）が要る。

### 併せて必要（どの案でも）

- **`create-order` を仕様どおり「決済成立時のみ生成」へ直す**（`ec_order_on_payment_success_spec.md`）。
  ここを直さない限り、**未決済の注文は増え続ける**ので、下流でいくら絞っても対症療法にしかならない。
